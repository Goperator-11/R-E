# pq_afec: QUIC 핸드셰이크 Initial 비행 FEC (정도현)

R&E 「ML-KEM 적용 시 전송 성능 개선을 위한 QUIC 기반 적응형 FEC 연구」의
**알고리즘·구현·실측** 부분이다. 팀 자료(`../mlkem-quic-amplification/`)와 짝을 이룬다.

---

## 검증 범위와 결과 해석

이 구현은 quic-go v0.61.0에서 클라이언트의 첫 Initial 비행을 보호하는 연구용 테스트베드다. 패딩 증가량 δ와 추가 패리티 수 m을 함께 선택한다.

실측한 12개 설정은 `C ≤ (k−1)(W−h−f)`를 만족하지 않아, 데이터그램 수와 크기를 그대로 둔 제자리 1개 소거 보호가 불가능했다. 다른 패킷 배치와 다른 설정까지 불가능하다는 결론은 아니다.

`InitialPacketSize`를 1280에서 1281로 올린 과거 측정에서 X25519는 약 51.98 ms, X25519MLKEM768은 약 50.86 ms 짧아졌다. 추가량은 데이터그램당 1 B다. 첫 비행이 k개면 총 추가량은 k B이며, 아래 ML-KEM 실험(k=2)은 총 2 B를 추가했다. `1350`과의 비교는 데이터그램당 1 B 대 70 B다.

`A(B)=ceil(3B/P)·P`는 이 테스트베드의 패킷 단위 송신 동작을 설명하는 모형이다. RFC의 송신 한도는 주소 검증 전 수신량의 3배이며, 이 모형의 올림은 RFC가 허용한 추가 예산이 아니다. 다른 QUIC 구현에서 같은 경계나 시간 이득이 성립하는지는 재현하지 않았다. [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1).

정본 명세는 [PADFEC v2 명세](docs/PADFEC%20v2%20명세.md)다. 아래 날짜가 붙은 표는 해당 실행의 기록이며, 코드 수정 뒤의 새 측정 결과로 읽으면 안 된다.

## 핵심 결과

### 1. 1 바이트 절벽 (v2 헤드라인)

```
A(B) = ceil(3B/P)·P ,  P = 1280       Δ_min = floor(A(B)/3 − B) + 1
W = 1280 = P  ⟹  3B = 3k·1280 은 항상 P 의 배수  ⟹  Δ_min = 1   (k 무관)
```

인증서를 두 예측 임계 **사이**에 고정하고 `ips` 만 바꿨다 (RTT 50 ms, 손실 0, n=40):

| 그룹 | `ips=1280` | `ips=1281` | 차이 |
|---|---|---|---|
| x25519 (k=1), cert 4,000 | 104.838 ms (2-RTT) | **52.854 ms (1-RTT)** | **51.98 ms = 1.040 RTT** |
| X25519MLKEM768 (k=2), cert 6,500 | 104.899 ms (2-RTT) | **54.044 ms (1-RTT)** | **50.86 ms = 1.017 RTT** |

부정 시험도 통과했다 — `1279 ≡ 1280`(같은 칸), `1281 ≡ 1350`(**데이터그램당 1 바이트가 70 바이트와 같은 칸에 도달**).
연속 3배 모형은 이 결과를 원리적으로 만들 수 없다.

### 2. 측정한 자연 비행에서는 제자리 보호가 불가능하다

```
제자리(바이트 중립) 1-소거 보호 가능  ⟺  C ≤ (k − 1)(W − h − f)
```

k=1 이면 우변 0 → 데이터그램 하나뿐인 비행은 **원리적으로** 보호 불가.
실측 12개 설정 **전부 위반**, 최근접(ML-KEM/Initial 1450)도 **76.0 B 초과**
(`f=0` 으로 잡아도 60.0 B — 결론이 꼬리표 크기에 강건하다).

> 이건 Singleton/MDS 한계의 QUIC 상수 대입이다. "정리"로 내세우면 반박당한다.
> 값어치는 수학이 아니라 **실측 상수로 60~76 B 모자란다는 부정 결론**에 있다.

### 3. s0 는 상수가 아니다

서버 첫 비행의 고정분 `s0` 가 **서버 패킷 수에 비례하는 항**을 갖는다.
임계 역산과 **서버 바이트 직접 계수** 두 방법이 독립적으로 상수 모형을 기각한다.

| 방법 | x25519 | X25519MLKEM768 |
|---|---|---|
| 임계 역산 | 34.5 B/패킷 | 34.5 B/패킷 |
| 서버 바이트 직접 계수 | **36.1** | **40.0** |
| 평균절대오차 (상수 → 패킷항) | 224.5 → 112.4 B | 144.2 → 101.8 B |

### 4. 신용과 복구는 하나의 패리티로 동시에 못 얻는다

- **증폭 신용**은 패리티가 *복호 가능한 마지막 패킷보다 먼저* 와야 생긴다
  (quic-go `connection.go:669` 의 `if !wasProcessed { continue }`).
- **손실 복구**는 복구본을 넣는 대신 *패리티를 버려야* 회계가 맞는다.
  그 판단은 패리티가 **원본들보다 뒤에** 와야 옳다.

정반대 요구다. 그래서 `m=1` → `[원본…, 패리티]`(복구), `m≥2` → `[패리티0, 원본…, 패리티1]`(앞이 신용, 뒤가 복구).

## 2026-08-20 감사와 수리

알고리즘 전체를 반증 시험으로 감사했다. **수학층·부호층·채널층은 0 건**이었고
(`A(B)` 를 독립 구현과 전수 대조, RS 의 MDS 성질을 모든 소거 패턴으로 확인,
GE 의 DP 를 40 만 시행 몬테카를로와 대조), 결함 4 건이 전부 **v2 비용식 층 한 곳**에
몰려 있었다. 넷 다 고쳤다.

| # | 무엇이 틀렸나 | 증거 | 수리 |
|---|---|---|---|
| 1 | 한 비용식에 손실 모형이 **둘** — 왕복항은 독립 이항, 실패항은 Gilbert-Elliott | 버스트를 1→5 로 바꾸면 `p_fail` 은 6.6 배인데 `n_exp` 는 소수점 6 자리까지 불변 | `joint_arrival_pmf` **하나**에서 두 항을 뽑는다 |
| 2 | 같은 손실 사건을 **두 항에서 각각 청구** | m=0·k=1·p=0.2 에서 `60 + 10 = 70 ms` (참값 60) | 왕복항은 복구 성공 상태에만, 실패는 `(RTT + T_recover)` 한 번 |
| 3 | Python 과 Go 가 **다른 m** 을 고름 | `policy.go` 가 버스트를 `1.0` 리터럴로 박아 둠 → 90 조건 중 **17 건** 불일치 | 버스트를 인자로 흘리고, 결합분포를 표로 심고, `pfailTable`(둘째 출처)을 삭제 |
| 4 | 순위·설명문이 **틀린 바이트 수**를 인용 | 패리티를 `W` 로 세서 m=1 에서 38 B, m=2 에서 76 B 어긋남 | 후보 생성부터 실크기 `W+32+6k` 를 주입 |

- **결함 1·2·3 은 뿌리가 같다** — `n_rtt` 항과 `p_fail` 항이 서로 다른 확률공간에서
  왔는데 한 식에서 더해졌다.
- **헤드라인은 영향받지 않는다.** `p=0` 이면 실패 확률이 0 이라 새 식이 옛 식으로
  정확히 환원된다(자체시험 6). 1 바이트 절벽과 용량 부등식은 순수 산술이고
  전수 검증을 통과했다.
- **결정이 실제로 바뀐 곳은 290 개 조건 중 5 건(1.7%)** 이다. 전부 필요 없는
  1,318 B 패리티를 사던 자리다.
- Python↔Go 대조: **2,688 격자점에서 고르는 m 불일치 0 건**(수리 전 19%).
  표는 `%.17g`(float64 왕복 정밀도)로 찍어 두 구현이 비트 단위로 같다.
- 되살아나지 않도록 `python -m padfec.policy` 에 **자체시험 13 종**을 심었다.
  하나라도 붉어지면 그 결함이 돌아온 것이다.

```bash
python -m padfec.policy     # 19 checks
python -m padfec.quantum    # 39 checks
```

### 헤드라인 재검증 10/10

### 🔥 `T_recover` 를 실측으로 고쳤다

무작위 손실로는 안 보였다(24 조건, 옛/새 비용식 RMSE 6.543 vs 6.548 — 구분 불가).
**측정 경로를 바꿨다** — `-drop-initial 0` 으로 매 판마다 첫 비행을 결정적으로 버리면
모든 표본이 손실 사건이 된다.

| RTT | k=1 | k=2 |
|---|---|---|
| 10 ms | **200.90 ms** (20.09×) | 12.62 ms (1.26×) |
| 50 ms | **200.96 ms** (4.02×) | 57.77 ms (1.16×) |
| 100 ms | **200.73 ms** (2.01×) | 113.88 ms (1.14×) |
| 판정 | **고정 상수** | **RTT 비례** |

가르는 것은 k 가 아니라 **실패한 순간 서버가 하나라도 받았는가**다. 0 개면 ACK 가
없어 PTO(경로 무관 200.86 ms), 1 개 이상이면 ACK 로 구멍이 드러나 즉시 재전송
(1.125·RTT + 1.42). 결합분포가 이미 두 가지를 구분하므로 `p_fail` 을
`p_fail_pto` / `p_fail_ack` 로 쪼개 각각 값을 매긴다.

**검증** (`results/probe_trecover_verify.json`, x25519·k=1·cert 1,000·RTT 10 ms·n=300):

| 손실 | 실측 `off` | 옛 예측 | 새 예측 | 실측 `m=1` |
|---|---|---|---|---|
| 2% | 14.656 ms | 10.20 (−4.46) | **14.02 (−0.64)** | 12.170 |
| 5% | 22.459 ms | 10.50 (−11.96) | **20.04 (−2.42)** | 12.128 |

- 예측 오차 **7.0 배 / 4.9 배** 감소.
- **옛 기본값은 두 조건 모두 `off` 를 최적이라 골랐다 — 실측으로는 가장 나쁜 팔이다.**
- 꼬리에 증거가 있다: 손실 5% `off` 의 **p95 = 211.2 ms**. 그 201 ms PTO 다.
- FEC 가 실제로 복구한다는 직접 증거도 나왔다: 결정적 소거에서 패리티 m=1 이
  **252.09 ms → 52.31 ms**(기준선 +1.04 ms).

## 2026-08-20 v2 정책 Go 이식

폐루프(`-fec auto`)의 결정은 **Go 안에서** 난다. 그런데 v2 로 결정 변수가 둘
(δ·m)이 된 뒤에도 Go 는 **m 만** 골랐다. 헤드라인인 "1 바이트로 왕복 하나 사기"는
사람이 `-ips` 를 손으로 줄 때만 실현됐다 — 정책이 스스로 그걸 고른 적이 없다.

이식한 것은 후보 생성(`levers`)과 순위(`evalCands`)다. 확률 모형은 **옮기지
않았다** — `padfec/table.py` 가 검증된 Python 모형에서 결합분포를 표로 뽑아
심고 Go 는 조회만 한다. 옮긴 것은 정수 산술뿐이라 갈라질 여지가 없다… 는 것이
가정이고, 실제로 한 곳이 갈라졌다.

> `ceilDiv` — Python `-((-a) // b)` 는 `//` 가 **내림**이라 올림이 되지만,
> Go `/` 는 **0 쪽 절사**라 그대로 옮기면 내림이 된다. `ceilDiv(161,2)` 가
> 81 이 아니라 80. 칸이 한 칸씩 낮게 잡혀 δ 후보가 통째로 쓸모없어졌다.
> **5,670 격자점 중 92 건**으로 드러났다.

그래서 격자 대조를 **관문에 상설로 붙였다**(`experiments/gate_go_parity.py`).
격자의 정본은 Go 쪽(`policy.go` 의 `policyGrid`)이고 Python 이 그 출력을 따라간다 —
양쪽에 목록을 각각 적으면 언젠가 갈라지기 때문이다.

- 대조 대상: **(mode, δ, m, InitialPacketSize) 네 개 전부** (예전엔 m 하나였다)
- 당시 **5,670 격자점 불일치 0 건**, 0.6 초.
- 지렛대가 실제로 쓰이는지도 같이 본다(당시): `parity` 64.8% · `none` 31.6% ·
  **`pad` 3.6%(206 건, 그중 δ=1 이 98 건)**. 일치만 보면 양쪽이 나란히
  아무것도 안 골라도 0 건이 나온다.
- 부정 시험: `ceilDiv` 를 일부러 내림으로 되돌리면 **92 건**이 그대로 재현된다.

### 실측 — 정책이 스스로 그 자리를 찾는가

격자 대조는 "두 구현이 같은 답을 낸다"만 말한다. 그 답이 실제 경로에서 값을
하는지는 다른 질문이라 테스트베드에서 따로 쟀다(`_probe_v2converge.py`,
x25519 · cert 4,032 · RTT 50 ms · 무손실 · 라운드당 400 연결, 빈 캐시에서 시작).

| 라운드 | p 추정 | 평상시 선택 | ips 분포 | p50 |
|---|---|---|---|---|
| 1 | 0.0377 | `parity` m=2 | 1280: 388 / 1281: 12 | 52.35 ms |
| 3 | 0.0118 | `parity` m=1 | 1280: 380 / 1281: 20 | 52.40 ms |
| 6 | 0.0073 | `parity` m=1 | 1280: 380 / 1281: 20 | 52.41 ms |
| 7 | 0.0050 | **`pad` δ=1** | 1280: 106 / **1281: 294** | 51.33 ms |
| 8 | 0.0050 | **`pad` δ=1** | **1281: 400** | **51.29 ms** |

8 라운드째 **400 판 전부가 ips=1281 · 패리티 0 개**다. 사람이 손으로
`-ips 1281` 을 준 팔(51.25 ms)에 사실상 닿았고, 패리티 **1,318 B** 를 사던
자리를 **1 바이트**로 대체했다. 헤드라인이 처음으로 정책의 손에서 실현됐다.

> ⚠️ **여유가 1.42 배뿐이다.** `pad` 가 `parity` 를 이기려면 **p < 0.00703**
> 이어야 하는데, 추정기(Jeffreys 사후평균 + 감쇠 0.99)가 무손실 경로에서
> 도달하는 하한이 **0.00495** 다. 넘어가긴 하지만 **감쇠나 탐색 주기를 조금만
> 건드려도 영영 안 넘어간다.** 그래서 `_probe_v2converge.py` 는 측정과 함께
> 이 두 수를 같이 찍는다 — "아직 안 넘어갔다" 와 "영영 안 넘어간다" 는
> 측정만 보면 똑같이 생겼는데 처방이 정반대이기 때문이다.
>
> 6 라운드까지 `parity` 를 고른 것은 **정책이 틀린 게 아니다.** p=0.0073 이면
> 패리티가 실제로 옳다 — `pad` 는 복구를 주지 않아 손실 한 번에 PTO 201 ms 를
> 문다. 틀린 것은 결정 규칙이 아니라 **추정이 아직 참값에서 멀다**는 것이다.

덤으로 하나 더 나왔다. **탐색(무방비 관측)을 δ 후보로 보낼 수 있게 됐다.**
손실률은 `m=0` 인 연결에서만 편향 없이 관측되는데, 예전엔 `m=0` 후보가 맨몸
하나뿐이라 임계 위에서 탐색 한 번이 곧 2-RTT 였다. 그 비용 때문에 탐색 주기가
늘어나 400 연결에 무편향 관측이 3 회뿐이었고, `p` 가 Jeffreys 사전값(0.126)에
정체했다. **δ 는 복구를 주지 않으므로 관측을 편향시키지 않는다** — 이제 가장 싼
`m=0` 후보로 탐색한다.

## 2026-08-26 증폭 신용의 경주 — 모형에 시간 축을 넣다

위 4절("신용과 복구는 하나의 패리티로 동시에 못 얻는다")은 **배치**를 정한
근거였다. 그런데 비용 모형은 그 배치의 결과를 **바이트로만** 세고 있었다 —
패리티 m 개의 바이트를 무조건 증폭 예산에 넣었다. 바이트 회계로는 맞다.
틀린 것은 **시각**이다.

서버는 *복호 가능한 마지막 패킷*을 처리할 때 보낼지를 정한다. 패리티는 복호가
안 되므로 송신을 못 깨운다. 그래서 **뒤따르는** 패리티(m=1 의 유일한 것,
m≥2 의 index 1..)의 바이트는 예산에 들어가되 그 결정보다 늦으면 그 연결에서는
쓸모가 없다. 대역이 걸리면 늦는 정도가 곧 직렬화 시간이다:

    d = 패리티 바이트 / 업링크 대역

### 경주의 모양을 쟀다

`experiments/` 의 임시 탐침으로 전이 구간을 9 점 훑었다
(cert 9000·k=2·RTT 50 ms·**손실 0%**·gap 50 ms·팔당 250 연결).
손실 0 으로 재면 모형의 `p_two_rtt` 가 0 이라 **m1 의 1-RTT 비율이 곧 q(d)** 다.

| 업링크 | 무제한 | 80 | 40 | 30 | 20 | 15 | 10 Mbps |
|---|---|---|---|---|---|---|---|
| 도착지연 d (ms) | 0 | 0.133 | 0.266 | 0.355 | 0.533 | 0.710 | 1.066 |
| **m=1 이 1-RTT** | 1.000 | 0.996 | 0.972 | **0.640** | **0.404** | **0.212** | 0.004 |
| m=2 가 1-RTT | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |

**m=2 가 어느 대역에서도 100%** 인 것이 4절의 배치를 그대로 확인해 준다 —
앞선 패리티는 원본보다 먼저 나가므로 경주 자체가 없다. 흔들리는 것은 뒤따르는
쪽뿐이고 문턱은 `d ≈ 0.3 ms`(서버의 송신 결정 지연) 근처다.

지수꼴·정규꼴을 맞춰 봤지만 평평한 머리와 꼬리를 동시에 못 맞춘다(정규꼴은
`d=0.133` 에서 0.86, 실측 0.996). 그래서 **표로 심고 선형보간**한다 —
확률표를 Go 에 심는 것과 같은 이유다(`padfec/table.py` 머리말).

### 무엇이 바뀌나

`flight_outcome` 이 상태를 셋으로 가른다. (1) 복구가 일어난 상태는 서버가
복구용 패리티를 받아야 원본을 다 갖으므로 **경주가 없다**. (2) 복구가 없으면
앞선 패리티만 결정적이고 뒤따르는 것들은 `q(i·d)` 로 갈린다. (3) 실패는 그대로.

**대역 무제한이면 `d=0` → `q=1` 이라 옛 식과 비트 단위로 같다**(자체시험 9b 가
옛 식을 다시 적어 직접 댄다, 최대 차이 `1.11e-16`). 그래서 무제한에서 이미
검증된 것들은 그대로 남는다.

| 2 Mbps·손실 2% | m0 | m1 | m2 | m3 |
|---|---|---|---|---|
| 실측 | 126.78 | **121.31** | 70.36 | 70.50 |
| 모형(전) | 100.36 | **53.01** | 55.51 | 55.45 |
| 모형(후) | 100.36 | **100.07** | 56.45 | 56.41 |

m=1 의 오차 **68.3 → 21.2 ms**. 남은 것은 모든 팔에 공통인 오프셋이고
(J 는 기준선 대비 *추가* 바이트만 t_tx 로 청구한다) 팔끼리 비교에서 상쇄된다.
**순서가 실측과 같아졌고**, 정책의 선택이 m=1 → m=3 으로 바뀐다.

> ⚠️ **정정 (2026-08-26 저녁).** 위 줄에 원래 "m=3(**실측 최선**)" 이라고
> 적혀 있었다. **틀렸다.** 위 표 자신이 반증한다 — 실측은 m2 70.36 / m3 70.50

> ⚠️ **재정정 (2026-09-03).** 위 정정의 **판정 부분이 다시 뒤집혔다.**

### 왜 여태 안 잡혔나 — 관문과 p18 의 사각지대

- **Go↔Python 관문은 원리적으로 못 본다.** 관문이 재는 것은 *같은 식의 두
  구현이 서로 같은가*이지 *그 식이 테스트베드와 같은가*가 아니다.
  **둘이 똑같이 틀리면 관문은 초록이다.**
- 🩸 **바이너리가 낡으면 관문이 엉뚱한 데를 가리킨다** (2026-09-03 추가).
  관문은 **빌드를 안 한다.** 그래서 `policy.go`·`pfail_table.go` 를 고치고
  다시 빌드하지 않은 채 돌리면 무슨 일이 나는지, 외부 리뷰가 실제로 밟아서
  알게 됐다. 08-29 `fcdd7a0`(반복 라운드 항 + p 축 정밀화) 이전 바이너리로
  돌리면:

      격자점 178,200 · **진짜 불일치 5,016 건** · J 최대 **46.09 ms**
      (최악점 k=3 cert=12000 rtt=100 p=0.2875 L=4 up=10)

  다시 빌드하면 196,020 점에 불일치 0 건이다. 즉 **관문은 조용히 통과하지
  않았다 — 붉어졌다.** 위험한 것은 그 실패가 「진짜 불일치」라고 적혀 있어서
  **모형 결함으로 읽힌다**는 것이다. 멀쩡한 모형을 뜯게 만든다.
  열 수 검사(13 개)로는 못 잡는다 — 그 변경은 열 수를 안 건드렸다.
  `loop2.py` 로 돌면 `BED` 지문이 `.go` 를 포함하므로 안 걸리고,
  **무방비인 것은 관문 단독 실행 경로뿐**이었다. 이제 관문이 빌드 직전
  소스의 SHA256 을 `quicbed/build.sh` 가 남긴 지문과 대조하고, 어긋나면
  격자를 읽기 전에 「모형이 아니라 빌드를 보라」고 말하며 죽는다.
- **격자만 넓히고 표는 그대로면 그건 조용히 초록이다.** 옛 바이너리가 더 적은
  점을 내고 그 점들은 다 맞으므로 「불일치 0 건」이 뜬다 — 덮는 범위가 줄어든
  것은 아무 데도 안 적힌다. `grid_points` 는 결과에 남지만 그 수를 기대치와
  **대조하는 코드는 없다.** 위 지문 대조가 지금은 이 경우도 같이 막지만,
  자가 지문 하나에 걸려 있다는 뜻이기도 하다.
- **`p18` 이 그 축을 안 밟았다.** "고정팔 m=1..4 를 직접 재서 모형을 검증"하는
  단계인데 세 조건의 업링크가 **전부 0(무제한)** 이었다. 모형이 틀린 곳은 대역이
  걸린 자리뿐이라 통과할 수밖에 없었다. 이번에 `("임계위·2Mbps", …)` 조건과
  **m1−m2 를 모형과 대조하는 검사**를 넣었다.

## 정직하게 남기는 한계

- **`c` 의 정본값을 아직 못 박지 못했다** — 34.5 ~ 40.0 B/패킷 구간.
  서버 데이터그램 수를 직접 세는 계측을 붙여야 확정된다.
- **`p12c`(ips 1707·2134)는 영구히 불가능** — veth MTU 1500 + quic-go 가
  `InitialPacketSize` 를 **1452 로 깎는다**. x25519 는 칸 3·4, ML-KEM 은 6·7 밖으로 못 나간다.
- **1 바이트 절벽은 두 s0 모형을 구분하지 못한다** — 상수 모형도 절벽을 맞힌다.
  절벽은 *양자화*의 증거지 *패킷항*의 증거가 아니다.
- **양자화는 곧 RFC 9000 §8.1 위반이다.** quic-go 의 `isAmplificationLimited()` 는
  `bytesSent >= 3*bytesReceived` **불리언 게이트**라 마지막 패킷이 통째로 3배를 넘는다
  (실측 ips=1200 → 3.20배, ips=1350 → **3.79배**). 우리 설계가 그 위반에 기대고 있다.
- **단일 구현 관찰이다.** 양자화 상수 `P=1280` 은 quic-go 의 서버 패킷 크기이므로
  다른 스택에서는 달라진다. quiche·ngtcp2 재현이 없다.
- **폐루프의 후회는 기준 안에 들어왔다. 그런데 그 오차막대를 못 믿는다.**
  `p11`(v1 폐루프)의 수렴후 최악 후회는 **4.919 → 0.857 → 3.24 → (0.63 · 1.17)**
  으로 움직였다. 뜻이 각각 다르다: 4.919 는 비교 팔에 m=3 이 빠져 생긴
  **판정불능의 자국**(결함 아님), 0.857 은 그것을 고친 값, **3.24 는 증폭신용
  수리 뒤의 회귀** — 다만 **셋 다 `n=600`** 이다.

  `--precise`(N=4000)를 두 번 돌렸고 **둘 다 기준 2 ms 를 통과했다**(각각 9/9):

  | 실행 | 최악 후회(수렴 후) | 그 조건의 신뢰반폭 | 헤드라인 조건 |
  |---|---|---|---|
  | 2026-08-29 (커밋본) | **0.629 ms** | ±0.429 | 임계위·손실5% |
  | 2026-08-30 (작업본) | **1.173 ms** | ±0.049 | 임계아래·무손실 |

  🩸 **두 구간이 겹치지 않는다.** 같은 코드·같은 n 인데 0.629±0.429 와
  1.173±0.049 가 만나지 않는다면, 모자란 것은 표본이 아니라 **오차막대 자체**다.
  원인을 찾았다: 08-30 판까지는 팔을 **순차로** 쟀다(m0 → m1 → m2 → m3 → auto;
  2026-09-07 에 조건마다 서버 하나·10 블록 라틴 회전으로 교대 측정하게 고쳤다).
  08-30 의
  헤드라인 조건에서 두 실행의 m 분포는 같은데(auto `{m0:100, m1:1900}`,
  m1 팔 `{1:2000}`) 팔 평균이 **첫 팔 51.34 → 마지막 팔 52.51 ms** 로 단조
  표류했다. 08-29 의 같은 조건은 51.72 → 51.74 로 평평하다. 즉 08-30 의
  1.17 ms 중 대부분은 정책 후회가 아니라 **기계 표류가 후회로 계상된 것**이고,
  오차막대는 팔 **안** 표본분산만 담으므로 그것을 정의상 못 본다.
  → **처방은 팔을 교대(interleave)로 돌리는 것**이다. 표본을 더 늘리는 것이
  아니다. 그때까지 이 두 수는 **「2 ms 는 넘는다」까지만** 말한다.
  (같은 08-30 밤 자료에서 `p16` 도 부하 자국이 잡혀 09-01 에 다시 쟀다.
  `p11` 은 아직 안 다시 쟀다.)

- **후회의 분해는 조건 안에서만 성립한다.** 커밋본 헤드라인 조건에서
  **0.6287 = 탐색세 0.5094 + 결정 규칙 자체의 후회 0.1193** 이다. 즉 남은
  후회의 **81%가 탐색세**이고 결정 규칙이 지는 몫은 0.12 ms 다.
  🩸 이 세 수를 **다른 조건에서 뽑아 섞으면 안 된다** — `worst_probe_tax_ms`
  (0.56)는 임계위·손실2% 의 값이고 `worst_ci95_half_ms`(0.486)는 임계아래·손실5%
  의 값이라, 헤드라인과 짝지으면 산수가 안 맞는다(0.56+0.125 = 0.685 ≠ 0.63).
  `p11_adaptive.py` 가 그 혼동을 주석으로 경고해 두었는데도 실제로 한 번
  일어났다. 인용할 때는 `worst_regret_late_ms` 와
  `worst_regret_late_ci95_half_ms` 를 **쌍으로만** 쓴다.

- **`s/√n` 은 여섯 단계가 같이 쓰는 가정이다** (계통 감사 2026-09-01).
  판정이 실제로 뒤집힌 곳은 `p16` 하나였고 고쳤다. `p11` 은 여유 0.78 ms 라
  안전하지만(뒤집히려면 15 배 필요), **`p15` 의 보고 반폭은 1.25 배 과소평가**다
  (0.74 → 0.92, 여유 35% → 8%). 그 수를 보고서에 그대로 옮기면 정밀도를
  과장하는 것이 된다. `p17`·`p18`·`p20` 은 재실행 뒤 같은 자로 다시 잰다.

- 🩸 **원자료가 커밋보다 앞서 있었다** (2026-09-03 에 해소). 위 08-30 `p11` 을
  포함해 `results/*.json` 11 개가 작업 사본에만 있어서, **커밋된**
  `docs/다음 세션 인계.md` 가 **커밋되지 않은 파일의 수(1.17 ± 0.05)** 를
  인용하는 상태였다 — clone 한 사람이 읽으면 문서와 원자료가 어긋났다.
  이번에 같이 커밋했다. README 가 "`results/*.json` — 보고서의 모든 숫자가
  여기서 나온다"고 적어 둔 이상, **측정이 끝나면 결과도 같이 커밋해야
  그 문장이 참이 된다.** 지금 커밋된 `p11` 은 위 표의 **08-30 판(1.173 ±
  0.049)** 이고, 그 수가 계측 표류를 안고 있다는 것은 바로 위에 적어 둔
  그대로다 — **커밋했다고 표류가 없어진 것이 아니라, 문서와 원자료가
  같은 것을 가리키게 됐을 뿐이다.** 팔 교대 재측정은 아직 안 했다.
- **경주 문턱 `q(d)` 는 이 기계의 값이다.** 서버의 송신 결정 지연 분포라
  기계와 부하에 달렸다(`T_pto`·`c` 와 같은 종류의 환경 상수다). 실제로 다른
  실험과 겹쳐 돌던 탐침은 `d=1.066 ms` 에서 0.387 을 냈고 한가한 기계에서는
  0.004 였다. 정책이 밟는 자리는 `d≥1 ms`(대역 ≤10 Mbps, q≈0)이거나
  `d=0`(무제한, q=1)이라 선택은 안 바뀌지만, **다른 기계에서 다시 재야 한다.**
- **버스트 길이 L 을 Go 는 못 잰다.** 표에 심긴 가정값(`defaultAssumedBurst=1`)을
  쓴다. 경로가 버스트성이면 정책이 실패 확률을 낮게 본다.

## 선행연구에서 우리 자리

- **아이디어 자체는 RFC 규범에 이미 있다** — RFC 9002 §A.9 의사코드 주석:
  *"Initial is padded to **earn more anti-amplification credit**"*.
- **Fastly(McManus)** 가 *"extra 200 bytes of padding will halve the handshake time
  for 7% of connections"* 를 이미 적었다. 우리 기여는 **왜 200 이고 언제 1 로 충분한지**를
  닫힌 식으로 설명하는 것이다.
- **Nawrocki (CoNEXT 2022) §5** 가 우리 문제를 *"open challenge"* 로 명시 등록해 뒀다.
