# 실험 연결 계획

> 계획서 「연구 내용 1(ML-KEM 성능 분석)·2(실험 환경 구축)·4(성능 평가)」를 실행하기 위한 계획이다.
> 알고리즘(내용 3)은 완성·검증됐고, 남은 일은 이것을 실제 환경과 잇는 것이다.
> 작성: 2026-08-14. 전제: 공유 리눅스 서버(격리 규칙은 README 참고).

---

## 0. 전체 구성

다섯 단계로 나뉘고, 단계마다 보고서 재료가 나온다.

```
[1] ML-KEM 핸드셰이크 실측  ->  추정 상수 3개 확정        (연구 내용 1)
[2] 손실 트레이스 수집       ->  NetEm <-> 모델 환율표      (연구 내용 2)
[3] 트레이스 재생 평가       ->  실채널에서 알고리즘 성능    (내용 4 예비)
[4] 데이터 구간 FEC 라이브    ->  QUIC DATAGRAM 위 통합     (연구 내용 2+4)
[5] 핸드셰이크 보호 (스트레치) ->  quic-go Initial 경로 수정
```

[1]~[3]은 스택을 고치지 않고 할 수 있다. 그래서 알고리즘을 QUIC에 심기 전에
실측 데이터를 알고리즘 쪽으로 가져와 평가하는 것(trace-driven)을 먼저 한다.
이렇게 하면 통합 리스크 없이 "실채널에서 어떤가"에 답할 수 있고, [4][5]가
막혀도 연구가 성립한다.

## 1. 단계별 계획

### [1] ML-KEM 핸드셰이크 실측 (연구 내용 1)

연결할 것은 Go 1.24+와 quic-go다. Go 표준 `crypto/tls`가 X25519MLKEM768을
기본으로 쓰므로 클라이언트와 서버를 각각 40줄 정도로 짜면 실제 ML-KEM QUIC 핸드셰이크가
돈다. 대조군(X25519 단독)은 `CurvePreferences` 한 줄로 바꾼다.
- Go는 tarball을 홈 디렉터리에 풀기만 하면 되므로 sudo가 필요 없다.
- 패킷 관찰은 tcpdump 대신 quic-go 내장 qlog로 한다. 패킷 크기, 타이밍, 프레임
  구성이 모두 JSON으로 나오고, 캡처 권한(sudo)도 필요 없어서 공유 서버에서 쓰기 좋다.

수집할 데이터:
| 항목 | 대체할 추정값 | 쓰이는 곳 |
|---|---|---|
| ClientHello 전체 크기 (양쪽 KEM) | `ch_base=350` | handshake.py |
| Initial 1패킷의 실제 CRYPTO 수용량 | `INITIAL_CRYPTO_CAPACITY=1150` | 패킷 분할 계산 |
| 서버 플라이트 크기 (인증서 체인 포함) | `cert_chain=3000` | 서버 shield |
| 실제 패킷 분할 수 (ML-KEM이 정말 2+/5+가 되나) | 연구의 전제 검증 | 보고서 §1 |
| 캡슐화/디캡슐화 시간 (768/512/1024) | (계획서 내용 1 명시 항목) | 보고서 §1 |
| 핸드셰이크 완료 시간 분포 (손실 0~10% x 양쪽 KEM, 각 500회+) | 해석해 검증 | 모델 신뢰성 |

### [2] 손실 트레이스 수집 (연구 내용 2)

연결할 것은 NetEm/tc다. 공유 서버라서 방법이 두 가지다.
- sudo 없이 하는 방법: `unshare -r -n`으로 비특권 사용자 네임스페이스 안에 자기만의
  네트워크(veth 쌍 + netem)를 만든다. 커널이 unprivileged userns를 허용해야 하는데,
  서버에서 `unshare -r -n true`로 1분이면 확인할 수 있다. 이 방법이 되면 실제
  NIC나 다른 사용자 트래픽과 완전히 격리되므로 공유 서버 요구사항에도 맞는다.
- sudo를 쓸 수 있으면 veth+netns 표준 구성을 쓴다(주의: lo에 걸면 양방향에 중복 적용된다).

수집할 데이터:
- 손실 마스크 트레이스. 순번을 붙인 UDP 프로브를 일정 속도로 쏘고 수신을 기록해
  "몇 번째 패킷이 사라졌나"를 비트열로 얻는다. netem 설정별(loss p%, 상관 c%)로
  수십만 패킷씩 모은다.
- 이 트레이스에서 실측 (손실률, 평균 버스트)를 산출해 netem 설정과
  Gilbert-Elliott 파라미터 사이의 환율표를 만든다. 시뮬레이션과 실험을 이어 주는 표다.
- RTT 시계열. 혼잡 유발 시나리오(iperf로 큐를 채우면서)를 포함하고, 혼잡 가드
  검증에 쓴다.

### [3] 트레이스 재생 평가 (스택 수정 없는 실채널 평가)

연결할 것은 sim.py에 추가할 "트레이스 재생 채널"이다. GE 모델 대신 [2]의 실측
마스크를 그대로 흘리는 20줄짜리 확장이고, 알고리즘과 검증 62개는 그대로 둔다.

이 단계에서는 GE 근사가 아닌 실제 채널의 손실 패턴 위에서 정책을 비교한다.
none/static/adaptive/cached의 후회를 실측 트레이스로 다시 계산하고, 시뮬 결과
(§9)와 나란히 놓으면 모델 간극이 정량화된다. 통합 없이 할 수 있는 것은 여기까지이고,
보고서의 뼈대로는 이것으로 충분하다.

### [4] 데이터 구간 FEC 라이브 통합

연결할 것은 QUIC DATAGRAM(RFC 9221, quic-go 지원) 위에 심벌을 실어
나르는 실험 앱이다. 알고리즘은 파이썬 사이드카로 연결한다. Go 송신자가 블록마다
손실 마스크와 RTT를 로컬 파이프로 파이썬 프로세스에 넘기고 (K, r)을 받아온다.
- 알고리즘을 Go로 포팅하지 않는 이유: 검증 62개가 얹혀 있는 파이썬 원본을
  그대로 쓰는 쪽이 결과를 더 믿을 수 있고, 결정은 블록당 1회(수 ms 여유)라
  파이프 왕복 비용이 문제가 되지 않는다.

수집할 데이터는 계획서 내용 4의 지표 그대로다. 전송 총시간, goodput,
블록 복구율, 오버헤드, CPU 사용량을 정책 × netem 설정 × 반복 12회+로 잰다.

### [5] 핸드셰이크 보호 (스트레치 골)

가장 무거운 단계다. Initial 패킷 경로는 스택 내부라 응용 계층에서는 손댈 수 없다.
quic-go를 포크해 클라이언트 Initial 플라이트에 XOR 패리티 패킷 1개를 추가하는
최소 수정을 하고, 수신 측 재조립까지 만든다. K=2에서 r=1이면 RS가 아니라 XOR 한 장으로
충분하다(아무 1패킷 손실이나 복구). 이 단계가 막히면 [1]의 실측 분포와 해석해 예측을
결합해 핸드셰이크 효과를 논증한다(모델이 [1]에서 검증됐다는 전제에서).

## 2. 서버 요구사항

| 필요한 것 | sudo? | 확인 방법 |
|---|---|---|
| Python 3.8+ | X | `python3 --version` (준비됨) |
| Go 1.24+ | X (홈에 tarball) | `go version` |
| quic-go | X (`go get`) | - |
| unprivileged userns (netem용) | X | `unshare -r -n true; echo $?` |
| (대안) sudo로 netns/tc | O | 관리자와 협의 |
| 디스크 ~2GB (Go+모듈+트레이스) | X | - |

아직 모르는 것(도현님 확인 필요): 배포판/버전, Go 설치 여부, sudo 또는
unprivileged userns 가능 여부, 실험을 서버 한 대 안(netns)에서 할지 두 대
사이에서 할지. 이 답에 따라 [2]의 방법이 갈린다.

## 3. 격리 규칙과의 관계

- [1]~[3]의 산출물(qlog, 트레이스)은 전부 프로젝트 폴더 안에 저장한다.
- [4]부터는 소켓을 쓰므로 실험 하네스를 `experiments/` 폴더로 분리한다.
  알고리즘 라이브러리(afec/)의 "무접촉" 발자국 검증은 그대로 유지하고,
  소켓은 하네스에만 둔다.
- netns 안에서 도는 트래픽은 서버의 실제 네트워크와 격리된다(포트 충돌·
  대역폭 간섭 없음). 프로브/전송 실험도 run_confined.sh 아래에서 돈다.
