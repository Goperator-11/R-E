# 학술 동아리 연구문서 정정안

검토일: 2026-09-14. 대상: ML-KEM 적용 시 전송 성능 개선을 위한 QUIC 기반 적응형 FEC 연구.

현재 자료는 연구 질문과 구현 검증을 이어 가는 근거로 쓸 수 있다. 다만 과거 손실 통계의 분모, 첫 비행 바이트 해석, 규격과 구현 동작의 구분, 서로 다른 날짜의 결과 인용을 고쳐야 한다. 이 문서는 원본 Office·PDF·HWP를 보존하면서 제출문과 발표자료에 반영할 수정 문안이다. 수정한 코드의 기능 시험과 과거 실험의 성능 수치는 구분했다.

## 1. 읽고 확인한 범위

`01 R&E 우리학술`, `RnE_연구자료_전체`, `C:\dev\R-E\mlkem-quic-amplification`을 조사했다. 최초 목록은 실제 파일 112개와 ZIP 내부 항목 114개, 합계 226개다. SHA-256으로 같은 파일을 구분했고, 고유한 추출 대상 152개의 텍스트 추출에 오류가 없었다. 이 수가 모든 코드의 정확성을 증명한 수는 아니다.

Office·PDF·HWP는 중복 포함 41개, 고유 파일 31개다. HWP 2개는 내부 파일 해시는 다르지만 추출한 본문은 같았다. DOCX 7종의 문단과 표, PDF 6종 69쪽의 텍스트, PPTX 4종 36슬라이드의 본문·발표 노트·표를 추출했다. 발표 파일 안의 차트 값 3개도 확인했다. 종합기술문서는 50쪽 전체를 추출하고 연구 본문과 핵심 수치·결론을 상세 대조했다. 뒤쪽의 코드·데이터 부록은 현행 소스와 원자료를 기준으로 대조했다. 모든 페이지의 시각 배치, 그림 속 글자와 수식의 렌더링을 직접 검수한 것은 아니다.

고유 Excel 12개는 69시트, 비어 있지 않은 셀 12,348개와 수식 350개를 조사했다. 저장된 수식 결과에 Excel 오류나 누락은 없었다. 350개 수식을 Excel 엔진으로 전부 새로 계산한 것은 아니며, 주요 집계와 크기·비율·실패율을 별도로 계산했다.

`run1.csv` 120행의 1,440셀과 `run2.csv` 250행의 3,250셀은 대응하는 Excel 원자료 시트와 모두 일치했다. 총 4,690셀의 일치는 전사 정확성이다. 원자료가 이미 조건별 요약이므로 연결별 기록, 당시 netem 설정, 워밍업 실패 여부를 복원하지 못한다. 이 한계 때문에 아래의 역사적 분모 문제는 그대로 남는다.

파일별 경로·해시·추출 범위는 함께 제공한 `연구문서_검토목록.csv`에 있다. ZIP 안의 깨진 한글 파일명은 목록에서 그대로 보존했다. 작업 후 실제 Office·PDF·HWP·CSV 원본 43개의 해시를 다시 대조해 변경이 없음을 확인했다.

## 2. 중간보고서에 넣을 대체 요약

이 연구는 ML-KEM 계열 키 교환으로 커진 ClientHello가 QUIC 핸드셰이크에 미치는 영향을 조사하고, 클라이언트 Initial의 패딩과 추가 패리티를 선택하는 정책을 구현한다. 고정한 quic-go 설정의 무손실 실험에서는 인증서 크기가 특정 구간을 넘으면 핸드셰이크 중앙값이 약 1 RTT 증가했다. 이 관측은 인증서 크기, 패킷 배치와 주소 검증 전 서버 송신 제약이 함께 작용한 결과다. 인터넷 전체나 다른 QUIC 구현에서 같은 임계값이 성립한다고 확인한 것은 아니다.

초기에는 기존 패딩 공간에 FEC를 넣으면 송신 비용 없이 복구할 수 있다고 예상했다. 이후 실제 첫 비행 크기와 복구 용량을 계산한 12개 설정에서는 데이터그램 수와 크기를 유지하는 1개 소거 보호 조건이 성립하지 않았다. 현재 구현은 패딩 증가량과 추가 패리티 수를 함께 고른다. 이 불가능성의 범위는 고정한 패킷 수·크기·헤더·프레임 오버헤드에 한정한다.

과거 손실 실험은 워밍업 실패와 측정 성공을 함께 집계했고, 보존된 실행 스크립트와 문서의 손실 방향이 일치하지 않는 부분이 있다. 따라서 유의한 차이가 없다는 결과로 ML-KEM의 손실 취약성 가설을 기각하거나 두 방식의 동등성을 주장하지 않는다. 수정한 수집기는 워밍업을 같은 기준으로 제외하고 연결별 결과와 설정을 보존한다. 수집기의 짧은 기능 시험은 통과했으며, 제출용 손실 성능 수치는 수정된 수집기로 다시 측정해야 한다.

정책의 결과는 모형 재생, 알고리즘 시험, 실제 QUIC 핸드셰이크 측정을 구분해 보고한다. 과거 측정 파일의 통과 표시는 당시 소스와 설정에 대한 기록이다. 이후 코드 수정의 정확성과 새 성능을 보증하지 않는다. 평균 지연 감소만으로 서버 CPU 비용, 혼잡 공정성, 실제 인터넷 배포 효과까지 확인했다고 쓰지 않는다.

RFC 9000은 주소 검증 전 서버의 송신량을 제한하고, 연결에 귀속할 수 있는 수신 데이터그램의 UDP 페이로드를 세도록 한다. 전체 핸드셰이크의 수신/송신 비율이 3보다 작거나 크다는 사실만으로 이 규칙의 준수 여부를 판정할 수 없다. [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1)

패딩으로 추가 증폭 신용을 제공하는 의사코드의 직접 참조는 RFC 9002 부록 A.9다. 기존 A.6 참조는 고친다. 관측한 `200.86 ms`, `1.125×RTT+1.42 ms`는 해당 모형·측정의 값이며, 모든 경로의 PTO 규칙을 대신하는 상수가 아니다. [RFC 9002 부록 A.9](https://www.rfc-editor.org/rfc/rfc9002.html#appendix-A.9)

## 4. 표와 단위의 정정

### 크기 표

`ML-KEM_1단계_측정수치_v2.xlsx`의 `1_크기` 시트 E7:E8은 두 하이브리드 그룹의 공유비밀을 32 B로 적었다. TLS 결합 키 교환의 원시 공유비밀을 뜻한다면 각각 64 B로 고쳐야 한다. ML-KEM의 32 B와 ECDHE의 32 B를 결합한다. TLS에서 이후 파생하는 트래픽 비밀·키와 구분해 열 제목을 적는다. 2026-09-29에 규격 출처를 2026년 8월 발행된 최종 규격으로 갱신했다. 기존 크기 정정은 그대로다. [RFC 10024 §4.1·§4.3](https://www.rfc-editor.org/rfc/rfc10024.html#section-4.3)

| 그룹 | 클라이언트 key_exchange | 서버 key_exchange | 결합 전후를 구분한 공유비밀 |
|---|---:|---:|---:|
| X25519MLKEM768 | 1,216 B | 1,120 B | 결합 결과 64 B |
| SecP256r1MLKEM768 | 1,249 B | 1,153 B | 결합 결과 64 B |

순수 ML-KEM 표의 공개키·비밀키·암호문 크기와 공유비밀 32 B는 별도 표로 유지한다. X25519는 KEM이 아니므로 서버 값을 일괄해서 "암호문"으로 부르지 말고 `서버 key_exchange` 또는 `공개 키셰어`로 적는다. [FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)

### QUIC 증폭 Excel

`quic_amplification_v4.xlsx`는 셀의 숫자만 바꾸면 다른 설명과 어긋난다. 다음 위치를 묶어서 고친다.

| 위치 | 확인한 문제 | 수정 방향 |
|---|---|---|
| 5번째 시트 B6:C8 | 첫 비행 2개·3개와 예산 7,680·11,520 B | 기존 전체 Dial 계수를 첫 비행이라고 부르지 않는다. 해당 조건의 패킷 시간열에서 첫 비행을 확인한 경우에만 1개·2개와 1,280·2,560 B를 적고, 명시한 시점의 수신량으로 예산을 계산한다. |
| 같은 시트 A18 | 위 표와 다른 3,840·7,680 B가 다시 등장 | 계산의 기준 시점과 분모를 통일한다. "서버 수신"과 "클라이언트 수신"도 반대 방향으로 쓰이지 않도록 고친다. |
| 8번째 시트 B7:B10 | 2,400·2,560·2,700·2,914 B를 첫 비행이라고 표시 | 해당 실험의 전체 송신량인지 첫 비행인지 원자료 근거를 적는다. 전체 합계로 만든 1:3.8 비율을 RFC 예산의 인과 근거로 사용하지 않는다. |
| 3번째 시트 E4:E7과 요약 | 비율 약 0.950·0.984·0.993·0.989를 "98~99%"로 요약 | 네 조건 전체를 포함하면 약 95.0~99.3%다. 약 1 RTT라는 표현은 가능하나 정확히 1 RTT로 단정하지 않는다. |
| 4번째 시트 A23 | 500 B 너비의 연속된 전환 영역 | 5,400 B의 일부 꼬리 지연과 더 큰 크기에서 관측되지 않은 꼬리가 연속 구간을 증명하지 않는다. 반복 실험의 조건별 관측으로 적는다. |
| 8번째 시트의 FEC 제안 | 남는 패딩에 FEC를 넣으면 추가 송신이 없다 | 폐기한 초기 가설이라고 표시하고 용량 조건 검증과 후속 구현 설명으로 연결한다. |

Initial UDP 페이로드 1,280 B를 "IPv6 최소 MTU에서 안전한 크기"라고 부르면 안 된다. IPv6 헤더 40 B와 UDP 헤더 8 B를 더하면 IP 패킷은 1,328 B다. 최소 IPv6 MTU 1,280 B를 전제로 한 UDP 페이로드 한도는 1,232 B다. 실험의 IPv4 MTU 1,500 B에서는 UDP 페이로드 1,472 B가 한도이며, 실제 경로 MTU와 패킷 크기를 기록해야 한다. QUIC Initial의 최소 데이터그램 요구와 경로 MTU 제약을 같이 만족해야 한다. [RFC 9000 §14](https://www.rfc-editor.org/rfc/rfc9000.html#section-14)

| MLKEM1024 | 63,630 | 397 | 0.6201% | 6.4553 |
| X25519MLKEM768 | 63,735 | 266 | 0.4156% | 1.3880 |

이 표는 기존 계산의 추적용이다. 서로 다른 손실률·RTT·손실 모형을 합친 값이므로 하나의 독립·동일 조건 표본처럼 해석하는 데에도 제한이 있다. 기존 z값을 재현했다는 이유로 유효한 검정이라고 승인하지 않는다. 새 표에는 조건별 시행 수, 워밍업, 성공·실패·타임아웃, 독립 블록, 신뢰구간과 비교 기준을 함께 둔다.

1차 TLS 자료는 의도한 MTU가 적용되지 않았고 일부 조건이 타임아웃 없는 도구로 중단되었다. 해당 자료는 수집기 개발 이력과 무손실 조건의 제한된 참고로 남기고 손실률 비교의 근거에서는 제외한다. QUIC PTO 비율 12.0%와 10.4%, z=0.79도 표본별 사건 수·분모·검정 절차를 먼저 확인해야 한다. 예를 들어 독립 표본 각 2,000회라고 가정하면 단순 두 비율 검정 z는 약 1.60이므로 0.79와 자동으로 연결되지 않는다. 자료에 없는 분모를 가정해 정정 수치로 확정하지 않는다.

## 6. 실험환경 명세에 반영할 문안

보존된 학교 환경 명세와 현재 PC 환경은 구분한다. 문서가 기록한 Ubuntu·커널·OpenSSL·Go 버전을 현재 WSL에서 확인한 버전으로 소급 수정하지 않는다. 이전 실행의 정확한 바이너리와 커밋을 확보하지 못했다면 그 칸에 "보존 실행본 미확인"이라고 적는다.

손실은 방향별로 정의한다. 보존된 초기 스크립트는 클라이언트 송신측에만 손실을 걸지만 문서는 양방향으로 적었다. 2차 자료를 만든 실행본을 확정하지 못했으므로 당시 방향을 단정하지 않는다. 새 스크립트는 `netem_sides`를 남긴다. 양방향에 각각 독립 5% 손실을 주면 데이터그램 한 개씩 오가는 왕복에서 하나라도 잃을 확률은 9.75%다. 방향별 5%와 종단간 5%를 같은 말로 쓰지 않는다.

옛 `gemodel L% 50%`의 L은 good→bad 전이확률이다. bad에서 전부 버리고 good에서 버리지 않는 기본값을 전제로 정상상태 손실률은 `L/(L+50)`이다. L=5이면 약 9.09%이며 목표 손실 5%가 아니다. 수정한 스크립트는 목표 평균 손실에서 전이확률을 역산한다. 평균 손실을 맞춰도 burst 길이와 독립 손실의 특성은 같지 않으므로 각각 기록한다.

veth 두 끝점은 같은 커널과 자원을 공유한다. 두 물리 호스트와 동일한 환경이라고 쓰지 않는다. netem seed 가능 여부도 운영체제 일반론으로 단정하지 말고 사용한 `tc`·커널에서 지원 여부를 확인해 남긴다. TLS HCT는 TCP 연결 시작부터 TLS 완료까지, QUIC HCT는 Dial 시작부터 QUIC 연결 반환까지라는 측정 경계를 명시한다.

재측정 때는 조건 실행 순서를 블록 안에서 섞거나 교차 배치하고, 연결별 성공·실패와 조건 식별자를 함께 저장한다. 사전 지정한 워밍업은 성공·실패 모두 통계에서 제외한다. 실패를 지연 0으로 채우지 않고 성공 지연 분포와 실패율을 함께 보고한다. 패킷 추적은 첫 응답과 주소 검증 시점을 판별할 수 있어야 한다. 최초 실행의 이상값도 삭제하지 말고 전체 원자료와 제외 기준을 남긴다.

## 7. 선행연구와 신규성 표현

QUIC에서 클라이언트 패딩 증가가 서버 비행을 돕는 효과 자체를 새 발견으로 주장하면 안 된다. Fastly의 2020년 연구는 그 관계와 패딩에 따른 지연 감소를 이미 다뤘다. 이번 연구의 기여는 기존 메커니즘을 ML-KEM 첫 비행·구현의 패킷 경계·정책 선택과 어떻게 연결했고 어떤 조건에서 검증했는지로 한정해 설명한다. [Fastly, 2020년 5월 18일](https://www.fastly.com/blog/quic-handshake-tls-compression-certificates-extension-study)

인증서 크기 p50=4,032 B, p95=5,609 B는 2023년 `draft-jackson-tls-cert-abridge-00`의 약 75,000개 Tranco 인증서 체인 표에서 확인된다. 이 숫자는 2026년 현재 웹 분포나 트래픽 가중 분포가 아니다. 두 분위수만으로 현 인터넷 접속의 특정 비율이 개선된다고 계산하지 않는다. 압축·재개·캐시 여부도 다르다. [해당 초안의 예비 평가 표](https://datatracker.ietf.org/doc/html/draft-jackson-tls-cert-abridge-00#section-4)

RFC 9265는 FEC와 혼잡 제어를 함께 다루는 IRTF 정보 문서다. QUIC 핸드셰이크 FEC를 정의한 표준이나 모든 기존 FEC가 핸드셰이크 이후만 보호한다는 근거로 쓰지 않는다. [RFC 9265](https://www.rfc-editor.org/rfc/rfc9265.html)

Kempf 등의 `A Quantum of QUIC`은 저자 측 arXiv 메타데이터에서 IFIP Networking 2024 발표를 확인했다. Chou·Cao의 `Network Impact of Post-Quantum Certificate Chainsizes on Time to First Byte in TLS Deployments`는 arXiv 원문에서 TLS/TCP 인증서 크기 실험을 확인했지만, 로컬 문서에 붙은 IEEE CNS 2026 게재 표시는 확인하지 못했다. 확인 전에는 arXiv 식별자로 인용한다. 이 논문을 직접적인 QUIC 실험으로 분류하지 않는다. [Kempf 등](https://arxiv.org/abs/2405.09264), [Chou·Cao](https://arxiv.org/abs/2604.24869)

`선행연구노트_Sakk2026`의 로컬 PDF·DOCX는 읽었다. 연결된 출판사 원문은 이번 접근에서 열리지 않아 Table 1의 수치와 노트의 해석을 독립 검증하지 못했다. "선행연구 수치 검증 완료"로 표시하지 않는다. 본문에서 일부 선행연구를 원문 없이 요약에 의존했다고 적은 부분도 남아 있으므로, 모든 관련 문헌을 읽어 신규성을 확인했다는 결론은 삭제한다. 확인한 메타데이터, 초록, 실제로 읽은 본문 범위를 각각 적는다.

## 8. 발표자료 4종에 공통으로 반영할 내용

LoRa SF별 페이로드 51·115·222 B에 ML-KEM-768 공개키 1,184 B를 나눠 올림한 24·11·6은 계산 자체는 맞다. 그러나 이를 이번 QUIC 실측 패킷 수로 사용하면 안 된다. 발표에서는 초기 저속 무선망 동기 자료로 표시하거나 현재 veth 실험 설명에서 뺀다. RSSI·SNR로 정한 Good/Fair/Poor도 현재 통제변인이 아니면 결과 표와 연결하지 않는다.

"QUIC에는 HOL blocking이 없다"는 표현은 "독립 스트림 사이의 전송 순서 대기를 줄인다"로 고친다. 같은 스트림 안의 순서 대기까지 사라지는 것은 아니다. "손실 즉시 복구", "재전송 없음"은 "충분한 복구 심벌이 도착하고 구현의 복구 조건을 만족하면 재전송을 기다리지 않고 복구한다"로 바꾼다. Shor 알고리즘 설명은 충분한 규모의 양자 컴퓨터라는 조건을 적는다.

발표의 예시 `quic-server --kem ml-kem-768`은 저장소에 제공된 실행 명령이 아니다. 실제 빌드한 qamp·qhct와 지원 그룹의 명령으로 교체한다. 처리량·CPU·전력·에너지·실제 무선망을 측정하지 않았다면 해당 지표의 개선 결과를 쓰지 않는다.

| summarize_amp | CSV 행 수·중복·상태·수치 검사, 짝수 표본 중앙값, 실패 분리 | 독립 회귀 시험 6개 통과 |

WSL의 OpenSSL 3.5.5 런타임에는 개발 헤더가 없었다. 공식 Ubuntu 저장소에서 `libssl-dev_3.5.5-1ubuntu3_amd64.deb`를 받아 작업 폴더에만 풀고 그 헤더로 빌드했다. 시스템 패키지를 설치하거나 라이브러리를 교체하지 않았다. Bash 스크립트의 CRLF 때문에 구문 검사가 실패하는 문제도 LF로 고쳤다.

마지막 qhct 오류 처리 보완 뒤에는 최종 소스를 Linux용으로 빌드해 WSL localhost 2회를 추가 확인했다. 협상 그룹이 일치하고 qlog 2개가 정상 생성되었다. CSV를 `/dev/full`에 쓰게 한 경우와 qlog를 `/proc`에 만들게 한 경우 모두 성공으로 처리하지 않고 오류를 내며 종료했다.

localhost 시간 값은 성능 비교로 쓰지 않는다. 새 코드의 전체 TLS 손실 스윕, 인증서·Initial 크기 스윕, 방향별 netem 실제 적용 확인과 첫 비행의 패킷 추적은 추가 수집이 필요하다. 원본 보고서의 시험 수나 통과 수와 이번 도구 기능 시험의 수를 합산하지 않는다.

## 10. 제출 전 남아 있는 검증

현재 문서만으로 복원할 수 없는 것은 당시 실행 바이너리·정확한 netem 방향, 연결별 워밍업 실패 기록, 일부 인용 원문과 신규성의 전체 문헌 조사다. 예산표의 1,180,000+830,000=2,010,000원은 합산이 맞지만 실제 집행·승인 여부는 검증하지 않았다.

최종 제출용 실험에는 수정된 코드 지문, 전체 조건표, 연결별 CSV, 독립 블록, 원자료에서 생성한 표·그림을 함께 보존한다. 정책 선택에 쓴 조건과 최종 평가 조건을 분리하고, 실패 항목도 그대로 싣는다. 역사 자료를 설명하는 문단에는 날짜를 붙이고, 수정 후 재측정하지 않은 결과에는 그 사실을 표시한다.
