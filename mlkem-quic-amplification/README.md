## 자료의 현재 해석

무손실의 고정된 quic-go 설정에서 인증서 크기에 따라 핸드셰이크 중앙값이 약 1 RTT 증가하는 구간이 관측되었다. 역사 자료의 전환 구간은 X25519에서 3,300~3,400 B, X25519MLKEM768에서 5,900~6,000 B다. 이 범위는 해당 구현·인증서·Initial 크기에 대한 관측이며 인터넷 전체의 임계값이 아니다.

큰 키셰어가 서버의 송신 예산을 늘리는 효과와 패킷 손실 비용은 함께 존재할 수 있다. 유의한 손실률 차이를 찾지 못한 결과만으로 손실 취약성 가설을 기각하거나 FEC의 개선 대상이 없다고 결론 내릴 수 없다.

`qpkt`와 `qamp`가 재는 바이트는 클라이언트의 Dial 시작부터 반환까지다. first flight 또는 주소 검증 전 구간과 같지 않다. 따라서 이 전체 합계에 3을 곱한 값을 서버의 최초 증폭 예산으로 부르면 안 된다. RFC 9000의 상한은 주소 검증 전 서버 송신이 귀속 가능한 수신 UDP 페이로드의 3배를 넘지 않는 것이다. 패킷 생성 전에 남은 예산만 확인해 한 패킷을 초과 송신하는 구현 관찰은 별도로 다룬다. [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1)

## 파일

| 경로 | 용도 |
|---|---|
| `src/` | 수정한 측정 코드, 실행 스크립트, 고정한 Go 모듈 |
| `data/` | 2026년 8월 분석용 Excel과 TLS 집계 CSV |
| `docs/` | 당시 보고서와 인수인계서. 정정 문서 우선 참조 |
| `archive/` | 이전 코드와 자료. 재현 실행의 기준으로 사용하지 않음 |

`data/raw/run1.csv`와 `run2.csv`는 연결별 원자료가 아니라 조건별 요약이다. Excel 원자료 시트와 대조한 120행·250행, 총 4,690개 셀은 일치했다. 이것은 전사 검증이며, 소실된 연결별 시간열이나 네트워크 설정을 복원한 검증은 아니다.

## 빌드

Linux에서 다음처럼 각 Go 파일을 따로 빌드한다. 세 파일이 독립된 main 프로그램이므로 `go build .`로 함께 빌드하지 않는다. `src/go.mod`와 `go.sum`은 quic-go v0.61.0을 고정한다.

```bash
cd mlkem-quic-amplification/src
CGO_ENABLED=0 go build -o qamp qamp.go
CGO_ENABLED=0 go build -o qpkt qpkt.go
CGO_ENABLED=0 go build -o qhct qhct.go
```

TLS 도구는 ML-KEM을 지원하는 OpenSSL 3.5 이상 헤더와 라이브러리가 필요하다. 학교의 conda 환경을 사용하는 경우:

```bash
conda activate oreo_34
gcc -O2 hct_v2.c -o hct_v2 \
  -I"$CONDA_PREFIX/include" -L"$CONDA_PREFIX/lib" \
  -lssl -lcrypto -lm -Wl,-rpath,"$CONDA_PREFIX/lib"
```

`patch1_certsize.py`와 `patch2_initpkt.py`는 옛 코드 조각을 수정하던 이력 파일이다. 현재 qamp에는 두 기능이 들어 있으므로 실행하지 않는다.

## 실행

`bash check_env.sh`로 도구와 격리된 netem 사용 가능 여부를 확인한다. user namespace 또는 netem이 비활성화된 환경에서는 측정 스크립트가 실패할 수 있다. 측정망 구성 실패를 무시하고 결과를 만들지 않는다.

```bash
# TLS 축소 스윕: 양방향 지연은 각각 목표 RTT의 절반.
# 손실률은 각 방향의 패킷 손실률이다.
NETEM_SIDES=both bash run_v3.sh quick

# QUIC 증폭 스윕. 아래는 4개 조건의 동작 확인용 표본 규모다.
CERT_SIZES="3300 3400" KEMS="X25519 X25519MLKEM768" \
  ITERS=10 WARMUP=3 INITIAL_SIZE=1280 bash amp_sweep.sh

# 집계기 회귀 시험
python3 -m unittest test_summarize_amp.py
```

`amp_sweep.sh`는 실행 위치에 의존하지 않고 src의 qamp를 사용한다. BIN·OUT 환경변수로 경로를 바꿀 수 있다. 조건별 연결 CSV, 서버·클라이언트 로그, 인증서 목표값과 실제 DER 바이트를 보존한다. 요약은 원자료의 성공 연결에서 중앙값과 평균 바이트를 계산하고 실패·타임아웃을 별도 기록한다. 성공 표본이 없으면 지연 칸을 비워 두며, 행이 누락되거나 반복 번호가 중복되면 중단한다.

`qamp -initpkt 1281`은 데이터그램마다 목표 크기를 1 B 늘린다. 첫 비행이 2개라면 총 증가량은 2 B다. 이 도구의 initpkt 범위는 IPv4 MTU 1500을 전제로 1200~1472 B로 제한했다. 실제 송신 크기와 경로 MTU는 별도로 확인해야 한다.

## 기존 자료의 결함

1차 TLS 손실 자료는 의도한 MTU가 적용되지 않았고 일부 조건은 타임아웃 없는 도구로 중단되었다. 손실 성능 비교에 사용할 수 없다.

2차 TLS 자료를 만든 스크립트 버전은 확정하지 못했다. 문서는 양방향 손실을 주장하지만 저장된 초판은 클라이언트 송신측에만 손실을 걸었다. 현재 스크립트는 `netem_sides`를 기록한다. 기본값 one은 과거 동작을 재현하고, both를 명시하면 양방향에 같은 손실률을 건다.

옛 burst 설정 `gemodel L% 50%`의 L은 목표 손실률이 아니라 good→bad 전이확률이다. 기본 bad 상태의 손실 100%, good 상태의 손실 0%를 전제로 정상상태 손실률은 L/(L+50)이다. 표기 5%는 약 9.09%였다. 현재 코드는 목표 손실률에서 전이확률을 역산한다.

옛 hct·qhct는 워밍업 실패를 fail에 포함하면서 n에는 측정 성공만 셌다. 기존 run2의 n+fail은 330,046이고, 설계상 측정 시행은 330,000이다. 역사 z값은 이 혼합 분모에서 재계산할 수 있으나, 이를 오류 없는 통계로 인용하면 안 된다. 연결별 원자료와 당시 실행본 확인 또는 재측정이 필요하다.

## 2026-09-14 수정과 확인 범위

qamp·qpkt는 연결마다 소켓과 Transport를 분리해 이전 연결의 지연 패킷이 다음 집계에 들어오는 경로를 차단했다. 송신 계수는 WriteTo가 실제 반환한 바이트만 센다. qpkt의 성공 평균 분모, qamp의 initpkt·워밍업·타임아웃 기록, qhct의 qlog v0.61 API와 probe 동시접근을 수정했다.

amp_sweep은 사람이 읽는 "평균:" 문자열을 잘못 찾아 CSV 열을 누락하던 경로를 원자료 집계로 바꿨다. 두 스윕은 설정·서버·측정 실패를 중단 사유로 처리한다. hct의 타임아웃은 TCP와 TLS 전체에 하나만 적용하고, 잘못된 인수와 CSV 쓰기 실패를 오류로 보고한다.

Windows Go 1.27.0에서 세 도구를 빌드하고 각 4회 localhost 연결을 확인했다. qhct qlog 6개는 비어 있지 않고 JSON 구문을 만족했다. qamp의 측정 2회 타임아웃과 워밍업 제외도 확인했다. 집계기 회귀 시험은 6개 모두 통과했다.

WSL Ubuntu에서는 공식 Ubuntu 저장소의 OpenSSL 3.5.5 개발 패키지를 작업 폴더에만 풀어 헤더를 사용했다. 시스템에 설치하거나 라이브러리를 교체하지 않았다. `gcc -Wall -Wextra` 빌드 후 X25519·MLKEM768·X25519MLKEM768을 각각 측정 4회와 워밍업 2회 연결했고 협상 그룹도 일치했다. TLS를 응답하지 않는 localhost 서버에서 측정 2회 타임아웃, 워밍업 제외, 잘못된 반복 수 3종의 거부를 확인했다. run_v3·amp_sweep·check_env의 Bash 구문 검사도 통과했다.

최종 qhct 소스는 WSL localhost 2회를 추가 확인하고, `/dev/full` CSV 쓰기와 `/proc` qlog 파일 생성 실패가 오류 종료로 드러나는 것을 확인했다.

이 확인은 도구 동작 시험이며 학교 환경의 성능 수치를 재측정한 결과가 아니다. 전체 손실·증폭 스윕 결과는 수정한 측정 도구로 다시 수집해야 한다.
