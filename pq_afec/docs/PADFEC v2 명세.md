# PAD-FEC v2 명세 — 양자 인식 첫 비행 설계

> v1(고정 m 패리티)에서 v2(δ·m 두 지렛대)로. 2026-08-20.
> 이 문서가 구현·실험·검증의 정본이다. 숫자는 전부 `experiments/results/*.json` 에서 왔다.

---

## 0. 왜 다시 설계하는가

v1 은 결정 변수가 하나였다 — **패리티 데이터그램 몇 개(m)**. 그런데 실측이
두 가지를 보여줬다.

1. **증폭 신용은 바이트 수에만 의존한다.** 내용은 무관하다(p2 `ips_sweep`,
   e20/e21 `dup` 팔 — 내용이 문자 그대로 동일한 복제 데이터그램도 임계를 옮겼다).
2. **허용량은 연속이 아니라 1,280 B 계단이다.** `허용 = ceil(3B/1280)·1280`.

이 둘을 합치면 v1 이 못 보던 지렛대가 나온다. 신용만 사고 싶다면
**데이터그램을 하나 더 보낼 필요가 없다** — 기존 데이터그램을 몇 바이트
키우면 된다. 그리고 계단이므로 그 "몇 바이트"가 경계 근처에서는 **1 바이트**다.

## 1. 기호

| | |
|---|---|
| `C` | ClientHello CRYPTO 총 바이트 (TLS 설정이 정함, 우리가 못 바꿈) |
| `W` | 데이터그램 하나의 와이어 크기 = `InitialPacketSize` (≥1200, **우리가 정함**) |
| `h` | 패킷당 고정비 (롱헤더+AEAD 태그+CRYPTO 머리). 실측 47~51 |
| `f` | FEC 꼬리표 |
| `k` | 첫 비행 데이터그램 수 = `ceil(C/(W−h))` |
| `B` | 첫 비행 총 바이트 = `k·W` — **실측으로 확인됨**(p1 12/12) |
| `P` | 서버 패킷 크기. quic-go 1280 |
| `A(B)` | 주소 검증 전 서버 허용량 = `ceil(3B/P)·P` |
| `S` | 서버 첫 비행 = `cert + s0` |
| `s0` | 인증서를 뺀 서버 첫 비행 (SH+EE+CV+Fin+오버헤드) |

`n_rtt = 1 if S ≤ A(B) else 2`.

## 2. 두 지렛대

| 지렛대 | 무엇 | 신용 | 복구 | 바이트 값 |
|---|---|---|---|---|
| **δ** | 데이터그램을 키운다 `W → W+δ` | `+3kδ` | 없음 | `kδ` |
| **m** | 패리티 데이터그램 `m` 개 추가 | `+3mW` | 1-소거 복구(m=1) | `mW` |

### 보조정리 1 (지배)

같은 추가 바이트 `Δ` 에서, `Δ ≥ W` 이면 **패리티가 패딩을 엄격히 지배한다.**

> 증명. 신용은 바이트 수에만 의존하므로 두 방식의 신용이 같다(`3Δ`).
> 패리티는 추가로 1-소거 복구를 준다. 복구 확률은 단조 증가이므로
> 어떤 손실률에서도 손해가 아니다. ∎

따라서 **`Δ ≥ W` 일 때 패딩으로 채우는 것은 결코 최적이 아니다.**
반대로 `Δ < W` 이면 패리티 데이터그램을 만들 수 없다(Initial 데이터그램은
≥1200 이어야 하고 그건 곧 데이터그램 하나다) — 그때는 δ 가 **유일한** 수단이고,
동시에 매우 싸다.

### 보조정리 2 (경계까지의 최소 바이트)

현재 허용량이 `A(B)` 일 때 다음 칸으로 올라가는 최소 추가 바이트는

```
    Δ_min = floor(A(B)/3 − B) + 1
```

> 증명. 다음 칸에 들어가려면 `3(B+Δ) > A(B)`. 정수이므로 위 식. ∎

### 따름정리 (기본값이 최악이다)

quic-go 기본 `W = 1280 = P` 이면 `B = k·1280` 이고 `3B = 3k·1280` 은 **항상
`P` 의 배수**다. 그러므로 `A(B) = 3B` 이고

```
    Δ_min = floor(3B/3 − B) + 1 = 1
```

**k 와 무관하게 언제나 1 바이트다.** 즉 quic-go 클라이언트는 기본 설정에서
증폭 양자 경계에 **정확히 걸터앉아** 있고, 1 바이트만 더 보내면 서버 예산이
`P = 1,280 B` 늘어난다. 이것이 얻을 수 있는 **최대 낭비**다.

인증서를 두 예측 임계 사이(3,340 < 4,000 < 4,585.5)에 놓고 `ips` 만 바꿨다.

|---|---|---|---|---|---|---|---|---|
| 1279 | 1279 | 3,840 | 3 | 3,340.0 | 2 | **2** | 104.496 ms | 1.00 |
| **1280** | 1280 | 3,840 | 3 | 3,340.0 | 2 | **2** | **104.838 ms** | 1.00 |
| **1281** | 1281 | 5,120 | 4 | 4,585.5 | 1 | **1** | **52.854 ms** | 0.025 |
| 1282 | 1282 | 5,120 | 4 | 4,585.5 | 1 | **1** | 53.468 ms | 0.00 |
| 1350 | 1350 | 5,120 | 4 | 4,585.5 | 1 | **1** | 53.452 ms | 0.00 |

**1 바이트에 51.98 ms = 1.040 RTT.** 검사 5/5 통과.

- **부정 시험 통과**: 1279 와 1280 이 **같은 칸**(둘 다 2-RTT). 경계는 정확히 1281 이다.

- 첫 비행 = `k × ips` 가 5개 설정 전부에서 성립.

> `Δ_min(B=1200) = floor(3840/3 − 1200)+1 = 81` → 경계는 `W=1281`.
> `Δ_min(B=1280) = 1` → 경계는 `W=1281`. **두 계산이 같은 점을 가리킨다.**

## 2.5. s0 는 상수가 아니다 — 서버 패킷 수 항 (v2 에서 새로 잡음)

감사에서 "s0 가 그룹 안에서 34.5 B 씩 갈린다"가 **불일치**로 보고됐다.
불일치가 아니라 **빠진 항**이었다.

| 그룹 | A | 서버 패킷 수 `n = A/P` | s0 실측 |
|---|---|---|---|
| x25519 | 3,840 | 3 | 500.0 |
| x25519 | 5,120 | 4 | 534.5 |
| X25519MLKEM768 | 7,680 | 6 | 1,734.5 |
| X25519MLKEM768 | 8,960 | 7 | 1,769.0 |

두 그룹에서 **패킷당 증분이 정확히 같다.**

```
    s0(n) = s0_base + n · c ,     c = 34.5 B
    s0_base:  x25519 396.5 ,  X25519MLKEM768 1527.5
    차이 1,131 B ≈ ML-KEM-768 암호문 1,088 B + 43 B
```

즉 **서버 첫 비행은 인증서 + 고정분 + (패킷 수 × 패킷 오버헤드)** 다.
칸이 올라가면 서버가 패킷을 하나 더 쓰므로 s0 도 그만큼 커진다.
`s0` 를 단일 상수로 쓰면 높은 칸에서 임계를 **과대예측**한다.

정밀화된 임계 식:

```
    임계(B) = A(B) − s0_base − (A(B)/P) · c
```

> 정직하게: `c = 34.5` 는 그룹당 2점, 그것도 폭 ~56 B 이분탐색 구간의 **중점**에서 나왔다.
> 불확실성이 크다(±40 B 수준). 그러나 **두 그룹이 독립적으로 같은 값을 준 것**이 우연일 확률은 낮다.

### ✅ 직접 측정으로 확인 (2026-08-20, `_probe_s0.py`, `results/probe_s0_x25519.json`)

⚠️ **먼저 정정.** 1 바이트 절벽 실험(§2 아래)은 **이 두 모형을 구분하지 못한다.**
상수 s0 모형도 절벽 10점을 똑같이 맞힌다 — 절벽은 *양자화*의 증거지 *패킷항*의 증거가 아니다.
그리고 §8 이 계획했던 `p12c`(ips 1707·2134)는 **영구히 불가능**하다:
veth MTU 1500 + **quic-go 가 `InitialPacketSize` 를 1452 로 깎는다**.
x25519 는 칸 3·4, ML-KEM 은 칸 6·7 밖으로 못 나간다.

그래서 **임계를 거치지 않는 길**로 갔다. 클라이언트가 시행마다 기록하는 `server_bytes`
(= 서버에게서 받은 총 바이트)를 쓰면 `s0 = S − cert` 를 **직접** 얻는다. 인증서를
1,000~12,000 B 로 훑었다(x25519, RTT 50 ms, 손실 0, 조건당 n=12).

| cert | S(서버바이트) | n̂ | **s0 실측** | 상수 예측 | 패킷항 예측 |
|---|---|---|---|---|---|
| 1,000 | 1,561 | 2 | **561.0** | 500.0 | 465.5 |
| 3,000 | 3,602 | 3 | **602.0** | 500.0 | 500.0 |
| 6,000 | 6,724 | 6 | **724.0** | 500.0 | 603.5 |
| 9,000 | 9,805 | 8 | **805.0** | 500.0 | 672.5 |
| 12,000 | 12,886 | 11 | **886.0** | 500.0 | 776.0 |

**결과 — 상수 s0 모형은 기각된다.**

```
    패킷당 증분 실측       36.1 B/패킷    (임계역산이 준 34.5 와 5% 이내)
    평균절대오차           상수 224.5 B   vs   패킷항 112.4 B
    직접측정 재적합        s0(n) = 479.4 + 39.21 n   →  평균절대오차 14.1 B
    s0 단조 증가           n=2: 561 → n=11: 886  (검사 통과)
```

**교차 확인 — X25519MLKEM768** (같은 방법, cert 1,000~12,000, n=12)

```
    패킷당 증분 실측       40.0 B/패킷
    평균절대오차           상수 144.2 B   vs   패킷항 101.8 B
    s0 단조 증가           n=3: 1,710.5 → n=11: 2,030.5
    "같은 n 안에서 일정" 폭  7.0 / 4.0 / 1.0 B  ← x25519(34·44)보다 훨씬 깨끗
```

**두 그룹 · 두 독립 방법이 전부 같은 결론을 준다.**

| 방법 | x25519 | X25519MLKEM768 |
|---|---|---|
| 임계 역산 (§2.5 원판) | 34.5 | 34.5 |
| **서버 바이트 직접 계수** | **36.1** | **40.0** |
| 상수 모형 기각 여부 | 기각 (224.5 → 112.4) | 기각 (144.2 → 101.8) |

정직하게 남길 것:
- **절편은 비교하면 안 된다.** `server_bytes` 는 첫 비행 + **꼬리**(ACK·HANDSHAKE_DONE·
  NewSessionTicket)를 포함하므로 직접측정 절편(479.4)이 임계역산 절편(396.5)보다 ~83 B 높다.
  꼬리가 대략 상수라 **기울기만 비교 가능**하다.
- 검사 4개 중 1개 실패 — "같은 패킷 수 안에서 s0 일정"(n=3 폭 34.0, n=7 폭 44.0).
  원인은 `n̂ = ceil(S/1280)` 이 경계에서 한 칸씩 틀리기 때문으로 보인다(꼬리 바이트가 섞여
  S/1280 이 정수 경계를 살짝 넘는다). **서버 데이터그램 수를 직접 세면 해소될 것** — 미확인.
- 따라서 `c` 의 정본값은 아직 하나로 못 박지 못한다. **34.5 ~ 39.2 사이**로 적고,
  서버 데이터그램 수를 직접 세는 계측을 붙인 뒤 확정한다.

## 2.6. 모형은 FEC 팔에서 깨지지 않았다 — 세는 바이트가 틀렸다

v1 감사의 최대 약점은 `p4_model.json` 의 `threshold_hits = [4,8]` 이었다.
기준선 팔 4개는 맞고 **FEC 팔 4개는 전부 빗나간다**(+136 / +294 / +4032.5 / +7974.5 B).

§2.5 의 패킷항 `c = 34.5` 를 넣고 각 팔의 측정 임계를 설명하는 칸 `n` 을 역산하면
**8개 팔 전부**가 어떤 칸으로 설명된다. 오차는 전부 **이분탐색 한 칸(56 B) 이내**다.

| 그룹 | 팔 | 측정 임계 | 맞는 칸 n | 예측 임계 | 오차 | 필요 `B_eff` 구간 | 보고 `B` | |
|---|---|---|---|---|---|---|---|---|
| x25519 | off/buf | 3312~3368 | 3 | 3,340.0 | 0.0 | (853, 1280] | 1,280.0 | ✓ |
| x25519 | on1 | 8239~8296 | 7 | 8,322.0 | +54.5 | (2560, 2986.7] | 3,922.4 | ✗ **초과 936** |
| x25519 | on2 | 11977~12034 | 10 | 12,058.5 | +53.0 | (3840, 4266.7] | 6,562.9 | ✗ **초과 2,296** |
| MLKEM | off/buf | 5917~5974 | 6 | 5,945.5 | 0.0 | (2133, 2560] | 2,560.0 | ✓ |
| MLKEM | on1 | 10901~10958 | 10 | 10,927.5 | **−2.0** | (3840, 4266.7] | 4,154.9 | ✓ |
| MLKEM | on2 | 14583~14640 | 13 | 14,664.0 | +52.5 | (5120, 5546.7] | 5,396.9 | ✓ |

**MLKEM 의 FEC 팔은 보고된 바이트 그대로 맞는다**(on1 은 오차 2 B). 어긋나는 것은
**x25519 의 FEC 팔뿐**이고, 초과분이 대략 패리티 데이터그램 하나(m=1) / 둘(m=2) 몫이다.

이건 우리가 이미 증명한 **배치 의존성이 임계 데이터에서 숫자로 다시 나온 것**이다.

```
m=1 배치 = [원본…, 패리티]
k=1 (x25519) 이면 원본 하나로 서버가 즉시 응답 비행을 만들기 시작한다
  → 뒤따라오는 패리티는 **결정 시점 이후**에 도착 → 신용을 못 산다
k=2 (MLKEM) 이면 두 원본이 다 와야 복호가 끝나므로 패리티가 결정 전에 들어온다
```

따라서 모형의 인자는 "클라이언트가 보낸 총 바이트"가 아니라
**"서버가 응답 비행을 만들기로 결정한 시점까지 도착한 바이트" `B_eff`** 여야 한다.
v2 는 이걸 명시한다.

> 이 재해석은 사후적이므로 **반드시 직접 측정으로 확인해야 한다** — §8 의 `p13`.
> 확인 전까지는 "가설"로만 적는다.

## 3. 결정 규칙

```
    J(δ, m) = E[n_rtt | 복구 성공] · RTT
            + P(실패·PTO) · (RTT + T_pto)
            + P(실패·ACK) · (RTT + T_ack)
            + t_tx(추가 바이트)

    (δ*, m*) = argmin J
```

네 항 전부가 **하나의 결합 도착분포**에서 나온다.

```
    Pr[a, b]  = 원본 a 개 · 패리티 b 개가 도착할 확률   (Gilbert-Elliott, 배치 반영)
    복구 가능  ⟺  k − a ≤ b                            (MDS)
    신용 바이트 = a·W_eff + b·파(W_eff, k)              (도착한 것만)
```

`파(w,k) = w + 32 + 6k` 는 패리티 데이터그램의 **실제** 크기다(롱헤더 ~19 +
FEC 머리 13 + crc/len 목록 6k). 원본보다 크므로 후보 생성부터 이 값을 쓴다.

### ⚠️ 2026-08-20 감사에서 이 식을 고쳤다

고치기 전 식은 `E[n_rtt] · RTT + P_fail · T_recover` 였고, 결함이 둘 있었다.

**(1) 한 식에 손실 모형이 두 개였다.** `E[n_rtt]` 는 원본과 패리티를 각각
독립 이항으로 굴렸는데 `P_fail` 은 Gilbert-Elliott 을 썼다. 증거: k=2·m=1·p=0.05
에서 버스트를 1→5 로 바꾸면 `P_fail` 은 6.6 배가 되는데 `E[n_rtt]` 는 소수점
6 자리까지 꿈쩍도 안 했다. 손실이 뭉치면 "패리티까지 같이 잃어 신용을 못 사는"
사건이 독립 가정보다 훨씬 흔한데 그 항이 버스트를 못 봤다 — **항상 낙관 쪽**이었다.

**(2) 같은 손실 사건을 두 항에서 각각 청구했다.** 전멸하면 서버가 아무것도 못
받으므로 `A(0)=0` 이라 `n=2` 로 세어지고, **동시에** `P_fail` 로 `T_recover` 도
물었다. 물리적으로는 한 사건(전멸 → 재전송)이다. 실측: m=0·k=1·p=0.2·RTT 50 ms
에서 `60 ms(왕복항) + 10 ms(정지항) = 70 ms` 였다. 보정하면 **60 ms** 이고,
290 개 조건 중 **5 건(1.7%)에서 결정이 뒤집혔다** — 전부 필요 없는 1,318 B
패리티를 사고 있었다.

그래서 `n_rtt` 는 **복구 성공 상태에만** 매기고, 실패는 `(RTT + T_recover)`
한 번으로 값을 매긴다. `p = 0` 이면 실패 확률이 0 이라 예전 식과 **완전히 같다** —
§2 의 헤드라인(1 바이트 절벽)은 영향받지 않는다.

### 배치가 결과를 바꾼다

```
    m = 1  →  [원본…, 패리티]              뒤엣것이 복구용
    m ≥ 2  →  [패리티0, 원본…, 패리티1]    앞이 신용, 뒤가 복구
```

독립 손실 가정에서는 배치가 무의미했다. 버스트에서는 **인접한 것이 함께
사라지므로** 패리티를 어디에 두느냐가 도착 조합의 분포를 바꾼다.

후보 집합은 **연속 스윕이 아니라 경계점만** 본다. 이것이 v2 의 계산상 핵심이다.

```
후보 = { (0, 0) }                                  # 아무것도 안 함
     ∪ { (ceil(Δ_j/k), 0)  : j = 1..J }            # δ 로 j 칸 올라간다
     ∪ { (0, m)            : m = 1..m_max }        # 패리티만
     ∪ { (0, ceil(Δ_j/파)) : j = 1..J, Δ_j ≥ W }   # 패리티로 j 칸 올라간다

    Δ_j = (다음 j 번째 칸에 들어가는 최소 추가 바이트)
```

동점 처리: ① `J` 최소 → ② **실제** 추가 바이트 최소 → ③ 같은 바이트면 패리티
우선(보조정리 1) → ④ `late_parity_risk` 없는 쪽 → ⑤ `over_mtu` 없는 쪽.

> ②가 "실제"인 것도 위 감사의 수리다. 예전에는 패리티를 `W` 로 센 근사값으로
> 동점을 갈랐는데 점수 `J` 는 실크기로 계산됐다. 동점일 때 실제로 더 큰 후보를
> "더 작다"고 보고 골랐다(m=1 에서 38 B, m=2 에서 76 B 차이).

**보낼 수 없는 후보는 뺀다.** `W_eff > 1452` 는 후보에서 제외한다 —
2026-08-20 실측으로 **quic-go 가 `InitialPacketSize` 를 1452 로 깎는다**.
`pad_repack`(데이터그램을 합쳐 재패킹)도 기본 제외한다: 모형에는 있지만
우리 테스트베드가 CRYPTO 재분할을 하지 않는다. **구현 안 된 선택지를 고르면 안 된다.**

### ⚠️ `T_recover` — 두 번 고쳤다

**v1 → v2**: v1 은 원본 하나를 잃으면 PTO(RFC 9002 초기값 999 ms)를 문다고 봤다.
측정으로 틀렸음이 밝혀져 `rtt_ms` 로 바꿨다.

**2026-08-20**: 그 `rtt_ms` 도 틀렸다. **결정적 소거로 직접 재니 대가가 하나가 아니라
둘이었다.** 가르는 것은 k 가 아니라 **실패한 순간 서버가 하나라도 받았는가**다.

`experiments/_probe_trecover_rtt.py` (`-drop-initial 0` 으로 매 판마다 첫 비행을
버리고 기준선과의 p50 차를 잰다. 모든 표본이 손실 사건이라 잡음이 없다):

| RTT | k=1 (x25519) | k=2 (X25519MLKEM768) |
|---|---|---|
| 10 ms | **200.90 ms** (20.09×) | 12.62 ms (1.26×) |
| 50 ms | **200.96 ms** (4.02×) | 57.77 ms (1.16×) |
| 100 ms | **200.73 ms** (2.01×) | 113.88 ms (1.14×) |
| 판정 | **고정 상수** (폭 0.23 ms) | **RTT 비례** (배수 폭 0.10) |

```
    받은 게 0 개  ->  서버가 ACK 를 못 준다  ->  클라가 PTO 타이머를 문다
                     그 타이머는 RTT 표본이 없을 때의 값이라 경로와 무관하다
                     T_pto = 200.86 ms                    (quic-go v0.61.0 실측)

    1 개 이상     ->  서버가 ACK 를 준다 -> 패킷번호 구멍으로 즉시 재전송
                     T_ack = 1.125·RTT + 1.42 ms          (최소제곱, 잔차 |0.10| ms)
```

`k=1·m=0` 은 실패가 곧 전멸이라 **항상 PTO 가지**다. 그래서 겉보기엔 "k 에 따라
다르다"로 보였지만, 결합분포가 두 가지를 이미 구분해 주므로 **k 로 분기하지 않고
도착 개수로 나눈다**(`p_fail_pto` / `p_fail_ack`).

> v2 초판의 "서버가 ACK 를 주므로 대가는 왕복 하나다" 는 **ACK 가지에서만** 참이다.
> 코드 주석은 PTO 경로를 알고 있었는데 **기본값이 말없이 틀린 가지를 탔다.**

#### 이 수리가 실제로 바꾼 것

옛 기본값(`t_recover = RTT`)으로는 스윕 2,640 조건 중 **405 건(15.3%)**,
`k=1` 만 보면 1,320 중 **286 건(21.7%)** 에서 결정이 달라진다. 방향이 전부 같다 —
옛 기본값은 `none`(무방비)을 고르는데 새 기본값은 `parity` 를 고른다.
**손실 한 번이 201 ms 인 자리에서 정확히 과소보호하고 있었다.**

#### ✅ 실측 검증 (`results/probe_trecover_verify.json`)

x25519 · k=1 · cert 1,000 · RTT 10 ms · n=300(워밍업 20 제외):

| 손실 | 실측 `off` | 옛 예측 | 새 예측 | 실측 `m=1` | 실측 `m=2` |
|---|---|---|---|---|---|
| 2% | **14.656 ms** | 10.20 (−4.46) | **14.02 (−0.64)** | 12.170 | 12.134 |
| 5% | **22.459 ms** | 10.50 (−11.96) | **20.04 (−2.42)** | 12.128 | 12.139 |

- `off` 팔 예측 오차가 **7.0 배 · 4.9 배** 줄었다.
- **옛 기본값은 두 조건 모두에서 `off` 를 최적이라 골랐다** — 실측으로는 가장 나쁜 팔이다.
  새 기본값은 두 조건 모두 패리티를 고른다(맞다). `m=1` 과 `m=2` 의 실측 차는
  0.01~0.04 ms 로 구분 불가이므로 둘 사이는 판정하지 않는다.
- **꼬리에 증거가 그대로 보인다**: 손실 5% `off` 의 p95 가 **211.2 ms** 다. 201 ms PTO 다.

> ⚠️ 세 상수는 **quic-go v0.61.0 의 타이머**를 잰 값이다. 다른 스택에서는 다시 재야 한다.
> 상수를 쓰는 게 문제가 아니라 **출처 없는 상수를 쓰는 것**이 문제였다.

### ✅ Go 이식은 같은 표에서 읽는다

`experiments/quicbed/policy.go` 의 `flightOutcome` 이 같은 식을 쓴다. 결합분포는
**Go 에서 다시 계산하지 않는다** — `padfec/table.py` 가 검증된 Python 모형에서
표로 뽑아 심고 Go 는 조회만 한다(1 차에서 Cauchy 행렬을 양쪽에 각각 짰다가
갈라진 전례가 있다). 표는 `%.17g`(float64 왕복 정밀도)로 찍는다.

> 🩸 같은 감사가 여기서도 결함을 찾았다. `policy.go` 는 `pfailLookup(k, m, p, 1.0)`
> 으로 **버스트를 호출부에 리터럴로 박아** 뒀고 Python 은 실제 버스트를 썼다.
> 같은 입력에 두 구현이 다른 `m` 을 골랐다(90 조건 중 **17 건**). 지금은 버스트가
> 인자로 흐르고, `P_fail` 의 두 번째 출처(`pfailTable`)를 아예 지웠다 —
> 남겨 두면 누군가 다시 그걸 부른다. 2,688 격자점 대조에서 **불일치 0 건**.

|---|---|---|---|---|---|---|
| 1,000 | 0% | `none` | 1280 | 0 | 0 | — |
| 1,000 | 5% | `parity` | 1280 | 1 | 1,318 | 1.32 ms |

| 3,000 | 5% | `parity` | 1280 | 1 | 1,318 | 1.32 ms |
| **4,000** | **0%** | **`pad`** | **1281** | **0** | **1** | **50.00 ms** |
| 4,000 | 5% | `parity` | 1280 | 2 | 2,636 | 47.77 ms |
| 6,000 | 0% | `parity` | 1280 | 1 | 1,318 | 48.95 ms |

> 추가 B 는 **실제** 바이트다(패리티 = `W+32+6k` = 1,318). 2026-08-20 감사 전에는
> 이 자리에 패리티를 `W` 로 센 1,280 이 적혀 있었다 — 표가 코드의 근사값을
> 인용하고 있었다.

ML-KEM(C=1450, k=2) · cert 6,500 · 무손실 → `pad`, `W_eff=1281`, 추가 **2 B**(δ=1 × k=2), 50.00 ms.

읽는 법:
- **신용만 필요하면 δ 1 바이트.** cert 4,000 무손실에서 `pad`(J=50.001)가
  `parity m=1`(J=51.054)을 이긴다 — 같은 1-RTT 를 **1,318 배 싸게** 산다.
- **복구만 필요하면 패리티.** cert 3,000(임계 아래)·손실 5% 에서 신용은 쓸모없고 복구만 값을 한다.
- **둘 다 필요하면 패리티.** 보조정리 1 — 어차피 `Δ ≥ W` 를 쓸 거면 패딩 대신 패리티다.
- **1 바이트로 못 닿는 곳이 있다.** cert 6,000 은 칸 4(임계 4,585.5) 밖이라 δ 로는 못 넘고
  패리티의 1,318 B 가 필요하다. `ips` 상한 1452 때문에 δ 로 갈 수 있는 칸이 막혀 있다.

## 4. 무엇이 바뀌지 않는가

- **용량 정리는 그대로 살아 있다.** `C ≤ (k−1)(W−h−f)`. 이건 이제 v2 에서
  **δ 가 복구를 줄 수 없는 이유**를 설명하는 자리에 놓인다 — 키운 데이터그램
  안의 여분 바이트는 그 데이터그램이 통째로 사라질 때 같이 사라진다.
  `k=1` 이면 우변 0. 실측 12개 설정 전부 위반, 최근접 **76.0 B** 부족
  (`p1_flight.json` capacity_checks, ML-KEM/ips1450: C=1457, 용량 1381.0).
  `f=0` 으로 잡아도 **60.0 B** 부족 — **결론이 꼬리표 크기에 강건하다.**
  (⚠️ 정정: v1 문서와 이 명세 초판이 적은 '56 B' 는 틀렸다. 같은 행 h=53.0 으로 재계산하면 60.0 B 다.)
- **배치 규칙 그대로.** `m=1` → `[원본…, 패리티]`(복구), `m≥2` →
  `[패리티0, 원본…, 패리티1]`(앞이 신용, 뒤가 복구). 근거는 quic-go
  `connection.go:669` 의 `if !wasProcessed { continue }`.
- **회계 불변식 그대로.** `스택에 넘긴 누적 ≤ 물리적으로 받은 누적`.
- **타이밍 조건 그대로.** 추가 바이트는 **서버가 응답 비행을 만들기 전에**
  도착해야 한다(e21: dup1 은 정지 2.3 ms 뒤 도착 → 임계 못 옮김).
  δ 는 같은 데이터그램을 키우는 것이라 이 조건을 **구조적으로** 만족한다 —
  패리티보다 안전하다.

### 규격 위반 사실

quic-go `isAmplificationLimited()` 는 `bytesSent >= 3*bytesReceived` **불리언
게이트**다 — 패킷을 만들기 **전에만** 본다. RFC 9000 §8.1 은 예외 문구 없는
`MUST NOT send more than three times` 이므로, 이 양자화는 곧 **규격 위반**이다.
v2 는 이 사실을 명시한다. 우리 설계가 그 위반에 기대고 있다는 점도 함께 적는다.

## 6. 선행연구 — v2 가 서 있는 자리

- **아이디어는 이미 규범에 있다.** RFC 9002 §A.6 의사코드 주석:
  *"Initial is padded to **earn more anti-amplification credit**"*.
  RFC 9000 §8.1 도 교착 방지로 클라가 ≥1200 B 를 보내라고 MUST 로 요구한다.
  → "클라가 바이트로 예산을 산다"는 **우리 기여가 아니다.**
- **Fastly(McManus)** 가 이미 적었다 — *"certificate chain budget between
  3333 and 4356 bytes depending on the initial client packet size"*,
  *"extra 200 bytes of padding will halve the handshake time for 7% of connections"*.
  → 우리 기여는 그 **200 바이트가 왜 200 이고 언제 1 바이트로 충분한지**를
  닫힌 식으로 설명하는 것이다.
- **Nawrocki (CoNEXT 2022)** 기여 (3) = *"Analysis of QUIC server behaviors for
  different sizes of client Initial messages"* + §5 *"Dealing efficiently with
  loss of messages during the connection setup seems an open challenge."*
  → 우리 문제는 **이미 등록된 미해결 과제**다. 인용하면 기여가 강해진다.
- **용량 부등식은 Singleton/MDS 한계의 QUIC 상수 대입이다.** "정리"로
  내세우면 한 줄로 반박당한다. **부정 결론(60~76 B 부족)과 그 강건성**으로 쓴다.
- 누락 보충 필요 9건: QUIRL(ToN 2024), Nawrocki(CoNEXT 2022),
  ReACKed QUICer(2024), Banks 5x 제안(2024-07), `draft-ietf-tls-cert-abridge`,
  Huawei FEC 드래프트 2건, RFC 9000 §8.1 교착 문단, RFC 9002 §A.6.

## 7. 주장 서열 (신규성 순)

1. **양자 경계 절벽** — `Δ_min = 1` 따름정리와 그 실측. 기본값이 최악점에
   걸터앉는다는 사실. **새로 만든 것, v2 의 헤드라인.**
2. **신용/복구 배치 의존성** — 하나의 패리티로 둘을 동시에 못 얻는다.
   충돌 선행 못 찾음. 단 근거가 quic-go 단일 경로 → 다른 스택 재현 필요.
3. **증폭 임계 양자화 모형** — 아이디어는 규범에 있으나 **게이트 대 바이트상한
   구분**과 닫힌형 `ceil(3B/P)·P` 는 못 찾음.
4. **용량 부등식** — Singleton 따름정리. 부정 결론으로만 쓴다.
5. **폐루프 후회** — 적응형 FEC 비용최적화 계보가 두껍다(Bolot 1999, Park AFEC).
   지표 자체는 기여 아님.

## 8. 검증 계획

| 단계 | 무엇 | 통과 기준 |
|---|---|---|
| `p12` | **양자 경계 절벽** — `ips` 를 1279/1280/**1281**/1282/1350 으로 훑어 임계 이분탐색 | 1280→1281 사이에서 임계가 한 칸(≈1,246 B) 뛴다. **1281 과 1350·1450 이 같은 칸** |
| `p12b` | 같은 실험을 ML-KEM(k=2)에서 `ips` 1280/**1281** | 2560→2562 에서 한 칸. 1281 과 1350 이 같은 칸 |
| `p12c` | **s0 패킷항 확인** — x25519 `ips` **1707**·**2134** (칸 5·6) | 임계 5,831 / 7,076.5 (±60). 단일 s0 모형은 5,865.5 / 7,145.5 로 과대예측 → 두 모형이 갈린다 |
| `p13` | **`B_eff` 직접 측정** — 서버 앞 바이트 타임라인에서 "서버 첫 송신 시각까지 도착한 클라 바이트"를 센다(e21 방식). x25519 on1/on2 와 MLKEM on1/on2 | x25519 on1 의 `B_eff` 가 (2560, 2986.7] 안에 든다. 늦게 온 패리티 바이트 = §2.6 의 초과분(936 / 2296 B) |
| `p14` | **지배 보조정리** — 같은 Δ 에서 δ-패딩 팔 vs 패리티 팔 | 신용 동일(임계 같음), 손실에서 패리티만 꼬리 제거 |
| `p15` | **v2 정책 후회** — δ·m 결합 정책 vs 최선 고정 조합 | 수렴 후 최악 후회 < 2 ms |

부정 시험(반드시 포함):
- `ips=1280` 과 `ips=1279` 는 **같은 칸**이어야 한다(경계를 안 넘으므로).
- δ 를 준 팔은 손실에서 **복구가 0** 이어야 한다(패딩은 복구를 못 준다).
- 패리티를 없애면 기준선으로 복귀.
