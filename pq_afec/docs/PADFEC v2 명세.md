# PAD-FEC v2 명세

> 양자 인식 첫 비행 설계. v1(고정 m 패리티)에서 v2(δ·m 두 지렛대)로 바꾼다. 2026-08-20.
> 이 문서가 구현·실험·검증의 정본이다. 숫자는 전부 `experiments/results/*.json`에서 왔다.

> 해석 정정 (2026-09-14): `A(B)=ceil(3B/P)·P`는 quic-go v0.61.0 테스트베드의 송신 동작을 설명하는 모형이다. RFC 9000의 규범적 한도는 `3B`이며, 패킷 단위 올림을 허용한다는 뜻이 아니다. `δ=1`은 데이터그램당 증가량으로, k개 비행의 총 추가량은 k B다. 제자리 보호의 불가능성은 고정한 k·W·h·f와 측정 설정에 한정한다. 아래 날짜별 실측값은 그 실행의 과거 기록이다.

근거: [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1), 패딩으로 증폭 신용을 확보하는 의사코드는 [RFC 9002 §A.9](https://www.rfc-editor.org/rfc/rfc9002.html#appendix-A.9)에 있다.

## 0. 다시 설계하는 이유

v1은 결정 변수가 패리티 데이터그램 개수(m) 하나였다. 그런데 실측에서 두 가지가 드러났다.

1. 증폭 신용은 바이트 수에만 의존하고 내용과는 무관하다. p2 `ips_sweep`와 e20/e21 `dup` 팔에서는 내용이 글자 그대로 같은 복제 데이터그램도 임계를 옮겼다.
2. 허용량은 연속값이 아니고 1,280 B 단위의 계단이다. `허용 = ceil(3B/1280)·1280`.

둘을 합치면 v1이 보지 못한 지렛대가 생긴다. 신용만 사고 싶다면 데이터그램을 하나 더 보낼 필요 없이 기존 데이터그램을 몇 바이트 키우면 된다. 허용량이 계단이므로 경계 근처에서는 그 몇 바이트가 1바이트다.

## 1. 기호

| | |
|---|---|
| `C` | ClientHello CRYPTO 총 바이트 (TLS 설정이 정함, 우리가 못 바꿈) |
| `W` | 데이터그램 하나의 와이어 크기 = `InitialPacketSize` (≥1200, 우리가 정함) |
| `h` | 패킷당 고정비 (롱헤더+AEAD 태그+CRYPTO 머리). 실측 47~51 |
| `f` | FEC 꼬리표 |
| `k` | 첫 비행 데이터그램 수 = `ceil(C/(W−h))` |
| `B` | 첫 비행 총 바이트 = `k·W`. 실측으로 확인됨(p1 12/12) |
| `P` | 서버 패킷 크기. quic-go 1280 |
| `A(B)` | 주소 검증 전 서버 허용량 = `ceil(3B/P)·P` |
| `S` | 서버 첫 비행 = `cert + s0` |
| `s0` | 인증서를 뺀 서버 첫 비행 (SH+EE+CV+Fin+오버헤드) |

`n_rtt = 1 if S ≤ A(B) else 2`.

## 2. 두 지렛대

| 지렛대 | 무엇 | 신용 | 복구 | 바이트 값 |
|---|---|---|---|---|
| δ | 데이터그램을 키운다 `W → W+δ` | `+3kδ` | 없음 | `kδ` |
| m | 패리티 데이터그램 `m`개 추가 | `+3mW` | 1-소거 복구(m=1) | `mW` |

### 보조정리 1 (지배)의 반증

2026-08-21에 반증됐다. 원래는 이렇게 적혀 있었다.

> 같은 추가 바이트 `Δ`에서, `Δ ≥ W`이면 패리티가 패딩을 엄격히 지배한다.
> 증명. 신용은 바이트 수에만 의존하므로 두 방식의 신용이 같다(`3Δ`).
> 패리티는 추가로 1-소거 복구를 준다. 복구 확률은 단조 증가이므로
> 어떤 손실률에서도 손해가 아니다. ∎

증명의 첫 문장이 틀렸다. §2.6에서 밝혔듯이 신용은 "보낸 바이트"가 아니라 서버 QUIC 스택이 실제로 센 바이트로 생긴다. 두 지렛대는 이 바이트의 도착 상관이 서로 다르다.

| | 여분 바이트가 실린 곳 | 원본이 도착했을 때 신용도 오는가 | 복구했을 때 |
|---|---|---|---|
| δ | 데이터 데이터그램 안 | 반드시 온다 (원자적) | 해당 없음 |
| m | 별도 데이터그램 | 따로 유실될 수 있다 | 패리티를 버리고 복구본(더 작다)을 넘기므로 신용이 줄어든다 |

그래서 `k=1·m=1`에서 2-RTT로 떨어지는 경우는 두 가지다.

```
    (1) 패리티가 유실된다                    확률 p
    (2) 원본이 유실되고 패리티로 복구된다      확률 p     <- 옛 모형이 놓친 쪽
    합계 ≈ 2p
```

#### 실측 (2026-08-21, `p14_dominance.py`, cert 4,032 · RTT 50 ms · 손실 5%)

| 팔 | 평균 HCT | 2-RTT | PTO 꼬리 | 서버 복구 |
|---|---|---|---|---|
| 맨몸 | 120.39 ms | 88.8% | 11.2% | 0 |
| `pad` δ=1 | 66.12 ms | 0.0% | 7.2% | 0 |
| `parity` m=1 | 56.87 ms | 10.5% | 0.0% | 43 |
| `combo` δ=1·m=1 | 52.05 ms | 0.0% | 0.2% | 37 |

정정 모형은 `parity`의 2-RTT를 9.5%로 예측한다(실측 10.5%). 옛 회계로는 5.0%였다. `pad`는 복구가 없어서 PTO 꼬리(7.2%)를 문다.

#### 정정된 보조정리 1

> 같은 추가 바이트 `Δ`에서 패리티가 패딩을 지배하려면, 데이터그램 하나가 혼자 사들이는 신용의 바닥(`W_eff`)이 낮아지지 않아야 한다. 패리티는 `W_eff`를 올리지 않으므로 이 조건을 만족하지 못한다. 따라서 두 지렛대 사이에는 지배 관계가 성립하지 않는다.
>
> 판정식(`padfec/quantum.py dominates`)에 `W_eff ≥` 축을 더하자, 도달 가능한 후보집합에서 지배 간선이 0/460이었다. 그래서 `dominates()`는 더 이상 가지치기 규칙으로 쓰지 않는다. 후보가 5~6개뿐이라 어차피 전수 평가해도 싸다.

교차점도 물리적으로 설명된다. `pad`의 대가는 `p·(RTT + T_pto)`(전멸)이고 `parity`의 대가는 `p·RTT`(신용 상실)이므로, `RTT > T_pto`(≈201 ms)이면 pad가 더 싸다. 모형도 이를 그대로 재현한다. 같은 Δ 쌍에서 `J(parity) − J(pad)`는 RTT 50/100/250 ms에서 각각 −7.17 / −4.79 / +2.33 ms다.

#### 따름정리 (결합 후보)

2026-08-21에 새로 넣었다. 두 지렛대는 서로 배타적인 대안이 아니다. 지배 관계가 없으니 후보 집합을 `{(δ,0)} ∪ {(0,m)}`로 제한할 근거도 없다. 그래서 결합 후보 `(δ>0, m>0)`를 넣는다. `δ`는 살아남은 모든 데이터그램의 신용 바닥을 올려 부분 손실에서도 칸을 지키고, `m`은 복구를 준다. 둘을 함께 쓰면 각자의 약점이 동시에 사라진다.

- 후보는 경계점만 본다(§3 원칙 유지). 각 도착 상태 `(a,b)`를 목표 칸으로 올리는 최소 `δ`들이다. 후보 수는 평균 5.00 → 5.50으로만 는다.
- 경계점 후보만으로 충분하다. `δ∈[0,172]×m∈{0,1,2}` 완전탐색과 오차 0.000000 ms로 같다(`padfec/quantum.py` 자체시험 13).
- 격자 880점 중 112점(12.7%)이 개선된다. 최대 개선폭은 RTT 50 ms에서 14.2 ms, RTT 250 ms에서 72.5 ms다. 실측에서는 위 표의 `combo`가 가장 나은 단일 지렛대(`parity`)보다 4.8 ms 빠르다.

`Δ < W`이면 패리티 데이터그램을 만들 수 없다(Initial 데이터그램은 ≥1200이어야 하고, 그 크기면 이미 데이터그램 하나다). 이때는 δ가 유일한 수단이고 비용도 매우 작다. 옛 보조정리의 이 문장은 그대로 유효하다.

> 이 테스트베드에서는 옛 보조정리의 전제("같은 Δ")에 도달할 수 없다. `QUICGO_MAX_IPS = 1452` 때문에 `k=1`에서 pad로 낼 수 있는 최대 Δ는 172 B이고 패리티의 최소 Δ는 1,325 B라서 둘이 만나지 않는다. p14 검사 7이 이 값을 출력한다.

### 보조정리 2 (경계까지의 최소 바이트)

현재 허용량이 `A(B)`일 때 다음 칸으로 올라가는 최소 추가 바이트는 다음과 같다.

```
    Δ_min = floor(A(B)/3 − B) + 1
```

> 증명. 다음 칸에 들어가려면 `3(B+Δ) > A(B)`여야 한다. 바이트 수는 정수이므로 위 식이 된다. ∎

### 따름정리 (기본값이 최악이다)

quic-go 기본값 `W = 1280 = P`이면 `B = k·1280`이고 `3B = 3k·1280`은 항상 `P`의 배수다. 그러므로 `A(B) = 3B`이고

```
    Δ_min = floor(3B/3 − B) + 1 = 1
```

k와 관계없이 항상 1바이트다. quic-go 클라이언트는 기본 설정에서 증폭 양자 경계에 정확히 걸터앉아 있고, 1바이트만 더 보내면 서버 예산이 `P = 1,280 B` 늘어난다. 이것이 가능한 최대 낭비다.

> 앞선 x25519 실행에서는 `ips=1281`만 2-RTT 비율이 0.025였는데, 이번 실행에서는 그 자리가 `ips=1282`로 옮겨 갔다. 40회 중 1회 나오는 잡음이고, 경계에서 생긴 인공물은 아니다. 열려 있던 질문은 이것으로 해소됐다.

> 실측 대조. `ips_sweep`에서 1200과 1280은 임계 [3312, 3368]로 같고, 1350과 1450은 [4557, 4614]로 같다. 계단 하나는 1,245.5 B ≈ P다.
> `Δ_min(B=1200) = floor(3840/3 − 1200)+1 = 81`이므로 경계는 `W=1281`이다.
> `Δ_min(B=1280) = 1`이므로 경계는 역시 `W=1281`이다. 두 계산이 같은 점을 가리킨다.

## 2.5. s0의 서버 패킷 수 항

v2에서 새로 잡은 항이다. 감사에서 "s0 가 그룹 안에서 34.5 B 씩 갈린다"가 불일치로 보고됐다. 실제로는 불일치가 아니었고, 상수로 둔 모형에서 서버 패킷 수 항이 빠져 있었다.

| 그룹 | A | 서버 패킷 수 `n = A/P` | s0 실측 |
|---|---|---|---|
| x25519 | 3,840 | 3 | 500.0 |
| x25519 | 5,120 | 4 | 534.5 |
| X25519MLKEM768 | 7,680 | 6 | 1,734.5 |
| X25519MLKEM768 | 8,960 | 7 | 1,769.0 |

두 그룹 모두 패킷당 증분이 정확히 같다.

```
    s0(n) = s0_base + n · c ,     c = 34.5 B
    s0_base:  x25519 396.5 ,  X25519MLKEM768 1527.5
    차이 1,131 B ≈ ML-KEM-768 암호문 1,088 B + 43 B
```

서버 첫 비행은 인증서 + 고정분 + (패킷 수 × 패킷 오버헤드)다. 칸이 올라가면 서버가 패킷을 하나 더 쓰므로 s0도 그만큼 커진다. `s0`를 단일 상수로 쓰면 높은 칸에서 임계를 과대예측한다.

이를 반영한 임계 식은 다음과 같다.

```
    임계(B) = A(B) − s0_base − (A(B)/P) · c
```

> 한계: `c = 34.5`는 그룹당 2점에서 나왔고, 그 점도 폭 ~56 B 이분탐색 구간의 중점이다. 불확실성이 크다(±40 B 수준). 다만 두 그룹이 독립적으로 같은 값을 냈으니 우연일 확률은 낮다.

### 직접 측정으로 확인 (2026-08-20, `_probe_s0.py`, `results/probe_s0_x25519.json`)

먼저 정정할 것이 있다. 1바이트 절벽 실험(§2 아래)으로는 이 두 모형을 구분할 수 없다. 상수 s0 모형도 절벽 10점을 똑같이 맞힌다. 절벽은 양자화의 증거일 뿐 패킷항의 증거는 아니다. 또 §8에서 계획했던 `p12c`(ips 1707·2134)는 영영 할 수 없다. veth MTU가 1500이고, quic-go가 `InitialPacketSize`를 1452로 깎기 때문이다. x25519는 칸 3·4, ML-KEM은 칸 6·7 밖으로 나갈 수 없다.

그래서 임계를 거치지 않는 방법을 썼다. 클라이언트가 시행마다 기록하는 `server_bytes`(서버에게서 받은 총 바이트)를 쓰면 `s0 = S − cert`를 직접 얻는다. 인증서를 1,000~12,000 B로 훑었다(x25519, RTT 50 ms, 손실 0, 조건당 n=12).

| cert | S(서버바이트) | n̂ | s0 실측 | 상수 예측 | 패킷항 예측 |
|---|---|---|---|---|---|
| 1,000 | 1,561 | 2 | 561.0 | 500.0 | 465.5 |
| 3,000 | 3,602 | 3 | 602.0 | 500.0 | 500.0 |
| 6,000 | 6,724 | 6 | 724.0 | 500.0 | 603.5 |
| 9,000 | 9,805 | 8 | 805.0 | 500.0 | 672.5 |
| 12,000 | 12,886 | 11 | 886.0 | 500.0 | 776.0 |

이 결과로 상수 s0 모형은 기각된다.

```
    패킷당 증분 실측       36.1 B/패킷    (임계역산이 준 34.5 와 5% 이내)
    평균절대오차           상수 224.5 B   vs   패킷항 112.4 B
    직접측정 재적합        s0(n) = 479.4 + 39.21 n   →  평균절대오차 14.1 B
    s0 단조 증가           n=2: 561 → n=11: 886  (검사 통과)
```

X25519MLKEM768에서도 같은 방법으로 교차 확인했다(cert 1,000~12,000, n=12).

```
    패킷당 증분 실측       40.0 B/패킷
    평균절대오차           상수 144.2 B   vs   패킷항 101.8 B
    s0 단조 증가           n=3: 1,710.5 → n=11: 2,030.5
    "같은 n 안에서 일정" 폭  7.0 / 4.0 / 1.0 B  ← x25519(34·44)보다 훨씬 깨끗
```

두 그룹, 두 독립 방법이 모두 같은 결론을 낸다.

| 방법 | x25519 | X25519MLKEM768 |
|---|---|---|
| 임계 역산 (§2.5 원판) | 34.5 | 34.5 |
| 서버 바이트 직접 계수 | 36.1 | 40.0 |
| 상수 모형 기각 여부 | 기각 (224.5 → 112.4) | 기각 (144.2 → 101.8) |

절편은 비교할 수 없다. `server_bytes`는 첫 비행에 꼬리(ACK·HANDSHAKE_DONE·NewSessionTicket)까지 포함하므로 직접측정 절편(479.4)이 임계역산 절편(396.5)보다 ~83 B 높다. 꼬리가 대략 상수라서 비교할 수 있는 것은 기울기뿐이다.

### c 확정 (2026-08-20, `results/p13_beff.json`)

p13은 서버 첫 비행 데이터그램을 직접 셌다. 서버 송신(WriteTo)을 연결별로 가로채고, 첫 비행을 시각으로 잘라(버스트는 첫 송신 후 1 ms 안, 꼬리는 RTT 뒤) 데이터그램 수 n을 센 다음 s0(n) = (비행 바이트 − cert)를 회귀했다. 꼬리 오염도 없고 n̂ = ceil(S/P) 추정 오류도 없다.

```
    c 직접 계수     x25519 40.89 B/패킷 (MAE 7.4, n = 2..10)
                   ML-KEM 39.65 B/패킷 (MAE 0.4, n = 3..6)
    -> 정본 c = 40.0.  임계 앵커(x25519 s0(3)=500, ML-KEM s0(6)=1734.5)와 합치면
       s0_base = 380.0 / 1494.5
```

정정: 위 원판 표의 `c = 34.5`와 `s0_base 396.5/1527.5`는 그룹당 2점짜리 임계 역산(±40 B)이라 작게 나왔다. 앵커 자체(500.0 / 1734.5)는 그대로 유효하다. c만 바뀌므로 기준선 임계 예측(3340.0 / 5945.5)은 변하지 않고, 다른 칸으로 외삽한 값만 달라진다.

직접 계수에서도 "같은 패킷 수 안에서 s0 일정"은 성립하지 않았다(x25519 폭 39·41.5 B). n̂ 추정 오류가 아니라 실제로 있는 구조다. 같은 측정이 원인 메커니즘도 보여 줬다. 게이트는 패킷을 만들기 전에만 예산을 보므로, 마지막 작은 패킷은 예산을 넘기고도 통과할 수 있다. cert 3312에서는 서버가 3,931 B(> A = 3,840)를 보내고도 1-RTT였다. 마지막 95 B 패킷이 sent 3,836 < 3,840인 시점에 게이트를 통과했기 때문이다. cert 3330에서는 세 번째 패킷이 꽉 차서(3×1,280 = 3,840) 게이트가 닫혔고 2-RTT가 됐다. 임계 근처의 유효 폭은 서버 비행의 마지막 패킷 조성에 따라 ~100 B 흔들린다. s0(n) 선형 모형은 그 평균 구조이고, 앵커를 임계에서 맞추는 한 임계 예측에는 충분하다.

### 새 예측 (c=40으로 갱신)

기존 데이터 밖을 예측하는 것이 p12의 두 번째 목적이다.

| 그룹 | 칸 n | 필요 `ips` | 예측 임계 (c=40) | (구판 c=34.5) |
|---|---|---|---|---|
| x25519 | 4 | 1281 | 4,580.0 | 4,585.5 |
| x25519 | 5 | 1707 | 5,820.0 | 5,831.0 |
| x25519 | 6 | 2134 | 7,060.0 | 7,076.5 |
| X25519MLKEM768 | 7 | 1281 | 7,185.5 | 7,191.0 |

`ips` 1281·1707·2134를 재면, 표본이 한 칸짜리라는 감사 지적(회귀 기울기 x25519 5.90)도 함께 해소된다. 세 칸에 걸치면 한계 기울기 3을 제대로 추정할 수 있다.

### `s0_base`·`c`의 성격 (2026-08-21 정정)

이 둘은 물리 바이트가 아니라 유효 파라미터다. 위의 두 측정은 서로 100 B 어긋나 보였다.

```
    p13 직접 계수 : cert 3,000 · x25519 에서 서버 첫 비행 3,604 B  →  s0 = 604
    임계 역산     : 같은 칸(n=3)에서 s0 = 3,840 − 3,340 = 500
```

어느 쪽이 틀렸는지 가리려고 임계 근처에서 인증서를 훑으며 서버 송신 타임라인의 패킷 크기를 직접 봤다.

| cert | 첫 비행 패킷 | 합 | 허용량 `A(1280)` | 판정 |
|---|---|---|---|---|
| 3,250 | `[1280, 1280, 1209, 95]` | 3,864 | 3,840 | 1-RTT (+24 B 초과) |
| 3,300 | `[1280, 1280, 1257, 95]` | 3,912 | 3,840 | 1-RTT (+72 B 초과) |
| 3,340 | `[1280, 1280, 1280]` | 3,840 | 3,840 | 2-RTT |

둘 다 옳았고, 서로 다른 양을 재고 있었다. quic-go는 패킷을 만들기 전에 `bytesSent ≥ 3·bytesReceived`를 보므로 마지막 패킷이 작으면 한도를 넘겨서 보낸다. 정확한 규칙은 다음과 같다.

```
    1-RTT  ⟺  S − (마지막 패킷 크기) < 3B          (모형은 S ≤ A(B) 로 근사)
```

마지막 패킷 크기는 cert에 따라 95~1,280 B로 변한다. 유효 모형은 `s0`를 ~100 B 작게 잡는 방식으로 이 여유분을 흡수한다.

> 그래서 `s0_base`·`c`에는 물리 측정값을 그대로 넣지 않는다. 넣으면 임계를 100 B 낮게 예측하고, 정책이 필요 없는 바이트를 산다.

#### 앵커 여섯 개로 값 갱신

이전에는 그룹당 앵커 하나(x25519 n=3, ML-KEM n=6)로 절편을 잡았다. 그 점에서는 정확히 맞지만 다른 칸에서는 어긋난다. p4의 x25519 `on1` 예측은 8,300.0으로, 실측 밴드 8,239~8,296을 4 B 벗어났다(7/8).

앵커 6개(그룹 × 팔)에 공통 `c`와 그룹별 절편으로 최소제곱 적합을 했다.

    s0_base :  x25519 382.45 ,  X25519MLKEM768 1472.00
```

이렇게 얻은 `c = 41.98`은 p13이 서버 패킷을 직접 세어 얻은 `c = 40.55`(x25519) / `41.39`(ML-KEM)와 1.5 B/패킷 안에서 맞는다. 임계 이분탐색과 패킷 계수라는 전혀 다른 두 관측이 같은 기울기를 주므로, 아핀 형태 `S(n) = s0_base + n·c` 자체가 옳다는 근거가 된다.

## 2.6. FEC 팔 임계 불일치의 원인

모형은 FEC 팔에서 깨지지 않았다. 틀린 것은 세는 바이트였다. v1 감사의 가장 큰 약점은 `p4_model.json`의 `threshold_hits = [4,8]`이었다. 기준선 팔 4개는 맞고 FEC 팔 4개는 모두 빗나간다(+136 / +294 / +4032.5 / +7974.5 B).

§2.5의 패킷항 `c = 34.5`를 넣고 각 팔의 측정 임계를 설명하는 칸 `n`을 역산하면, 8개 팔이 모두 어떤 칸으로 설명된다. 오차는 모두 이분탐색 한 칸(56 B) 이내다.

| 그룹 | 팔 | 측정 임계 | 맞는 칸 n | 예측 임계 | 오차 | 필요 `B_eff` 구간 | 보고 `B` | |
|---|---|---|---|---|---|---|---|---|
| x25519 | off/buf | 3312~3368 | 3 | 3,340.0 | 0.0 | (853, 1280] | 1,280.0 | 통과 |
| x25519 | on1 | 8239~8296 | 7 | 8,322.0 | +54.5 | (2560, 2986.7] | 3,922.4 | 실패, 초과 936 |
| x25519 | on2 | 11977~12034 | 10 | 12,058.5 | +53.0 | (3840, 4266.7] | 6,562.9 | 실패, 초과 2,296 |
| MLKEM | off/buf | 5917~5974 | 6 | 5,945.5 | 0.0 | (2133, 2560] | 2,560.0 | 통과 |
| MLKEM | on1 | 10901~10958 | 10 | 10,927.5 | −2.0 | (3840, 4266.7] | 4,154.9 | 통과 |
| MLKEM | on2 | 14583~14640 | 13 | 14,664.0 | +52.5 | (5120, 5546.7] | 5,396.9 | 통과 |

MLKEM의 FEC 팔은 보고된 바이트 그대로 맞는다(on1은 오차 2 B). 어긋나는 것은 x25519의 FEC 팔뿐이고, 초과분은 대략 패리티 데이터그램 하나(m=1) / 둘(m=2) 몫이다.

이것은 우리가 이미 증명한 배치 의존성이 임계 데이터에서 숫자로 다시 나온 것이다.

```
m=1 배치 = [원본…, 패리티]
k=1 (x25519) 이면 원본 하나로 서버가 즉시 응답 비행을 만들기 시작한다
  → 뒤따라오는 패리티는 **결정 시점 이후**에 도착 → 신용을 못 산다
k=2 (MLKEM) 이면 두 원본이 다 와야 복호가 끝나므로 패리티가 결정 전에 들어온다
```

따라서 모형의 인자는 "클라이언트가 보낸 총 바이트"가 아니라 "서버가 응답 비행을 만들기로 결정한 시점까지 도착한 바이트" `B_eff`여야 한다. v2는 이를 명시한다.

### p13 직접 측정 (2026-08-20, `results/p13_beff.json`)

결과는 가설 기각이었고, 원인은 회계에 있었다. 서버 송신을 연결별로 가로채, 첫 데이터그램을 내보내기 직전의 수신 누적(원본/패리티 분리)을 스냅숏으로 쟀다. 조건당 n=24이고, 모든 시행을 계측했다.

| 그룹 | 팔 | B_eff 실측 | 원본 몫 | 패리티 몫 | 필요 구간 | |
|---|---|---|---|---|---|---|
| x25519 | on1 | 2,603.5 | 1,280 | 1,323.5 | (2560, 2986.7] | 통과 |
| x25519 | on2 | 3,930.0 | 1,280 | 2,650.0 | (3840, 4266.7] | 통과 |
| MLKEM | on1 | 3,892.0 | 2,560 | 1,332.0 | (3840, 4266.7] | 통과 |
| MLKEM | on2 | 5,224.0 | 2,560 | 2,664.0 | (5120, 5546.7] | 통과 |
| off 팔 (음성 대조) | | k·1,280 정확히 | 전부 | 0 | | 통과 |

- 위의 배치 가설(late-parity)은 기각됐다. k=1·m=1을 포함한 모든 조건에서 첫 비행 패리티는 100% 서버 결정 전에 도착해 신용을 산다. 코드에서 `late_parity_risk`는 항상 False가 됐다.
- 정밀도 정정(2026-08-21). 위의 "100%"는 조건당 n=24의 점추정이다. 24/24의 95% 하한은 0.883이다. 참 신용률이 88%(늦은 패리티 12%)여도 이 자료와 모순되지 않으므로, 이 기각으로는 1% 미만 규모의 현상을 배제하지 못한다. 또 p14 무손실에서 parity 팔만 2-RTT를 0.50%(2/400) 냈다(pad·combo 0/400, 모형 예측 0, 관측 1회, 재현 확인 중). 그래서 p13 검사 5를 전용 표본 600 + Clopper-Pearson 하한 ≥ 0.99로 바꿨다. `late_parity_risk = False`는 이 검사가 통과하는 동안만 유효하고, 검사가 실패하면 필드를 되살려야 한다.
- p4 임계 4/8의 원인은 p2의 회계였다. 클라이언트는 ACK 비행에도 패리티를 붙이는데, p2의 `client_bytes_total`이 연결 전체의 패리티(on1인데 ~2,642 B = 1,318 x 2)를 합산했다. 뒤 비행의 패리티는 서버의 첫 응답보다 한 왕복 늦게 오므로 예산과 관계가 없다. "반영률 64.6%"로 보였던 것은 늦은 패리티 때문이 아니라, 처음부터 세지 말았어야 할 바이트가 분모에 들어 있었기 때문이다.
- 확정된 회계는 B_eff = 첫 비행 원본 + 첫 비행 패리티 전부다(m≥2이면 신용 패리티와 복구 패리티 모두). 모형(`client_bytes_of`)은 처음부터 첫 비행만 세고 있었으므로, 모형은 옳았고 측정 쪽 합산이 틀렸다. p2는 첫 비행 몫만 세도록 고쳤다.

> 2026-08-21 전체 재실행 당시 값. 위 표와 아래 §8의 `threshold_hits = [4,8]`은 v1 감사 당시의 기록이다. 08-21에는 다음과 같았다. 지금 값은 README의 「지금 값」과 `results/*.json`이 정본이다(2026-09-07 기준 p13 14/14 · p14 12/12 · p16 6/6 · 관문 196,020점).
>
> ```
>     p4  임계 적중 7/8 · HCT MAE 3.65 ms · 정책 일치 5/12
>     빗나간 팔은 ML-KEM on1 하나이고 폭은 3.4 B (임계 10,900 B 의 0.03%)
>     — p4 는 기준선(off) 팔에서만 앵커를 잡고 FEC 팔은 **예측**한다(out-of-sample).

### 실패 가지(PTO vs ACK) 조건 정정 (2026-08-23)

비용식 J의 실패 항은 두 가지로 갈린다. 서버가 ACK를 낼 수 있으면 한 왕복(T_ack), 못 내면 PTO(경로와 무관한 상수, ~200 ms)다. 이 갈림 조건이 틀려 있었다.

    옛: 원본 또는 패리티가 하나라도 도착하면 ACK   (a + b >= 1)
    새: **복호 가능한 원본**이 하나라도 도착해야 ACK  (a >= 1)

이 설계의 패리티는 롱헤더 Initial로 위장한 패킷이라 AEAD를 통과하지 못한다. QUIC 스택은 복호에 실패한 패킷을 조용히 버리고 ACK하지 않는다(RFC 9000 §12.2). 복구에 성공해야만 원본이 스택에 올라간다.

실측 근거(p17, 10 Mbps · p=0.155 · k=2):

| | 옛 모형 | 새 모형 | 실측 |
|---|---|---|---|
| m=1 PTO | 0.0241 | 0.0241 | 0.023 |
| m=2 PTO | 0.0037 | 0.0241 | 0.023 |
| m2-m1 비용차 | -1.85 ms | +1.06 ms | +0.94 ms |

옛 식은 m이 클수록 PTO를 피한다고 봐서 m=2를 과대평가했고, 예측 부호도 실측과 반대였다. 격자 330점 중 81점(24.5%)에서 선택이 바뀐다.

## 3. 결정 규칙

```
    J(δ, m) = E[n_rtt | 복구 성공] · RTT
            + stall(δ, m)                      ← 아래 §3.1 (2026-08-29 에 배율이 붙었다)
            + t_tx(추가 바이트)

    stall  = (R − 1)/P_fail
             × [ P(실패·PTO)         · (RTT      + T_pto)
               + P(실패·PTO_표본)    · (n_ok·RTT + 3·RTT)
               + P(실패·ACK)         · (n_ok·RTT + T_ack) ]

    (δ*, m*) = argmin J
```

> 구판 명세는 이 식을 두 군데 틀리게 적고 있었다(2026-08-30 정정).
>
> ① 실패 가지가 셋인데 둘만 적었다(`p_fail_pto_sampled` 누락).
>
> ② 배율 `(R−1)/P_fail`이 아예 없었다. 2026-08-29에 코드에 들어갔는데 명세를 고치지 않아서 정본이 코드보다 낡아 있었다.

네 항은 모두 하나의 결합 도착분포에서 나온다.

```
    Pr[a, b]  = 원본 a 개 · 패리티 b 개가 도착할 확률   (Gilbert-Elliott, 배치 반영)
    복구 가능  ⟺  k − a ≤ b                            (MDS)
    신용 바이트 = a·W_eff + b·파(W_eff, k)              (도착한 것만)
```

`파(w,k) = w + 39 + 6k`는 패리티 데이터그램의 실제 크기다(롱헤더+CID ~26 + FEC 머리 13 + crc/len 목록 6k). 원본보다 크므로 후보 생성 단계부터 이 값을 쓴다. (정정 2026-08-20: 구판 상수 32는 CID를 과소평가했다. p13 실측 패리티가 1,323.5~1,332 B로 W+32+6k보다 ~7 B 컸다. CID 길이가 무작위라 ±수 B의 오차는 남고, 남는 오차는 신용을 과소평가하는 쪽(보수적)이다.)

### 3.1 반복 라운드 배율 `(R−1)/P_fail`

2026-08-29에 새로 넣었다. 그전까지 모형은 복구 라운드를 정확히 한 번만 청구하고 있었다. 옛 stall은 `P_fail · (대가)` 꼴이라 재전송이 다시 실패하는 경우가 통째로 빠져 있었다.

p18 실측(cert 4,032 · 버스트 3 · 손실 15% · 팔당 9,000판)에서 실패한 연결의 평균 라운드 수는 다음과 같다.

| m | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 실측 R | 1.1896 | 1.1759 | 1.1044 | 1.0648 |
| 모형 R (신설) | 1.2148 | 1.2590 | 1.1566 | 1.0993 |
| 비 | 1.02 | 1.07 | 1.05 | 1.03 |
| 옛 모형 | 1.000 | 1.000 | 1.000 | 1.000 |

문제는 오차가 m에 따라 달랐다는 점이다. 그래서 m끼리의 비교가 왜곡된다. p18 검사 6이 버스트 3에서 실측 이득 +31.01 vs 예측 +13.51로 실패한 원인이 이것이었다. 오차는 우리에게 불리한 방향이었다. 모형이 알고리즘의 값을 스스로 깎고 있었다.

#### 정상분포에서 다시 시작할 수 없는 이유

재전송은 직전 실패 때의 채널 상태에서 시작한다. netem의 `gemodel`은 패킷마다 전이하므로 PTO 대기(≈200 ms) 동안 사슬이 이완하지 않는다. 정상분포를 가정하고 재실패 확률을 구하면 실측의 0.38배, 즉 2.6배 과소평가가 된다(m=1: 유도 0.136 vs 실측 0.356).

그래서 라운드마다 실패 시점의 조건부 상태를 다음 라운드의 초기 분포로 넘긴다(`expected_rounds` / `_joint3c_state`). 이 상태는 같은 DP에서 나오므로 따로 맞춘 상수가 하나도 없다.

#### 안전판

- `p = 0`이면 `R = 1`이라 배율이 1.0이므로 무손실 실측값은 전혀 바뀌지 않는다.
- 버스트 1에서는 2차 항이라 p18 무버스트 조건의 예측 이득이 10.69 → 10.56(1.2%)만 변한다.
- 세 실패 가지의 상대 비율은 건드리지 않는다(`failFracLookup`의 배분을 그대로 쓴다).
- Go는 배율 자체를 표에서 읽는다(`roundMultTable`). R을 심고 Go에서 나누면 보간 오차가 겹친다. 실제로 그렇게 했을 때 관문 J 어긋남이 0.096 → 0.263 ms로 커졌다.

#### 이 수리에서 저지른 실수

모두 관문이나 자체시험이 잡았다.

| | 실수 | 잡은 것 |
|---|---|---|
| 1 | 실패 조건을 「소거 개수 > g」로 씀 | 단조성 자체시험 21e |
| 2 | `not recovers()`로 0 소거를 실패로 셈 (p_fail 0.14 → 0.94) | 21b |
| 3 | R을 심고 Go에서 나눔 | 관문 J 0.096 → 0.263 ms |
| 4 | 분모를 `table.pfail`(MDS 가정)로 씀. 실제는 `p_fail_of`(구현 기준). `pfail(k,m)`이 `p_fail_of(k,m+1)` 꼴로 한 칸 어긋난다 (k=3 m=2 p=0.15: 0.0266 vs 0.1095, 4.1배) | 관문 57,248건 · J 77.5 ms |
| 5 | 배율이 밑에 깔린 보간 오차를 같이 키운다(p=0.2875에서 1.49배) | 관문 초과점 → `P_VALS` 26점 |

> 같은 이름의 확률이 두 개 있을 수 있다(`table.pfail` = MDS, `p_fail_of` = 구현). 또 곱해지는 항을 새로 넣으면 밑의 격자도 그만큼 촘촘해야 한다. 이를 확인하지 않으면 「새 항이 부정확하다」고 오진한다.

### 3.2 세 번째 실패 가지 (표본 RTT PTO)

§2.6의 정정은 실패를 PTO / ACK 둘로 갈랐지만 구현에는 가지가 셋 있다.

| 가지 | 조건 | 대가 |
|---|---|---|
| `p_fail_pto` | 복호 가능한 원본이 하나도 안 왔다 | `RTT + T_pto` (T_pto = 200.86 ms, 경로 무관 상수) |
| `p_fail_pto_sampled` | 마지막 원본이 유실. RTT 표본은 이미 있다 | `n_ok·RTT + 3·RTT` |
| `p_fail_ack` | 원본 일부 도착, 구멍으로 즉시 재전송 | `n_ok·RTT + T_ack` |

> `PTO_SAMPLED_RTT_MULT = 3.0`은 실측값이 아니라 RFC에서 유도한 값이다. 코드 주석에 재는 법까지 적혀 있다. `_probe_trecover.py`에 `-drop-initial k-1` 팔을 여러 RTT에서 돌리면 이 식이 RTT에 비례하는지가 바로 나온다. 아직 재지 않았으므로 보고서에는 이 항을 「측정했다」고 쓰지 않는다.

> 코드 주석 두 곳이 서로 다른 수를 적고 있다(2026-08-30 발견, 미해결). `expected_rounds` 독스트링의 표는 모형/실측 비를 1.02~1.07로 적는데, `decide_v2` 안의 주석은 「1.01~1.02」라고 적는다. 재측정이 끝나면 두 값을 대조해 맞는 쪽으로 통일해야 한다.

### 2026-08-20 감사의 비용식 수정

고치기 전 식은 `E[n_rtt] · RTT + P_fail · T_recover`였고, 결함이 두 가지 있었다.

(1) 한 식에 손실 모형이 두 개 있었다. `E[n_rtt]`는 원본과 패리티를 각각 독립 이항으로 굴렸는데 `P_fail`은 Gilbert-Elliott을 썼다. 증거로, k=2·m=1·p=0.05에서 버스트를 1→5로 바꾸면 `P_fail`은 6.6배가 되는데 `E[n_rtt]`는 소수점 6자리까지 그대로였다. 손실이 뭉치면 패리티까지 같이 잃어 신용을 못 사는 사건이 독립 가정보다 훨씬 흔한데, 그 항은 버스트를 보지 못해 항상 낙관 쪽으로 치우쳤다.

(2) 같은 손실 사건을 두 항에서 따로 청구했다. 전멸하면 서버가 아무것도 받지 못하므로 `A(0)=0`이라 `n=2`로 세어지고, 동시에 `P_fail`로 `T_recover`도 물었다. 물리적으로는 전멸 뒤 재전송이라는 한 사건이다. 실측: m=0·k=1·p=0.2·RTT 50 ms에서 `60 ms(왕복항) + 10 ms(정지항) = 70 ms`였다. 보정하면 60 ms이고, 290개 조건 중 5건(1.7%)에서 결정이 뒤집혔다. 뒤집힌 조건은 모두 필요 없는 1,318 B 패리티를 사고 있었다.

그래서 `n_rtt`는 복구 성공 상태에만 매기고, 실패는 `(RTT + T_recover)` 한 번으로 값을 매긴다. `p = 0`이면 실패 확률이 0이라 예전 식과 완전히 같으므로, §2의 헤드라인(1바이트 절벽)은 영향을 받지 않는다.

### 패리티 배치와 후보 집합

```
    m = 1  →  [원본…, 패리티]              뒤엣것이 복구용
    m ≥ 2  →  [패리티0, 원본…, 패리티1]    앞이 신용, 뒤가 복구
```

독립 손실 가정에서는 배치가 결과에 영향을 주지 않았다. 버스트 손실에서는 인접한 데이터그램이 함께 사라지므로, 패리티를 어디에 두느냐에 따라 도착 조합의 분포가 바뀐다.

후보 집합은 연속으로 훑지 않고 경계점만 본다. v2 계산에서 가장 중요한 원칙이다.

```
후보 = { (0, 0) }                                  # 아무것도 안 함
     ∪ { (ceil(Δ_j/k), 0)  : j = 1..J }            # δ 로 j 칸 올라간다
     ∪ { (0, m)            : m = 1..m_max }        # 패리티만
     ∪ { (0, ceil(Δ_j/파)) : j = 1..J, Δ_j ≥ W }   # 패리티로 j 칸 올라간다

    Δ_j = (다음 j 번째 칸에 들어가는 최소 추가 바이트)
```

동점은 다음 순서로 가른다. ① `J`가 최소인 쪽, ② 실제 추가 바이트가 최소인 쪽, ③ 같은 바이트면 패리티를 우선(보조정리 1), ④ `late_parity_risk`가 없는 쪽, ⑤ `over_mtu`가 없는 쪽. ④는 p13이 가설을 기각한 뒤로 항상 거짓이라 사실상 무효다(§2.6 결과).

> ②에서 실제 바이트를 쓰는 것도 위 감사에서 고친 것이다. 예전에는 패리티를 `W`로 센 근사값으로 동점을 갈랐는데, 점수 `J`는 실크기로 계산했다. 그래서 동점일 때 실제로는 더 큰 후보를 더 작다고 보고 골랐다(m=1에서 38 B, m=2에서 76 B 차이).

보낼 수 없는 후보는 뺀다. 2026-08-20 실측에서 quic-go가 `InitialPacketSize`를 1452로 깎는다는 것을 확인했으므로 `W_eff > 1452`는 후보에서 제외한다. `pad_repack`(데이터그램을 합쳐 재패킹)도 기본으로 제외한다. 모형에는 있지만 우리 테스트베드가 CRYPTO 재분할을 하지 않기 때문이다. 구현되지 않은 선택지는 고르지 않는다.

### `T_recover`의 두 차례 수정

첫 번째는 v1에서 v2로 넘어올 때다. v1은 원본 하나를 잃으면 PTO(RFC 9002 초기값 999 ms)를 문다고 봤는데, 측정해 보니 틀려서 `rtt_ms`로 바꿨다.

두 번째는 2026-08-20이다. 그 `rtt_ms`도 틀렸다. 결정적 소거로 직접 재 보니 대가가 하나가 아니라 둘이었다. 둘을 가르는 것은 k가 아니라 실패한 순간 서버가 하나라도 받았는지다.

`experiments/_probe_trecover_rtt.py`는 `-drop-initial 0`으로 매 판 첫 비행을 버리고 기준선과의 p50 차이를 잰다. 모든 표본이 손실 사건이라 잡음이 없다.

| RTT | k=1 (x25519) | k=2 (X25519MLKEM768) |
|---|---|---|
| 10 ms | 200.90 ms (20.09×) | 12.62 ms (1.26×) |
| 50 ms | 200.96 ms (4.02×) | 57.77 ms (1.16×) |
| 100 ms | 200.73 ms (2.01×) | 113.88 ms (1.14×) |
| 판정 | 고정 상수 (폭 0.23 ms) | RTT 비례 (배수 폭 0.10) |

```
    받은 게 0 개  ->  서버가 ACK 를 못 준다  ->  클라가 PTO 타이머를 문다
                     그 타이머는 RTT 표본이 없을 때의 값이라 경로와 무관하다
                     T_pto = 200.86 ms                    (quic-go v0.61.0 실측)

    1 개 이상     ->  서버가 ACK 를 준다 -> 패킷번호 구멍으로 즉시 재전송
                     T_ack = 1.125·RTT + 1.42 ms          (최소제곱, 잔차 |0.10| ms)
```

`k=1·m=0`은 실패가 곧 전멸이라 항상 PTO 가지다. 그래서 겉으로는 k에 따라 다른 것처럼 보였다. 하지만 결합분포가 두 가지를 이미 구분해 주므로, k로 분기하지 않고 도착 개수로 나눈다(`p_fail_pto` / `p_fail_ack`).

> v2 초판의 "서버가 ACK 를 주므로 대가는 왕복 하나다"는 ACK 가지에서만 참이다. 코드 주석에는 PTO 경로가 적혀 있었는데, 기본값은 조용히 틀린 가지를 탔다.

#### 이 수리가 바꾼 결정

옛 기본값(`t_recover = RTT`)과 비교하면 스윕 2,640 조건 중 405건(15.3%), `k=1`만 보면 1,320 중 286건(21.7%)에서 결정이 달라진다. 방향은 모두 같다. 옛 기본값은 `none`(무방비)을 고르고 새 기본값은 `parity`를 고른다. 옛 기본값은 손실 한 번에 201 ms가 드는 바로 그 자리에서 과소보호하고 있었다.

#### 실측 검증 (`results/probe_trecover_verify.json`)

조건: x25519 · k=1 · cert 1,000 · RTT 10 ms · n=300(워밍업 20 제외).

| 손실 | 실측 `off` | 옛 예측 | 새 예측 | 실측 `m=1` | 실측 `m=2` |
|---|---|---|---|---|---|
| 2% | 14.656 ms | 10.20 (−4.46) | 14.02 (−0.64) | 12.170 | 12.134 |
| 5% | 22.459 ms | 10.50 (−11.96) | 20.04 (−2.42) | 12.128 | 12.139 |

- `off` 팔 예측 오차가 7.0배 · 4.9배 줄었다.
- 옛 기본값은 두 조건 모두에서 `off`를 최적으로 골랐는데, 실측으로는 가장 나쁜 팔이다. 새 기본값은 두 조건 모두 패리티를 고르고, 실측과 맞다. `m=1`과 `m=2`의 실측 차는 0.01~0.04 ms로 구분할 수 없으므로 둘 사이는 판정하지 않는다.
- 꼬리에도 증거가 그대로 보인다. 손실 5% `off`의 p95가 211.2 ms인데, 201 ms PTO가 드러난 값이다.

> 세 상수는 quic-go v0.61.0의 타이머를 잰 값이므로 다른 스택에서는 다시 재야 한다. 상수를 쓴 것이 문제가 아니라 출처 없는 상수를 쓴 것이 문제였다.

### Go 이식과 공유 표

`experiments/quicbed/policy.go`의 `flightOutcome`도 같은 식을 쓴다. 결합분포는 Go에서 다시 계산하지 않는다. `padfec/table.py`가 검증된 Python 모형에서 표를 뽑아 심고, Go는 조회만 한다. 1차 때 Cauchy 행렬을 양쪽에서 따로 짰다가 결과가 갈라진 전례가 있기 때문이다. 표는 `%.17g`(float64 왕복 정밀도)로 찍는다.

> 같은 감사에서 여기서도 결함이 나왔다. `policy.go`는 `pfailLookup(k, m, p, 1.0)`으로 버스트를 호출부에 리터럴로 박아 뒀고, Python은 실제 버스트를 썼다. 그래서 같은 입력에 두 구현이 다른 `m`을 골랐다(90 조건 중 17건). 지금은 버스트가 인자로 넘어가고, `P_fail`의 두 번째 출처(`pfailTable`)는 아예 지웠다. 남겨 두면 누군가 다시 그것을 부르기 때문이다. 2,688 격자점 대조에서 불일치는 0건이다.

#### v2 지렛대까지 이식 (2026-08-20)

위 문단은 비용식에 관한 것이다. 결정 변수가 둘(δ·m)이 된 뒤에도 Go는 `m`만 골랐고, 그래서 헤드라인(§8의 1바이트 절벽)은 사람이 `-ips`를 손으로 줄 때만 실현됐다. 후보 생성 `levers`와 순위 `evalCands`를 §3 그대로 옮겼다. `decide`의 반환값이 `m` 하나에서 `(InitialPacketSize, m, 근거, 무편향)`으로 늘었고, `qamp`가 고른 `ips`는 그 판의 `quic.Config.InitialPacketSize`에 그대로 들어간다.

옮겨도 되는 것과 안 되는 것을 나누는 기준은 그대로다. 확률 모형은 표로 심고 정수 산술만 옮긴다. 그런데 정수 산술은 갈라질 여지가 없다는 생각이 틀렸다.

> `ceilDiv`에서 문제가 났다. Python `-((-a) // b)`는 `//`가 내림이라 올림이 되지만, Go `/`는 0 쪽으로 절사하므로 그대로 옮기면 내림이 된다. `ceilDiv(161,2)`가 81이 아니라 80이 되고, `binIndex`가 한 칸씩 낮게 나와 δ 후보가 칸을 올리지 못한다. 그러면 `pad` 지렛대가 통째로 죽는다. 5,670 격자점 중 92건으로 잡혔다.

그래서 대조를 관문에 상설로 붙였다(`experiments/gate_go_parity.py`). 격자의 정본은 Go 쪽(`policy.go`의 `policyGrid`)이고, Python은 그 출력을 읽어 따라간다. 양쪽에 목록을 따로 적으면 언젠가 갈라지기 때문이다.

- 대조 대상은 (mode, δ, m, `W_eff`) 네 개 전부다. 예전에는 `m` 하나였다.
- 당시 5,670 격자점에서 불일치는 0건이었고, 0.6초 걸렸다.
- 일치만으로는 부족하다. 양쪽이 나란히 아무것도 안 골라도 불일치는 0건이다. 그래서 선택 분포도 같이 찍는다. 당시 분포는 `parity` 64.8% · `none` 31.6% · `pad` 3.6%(206건, 그중 δ=1이 98건)였다. δ=1이 0건이면 관문은 실패한다.
- 부정 시험으로 `ceilDiv`를 일부러 되돌리면 92건이 그대로 재현된다.

> 지금 값(2026-09-03). 격자를 네 번 넓혀(08-21 업링크 축 · 08-25 s0 정본 상수 · 08-28 격자 밖 p·버스트 · 08-29 p 축 정밀화) 196,020 격자점이 됐고, 불일치는 여전히 0건이다. 결정이 같은 점의 J 어긋남은 최대 0.0950 ms(한도 0.100, 초과 0건)로, 여유는 5%다. 선택 분포도 `parity` 75.6% · `combo` 17.6% · `none` 5.8% · `pad` 1.0%(1,960건, δ=1 720건)로 바뀌었다. 격자가 35배라 관문은 이제 0.6초가 아니라 수 분이 걸린다.
>
> 관문에는 빌드 지문 대조도 붙었다(2026-09-03). 관문은 Go를 빌드하지 않으므로 낡은 바이너리로 돌 수 있다. 08-29 이전 바이너리로 돌리면 「진짜 불일치 5,016 건 · J 최대 46.09 ms」가 나오는데, 모형 결함처럼 보이지만 실제로는 빌드 문제다. 이제 소스 SHA-256이 맞지 않으면 격자를 읽기 전에 중단한다.

#### 폐루프 실측

폐루프는 §8의 자리를 스스로 찾는다. 조건은 x25519 · cert 4,032 · RTT 50 ms · 무손실 · 라운드당 400 연결이고, 빈 캐시에서 시작했다(`experiments/_probe_v2converge.py`).

| 라운드 | p 추정 | 평상시 선택 | ips 분포 | p50 |
|---|---|---|---|---|
| 1 | 0.0377 | `parity` m=2 | 1280: 388 / 1281: 12 | 52.35 ms |
| 6 | 0.0073 | `parity` m=1 | 1280: 380 / 1281: 20 | 52.41 ms |
| 7 | 0.0050 | `pad` δ=1 | 1280: 106 / 1281: 294 | 51.33 ms |
| 8 | 0.0050 | `pad` δ=1 | 1281: 400 | 51.29 ms |

400판 모두 `ips=1281 · m=0`이다. 사람이 손으로 준 팔(51.25 ms)에 도달했고, 패리티 1,318 B가 하던 일을 1바이트가 대신했다.

다만 수렴 여유는 1.42배뿐이다.

    pad 가 이기는 상한   p <  0.00703   (§3 의 J 비교, 이분탐색)
    추정기가 닿는 하한   p =  0.00495   (Jeffreys + 감쇠 0.99)

감쇠 0.99의 관측 수 고정점이 100이므로 하한은 `0.5/101`로 고정된다. 감쇠를 0.98로만 낮춰도(고정점 50) 하한이 0.0098로 올라가 문턱을 넘고, 그러면 폐루프는 `pad`를 끝내 고르지 못한다. 감쇠·탐색 주기·`c`를 손볼 때는 이 부등식을 반드시 같이 확인해야 한다.

> 6라운드까지 `parity`를 고른 것은 정책의 오류가 아니다. p=0.0073에서는 패리티가 실제로 옳은 선택이다(pad는 복구가 없어 실패 한 번에 PTO 201 ms). 고칠 대상은 결정 규칙이 아니라 추정의 수렴 속도였고, 아래 절에서 다룬다.

#### δ 후보를 이용한 탐색

위의 이식 덕분에 가능해진 방법이다. `p`는 `m=0`인 연결에서만 편향 없이 관측된다(§4.3). 그런데 `m`만 있던 때에는 `m=0` 후보가 맨몸 하나뿐이라, 임계 위에서는 탐색 한 번이 곧 2-RTT였다. 그 비용 때문에 탐색 주기가 늘어나 400 연결에서 무편향 관측이 3회뿐이었고, `p`는 Jeffreys 사전값 근처(0.126)에 머물렀다. 그 `p`로는 패리티가 늘 이겨서 δ 후보가 끝내 뽑히지 않는다.

δ는 복구를 주지 않으므로 손실 관측을 편향시키지 않는다. 따라서 `m=0`이기만 하면 무엇이든 탐색에 쓸 수 있다. 후보는 이미 `J`로 정렬돼 있으니 첫 번째 `m=0` 후보가 가장 싼 탐색이다. 임계 위에서는 그것이 보통 `pad`이므로, 탐색의 대가가 왕복 하나(RTT)에서 δ 패딩의 전송시간으로 바뀐다. k=2·δ=81이면 162 B다. `decide`는 이 차이(`probeCost`)를 재서 탐색 주기를 스스로 정한다. 탐색 비용이 RTT의 1%를 넘지 않도록 주기를 늘린다.

- 신용만 필요하면 δ 1바이트를 쓴다. cert 4,000 무손실에서 `pad`(J=50.001)가 `parity m=1`(J=51.054)을 이기고, 같은 1-RTT를 1,318배 싸게 산다.

- 1바이트로 닿지 못하는 곳이 있다. cert 6,000은 칸 4(임계 4,585.5) 밖이라 δ로는 넘지 못하고 패리티의 1,318 B가 필요하다. `ips` 상한 1452 때문에 δ로 갈 수 있는 칸이 막혀 있다.

## 4. 바뀌지 않는 것

- 용량 정리 `C ≤ (k−1)(W−h−f)`는 그대로 유효하다. v2에서 이 정리는 δ가 복구를 줄 수 없는 이유를 설명한다. 키운 데이터그램 안의 여분 바이트는 그 데이터그램이 통째로 사라질 때 같이 사라지기 때문이다. `k=1`이면 우변은 0이다. 실측 12개 설정이 모두 위반했고, 가장 가까운 경우도 76.0 B 부족했다(`p1_flight.json` capacity_checks, ML-KEM/ips1450: C=1457, 용량 1381.0). `f=0`으로 잡아도 60.0 B 부족하므로 결론은 꼬리표 크기에 강건하다. (정정: v1 문서와 이 명세 초판이 적은 '56 B'는 틀렸다. 같은 행의 h=53.0으로 재계산하면 60.0 B다.)
- 배치 규칙도 그대로다. `m=1`이면 `[원본…, 패리티]`(복구), `m≥2`이면 `[패리티0, 원본…, 패리티1]`(앞이 신용, 뒤가 복구)이다. 근거는 quic-go `connection.go:669`의 `if !wasProcessed { continue }`다.
- 회계 불변식 `스택에 넘긴 누적 ≤ 물리적으로 받은 누적`도 그대로다.
- 타이밍 조건도 그대로다. 추가 바이트는 서버가 응답 비행을 만들기 전에 도착해야 한다(e21: dup1은 정지 2.3 ms 뒤에 도착해 임계를 옮기지 못했다). δ는 같은 데이터그램을 키우는 방식이라 이 조건을 구조적으로 만족하므로, 패리티보다 안전하다.

### 규격 위반 사실

quic-go `isAmplificationLimited()`는 `bytesSent >= 3*bytesReceived` 불리언 게이트이고, 패킷을 만들기 전에만 검사한다. RFC 9000 §8.1은 예외 문구 없이 `MUST NOT send more than three times`라고 적으므로, 이 양자화는 규격 위반이다. v2는 이 사실과 함께, 우리 설계가 그 위반에 기대고 있다는 점도 명시한다.

## 6. 선행연구와 v2의 위치

- 아이디어는 이미 규범에 있다. RFC 9002 §A.9 의사코드 주석에 "Initial is padded to earn more anti-amplification credit"라는 문장이 있다. RFC 9000 §8.1도 교착을 막으려고 클라이언트가 ≥1200 B를 보내도록 MUST로 요구한다. 그러므로 "클라가 바이트로 예산을 산다"는 우리 기여가 아니다.
- Fastly(McManus)도 이미 "certificate chain budget between 3333 and 4356 bytes depending on the initial client packet size", "extra 200 bytes of padding will halve the handshake time for 7% of connections"라고 적었다. 우리 기여는 그 200바이트가 왜 200이고 언제 1바이트로 충분한지를 닫힌 식으로 설명하는 것이다.
- Nawrocki (CoNEXT 2022)의 기여 (3)은 "Analysis of QUIC server behaviors for different sizes of client Initial messages"이고, §5에는 "Dealing efficiently with loss of messages during the connection setup seems an open challenge."라는 문장이 있다. 우리 문제는 이미 등록된 미해결 과제이고, 이 논문을 인용하면 기여가 강해진다.
- 용량 부등식은 Singleton/MDS 한계에 QUIC 상수를 대입한 것이다. "정리"로 내세우면 한 줄로 반박당하므로, 부정 결론(60~76 B 부족)과 그 강건성으로 쓴다.
- 보충이 필요한 누락 9건: QUIRL(ToN 2024), Nawrocki(CoNEXT 2022), ReACKed QUICer(2024), Banks 5x 제안(2024-07), `draft-ietf-tls-cert-abridge`, Huawei FEC 드래프트 2건, RFC 9000 §8.1 교착 문단, RFC 9002 §A.9.

## 7. 주장 서열 (신규성 순)

1. 양자 경계 절벽. `Δ_min = 1` 따름정리와 그 실측, 그리고 기본값이 최악점에 걸터앉아 있다는 사실이다. 우리가 새로 만든 결과이고 v2의 헤드라인이다.
2. 신용/복구 배치 의존성. 하나의 패리티로 둘을 동시에 얻을 수 없다. 충돌하는 선행연구는 찾지 못했다. 다만 근거가 quic-go 단일 경로뿐이라 다른 스택에서 재현해야 한다.
3. 증폭 임계 양자화 모형. 아이디어는 규범에 있지만, 게이트와 바이트 상한의 구분과 닫힌형 `ceil(3B/P)·P`는 찾지 못했다.
4. 용량 부등식. Singleton 따름정리이므로 부정 결론으로만 쓴다.
5. 폐루프 후회. 적응형 FEC 비용 최적화 연구의 계보가 두껍다(Bolot 1999, Park AFEC). 지표 자체는 기여가 아니다.
