# 실험 연결 계획 — 수집할 데이터와 연결할 것들

> 계획서 「연구 내용 1(ML-KEM 성능 분석)·2(실험 환경 구축)·4(성능 평가)」의
> 실행 청사진. 알고리즘(내용 3)은 완성·검증됐고, 이제 현실과 잇는 단계다.
> 작성: 2026-08-14. 전제: 공유 리눅스 서버 (격리 규칙은 README 참고)

---

## 0. 전체 그림 — 다섯 단계, 각각이 보고서 재료

```
[1] ML-KEM 핸드셰이크 실측  ->  추정 상수 3개 확정        (연구 내용 1)
[2] 손실 트레이스 수집       ->  NetEm <-> 모델 환율표      (연구 내용 2)
[3] 트레이스 재생 평가       ->  실채널에서 알고리즘 성능    (내용 4 예비)
[4] 데이터 구간 FEC 라이브    ->  QUIC DATAGRAM 위 통합     (연구 내용 2+4)
[5] 핸드셰이크 보호 (스트레치) ->  quic-go Initial 경로 수정
```

핵심 설계 판단: **[1]~[3]은 스택 수정 없이 된다.** 알고리즘을 QUIC에 심기
전에, 실측 데이터를 알고리즘 쪽으로 가져와서 평가하는 것(trace-driven)이
먼저다. 통합 리스크 없이 "실채널에서 어떤가"에 답할 수 있고, [4][5]가
막혀도 연구가 성립한다.

## 1. 단계별: 수집할 데이터 / 연결할 것 / 방법

### [1] ML-KEM 핸드셰이크 실측 (연구 내용 1)

**연결할 것**: Go 1.24+ 와 quic-go. Go 표준 `crypto/tls`가 X25519MLKEM768을
기본으로 쓰므로 클라이언트·서버 각 40줄 정도면 진짜 ML-KEM QUIC 핸드셰이크가
돈다. 대조군(X25519 단독)은 `CurvePreferences` 한 줄 전환.
- Go는 tarball을 홈 디렉터리에 풀면 끝 — **sudo 불필요.**
- 패킷 관찰은 tcpdump 대신 **quic-go 내장 qlog**로: 패킷 크기·타이밍·프레임
  구성이 JSON으로 다 나온다. **캡처 권한(sudo)도 불필요** — 공유 서버 친화.

**수집할 데이터**:
| 항목 | 대체할 추정값 | 쓰이는 곳 |
|---|---|---|
| ClientHello 전체 크기 (양쪽 KEM) | `ch_base=350` | handshake.py |
| Initial 1패킷의 실제 CRYPTO 수용량 | `INITIAL_CRYPTO_CAPACITY=1150` | 패킷 분할 계산 |
| 서버 플라이트 크기 (인증서 체인 포함) | `cert_chain=3000` | 서버 shield |
| 실제 패킷 분할 수 (ML-KEM이 정말 2+/5+가 되나) | 연구의 전제 검증 | 보고서 §1 |
| 캡슐화/디캡슐화 시간 (768/512/1024) | (계획서 내용 1 명시 항목) | 보고서 §1 |
| 핸드셰이크 완료 시간 분포 (손실 0~10% x 양쪽 KEM, 각 500회+) | 해석해 검증 | 모델 신뢰성 |

### [2] 손실 트레이스 수집 (연구 내용 2)

**연결할 것**: NetEm/tc. 공유 서버라 두 가지 길:
- **sudo 없이**: `unshare -r -n`으로 비특권 사용자 네임스페이스 안에 자기만의
  네트워크(veth 쌍 + netem)를 만든다. 커널이 unprivileged userns를 허용해야
  함 — 서버에서 `unshare -r -n true`로 1분 확인 가능. **이 길이 되면 실제
  NIC·다른 사용자 트래픽과 완전 격리라 공유 서버 요구사항과도 정확히 맞는다.**
- sudo 가능하면: veth+netns 표준 구성 (⚠️ lo에 걸면 양방향 중복 적용).

**수집할 데이터**:
- **손실 마스크 트레이스**: 순번 붙인 UDP 프로브를 일정 속도로 쏘고 수신
  기록 → "몇 번째 패킷이 사라졌나" 비트열. netem 설정별(loss p%, 상관 c%) ×
  수십만 패킷.
- 이 트레이스에서 실측 (손실률, 평균 버스트) 산출 → **netem 설정 vs
  Gilbert-Elliott 파라미터 환율표**. 시뮬 세계와 실험 세계를 잇는 다리.
- RTT 시계열 (혼잡 유발 시나리오 포함 — iperf로 큐 채우면서) → 혼잡 가드
  검증용.

### [3] 트레이스 재생 평가 (스택 수정 없는 실채널 평가)

**연결할 것**: sim.py에 "트레이스 재생 채널" 추가 — GE 모델 대신 [2]의 실측
마스크를 그대로 흘리는 20줄짜리 확장. 알고리즘·검증 62개는 그대로.

**얻는 것**: "GE 근사가 아니라 **진짜 채널의 손실 패턴** 위에서 정책 비교"
— none/static/adaptive/cached의 후회를 실측 트레이스로 다시 계산. 시뮬 결과
(§9)와 나란히 놓으면 모델 간극이 정량화된다. 여기까지가 통합 없이 가능한
최대치고, 보고서의 뼈대로 충분하다.

### [4] 데이터 구간 FEC 라이브 통합

**연결할 것**: QUIC DATAGRAM(RFC 9221, quic-go 지원) 위에 심벌을 실어
나르는 실험 앱. 알고리즘 연결은 **파이썬 사이드카**: Go 송신자가 블록마다
손실 마스크·RTT를 로컬 파이프로 파이썬 프로세스에 넘기고 (K, r)을 받아온다.
- 알고리즘을 Go로 포팅하지 않는 이유: 검증 62개가 얹혀 있는 파이썬 원본을
  그대로 쓰는 쪽이 결과의 신뢰성이 높고, 결정은 블록당 1회(수 ms 여유)라
  파이프 왕복 비용이 문제가 안 된다.

**수집할 데이터**: 계획서 내용 4의 지표 그대로 — 전송 총시간, goodput,
블록 복구율, 오버헤드, CPU 사용량. 정책 × netem 설정 × 반복 12회+.

### [5] 핸드셰이크 보호 (스트레치 골 — 제일 무겁다)

Initial 패킷 경로는 스택 내부라 응용 계층에서 불가능. quic-go를 포크해
클라이언트 Initial 플라이트에 **XOR 패리티 패킷 1개**를 추가하는 최소 수정
(K=2에서 r=1이면 RS가 아니라 XOR 한 장으로 충분 — 아무 1패킷 손실 복구).
수신 측 재조립까지. 여기가 막히면 [1]의 실측 분포 + 해석해 예측 결합으로
핸드셰이크 효과를 논증한다(모델이 [1]에서 검증됐다는 전제 하에).

## 2. 서버에 필요한 것 정리

| 필요한 것 | sudo? | 확인 방법 |
|---|---|---|
| Python 3.8+ | X | `python3 --version` (준비됨) |
| Go 1.24+ | X (홈에 tarball) | `go version` |
| quic-go | X (`go get`) | - |
| unprivileged userns (netem용) | X | `unshare -r -n true; echo $?` |
| (대안) sudo로 netns/tc | O | 관리자와 협의 |
| 디스크 ~2GB (Go+모듈+트레이스) | X | - |

**모르는 것 (도현님 확인 필요)**: 배포판/버전, Go 설치 여부, sudo 또는
unprivileged userns 가능 여부, 실험을 서버 한 대 안(netns)에서 할지 두 대
사이에서 할지. — 이 답에 따라 [2]의 길이 갈린다.

## 3. 격리 규칙과의 관계

- [1]~[3]의 산출물(qlog, 트레이스)은 전부 프로젝트 폴더 안에 저장한다.
- [4]부터는 소켓을 쓰므로 **실험 하네스를 `experiments/` 폴더로 분리**한다.
  알고리즘 라이브러리(afec/)의 "무접촉" 발자국 검증은 그대로 유지 —
  소켓은 하네스에만 존재.
- netns 안에서 도는 트래픽은 서버의 실제 네트워크와 격리된다(포트 충돌·
  대역폭 간섭 없음). 프로브/전송 실험도 run_confined.sh 아래에서 돈다.
