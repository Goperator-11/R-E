## 한 줄씩 결론

**측정 (`mlkem-quic-amplification/`)**
- ML-KEM 은 패킷 수를 늘리지만 **손실 취약성은 유의하게 늘지 않았다**(PTO 12.0% vs 10.4%, z=0.79).
  이 결과가 계획서의 전제를 기각했고 FEC 의 역할이 바뀌었다.
- 증폭 임계가 KEM 별로 다르고(X25519 3,300~3,400 B / PQC 5,900~6,000 B),
  그 사이 **역전 구간**에서 PQC 가 왕복 1회만큼 빠르다.
- 원인은 알고리즘이 아니라 **바이트 수**다 — 패딩만 늘려도 임계가 움직인다.

**알고리즘 (`pq_afec/`)**
- **무비용 FEC 는 원리적으로 불가능하다.** 제자리 1-소거 보호는 `C ≤ (k−1)(W−h−f)` 를 요구하는데
  실측 12개 설정이 전부 위반한다(최근접도 76.0 B 초과, 꼬리표를 0 으로 잡아도 60.0 B).
- 대신 **증폭 예산이 이산(1,280 B 단위)이라는 점**을 쓴다. quic-go 기본 `InitialPacketSize=1280` 은
  그 양자 경계에 정확히 걸터앉아서, **1 바이트만 더 보내면 서버 예산이 1,280 B 뛴다**(k 무관).
- 실측: **1 바이트에 왕복 하나** — x25519 51.98 ms(1.040 RTT), X25519MLKEM768 50.86 ms(1.017 RTT).
  부정 시험(`1279 ≡ 1280`, `1281 ≡ 1350`)도 통과했다.

각 폴더의 README 에 상세와 **정직하게 남긴 한계**가 적혀 있다. 숫자를 인용하기 전에 그 한계 절을 먼저 읽어라.

## 재현

측정 단계는 **WSL2 전용**이다(netns · veth · netem 을 쓴다).

```bash
python pq_afec/experiments/loop2.py --status    # 단계별 상태
python pq_afec/experiments/loop2.py             # 전체 파이프라인
```

원자료는 `pq_afec/experiments/results/*.json` 에 있고, **보고서의 모든 숫자가 여기서 나온다.**
