## 연구 요약

ML-KEM이 ClientHello를 크게 만들면 QUIC의 증폭 제한에 사용할 수 있는 수신 바이트도 늘어난다. 이 연구는 인증서 크기와 손실 조건에 따라 그 변화가 핸드셰이크 시간에 미치는 영향을 측정하고, 패딩 증가량과 패리티 수를 고르는 정책을 검증한다.

제자리 FEC의 용량 조건 `C ≤ (k−1)(W−h−f)`는 측정한 12개 설정에서 성립하지 않았다. 이는 데이터그램 수와 크기를 고정한 첫 비행의 결과다.

quic-go v0.61.0에서 `InitialPacketSize`를 1280에서 1281로 올린 과거 측정은 특정 인증서 조건에서 약 1 RTT의 감소를 보였다. 증가량은 데이터그램당 1 B다. X25519(k=1)는 총 1 B, X25519MLKEM768(k=2)는 총 2 B를 더 보냈다. 패킷 단위 올림 모형은 해당 구현의 관찰이며, RFC가 송신량을 수신량의 3배보다 크게 허용한다는 뜻은 아니다. [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1).

팀 자료의 버스트 손실률 표기와 단방향·양방향 설정에는 이전 코드와 문서 사이의 불일치가 있다. 해당 README의 데이터 주의를 확인해야 한다. 유의한 차이를 찾지 못한 결과만으로 두 방식이 동등하거나 기존 연구 전제가 기각됐다고 단정할 수 없다.

## 실행

측정은 Windows와 WSL Ubuntu에서 실행한다. 실험별 조건과 한계는 [PADFEC 명세](pq_afec/docs/PADFEC%20v2%20명세.md)와 [팀 측정 README](mlkem-quic-amplification/README.md)에 있다.

`pq_afec`에는 측정 원자료까지 들어 있다. `results/*.json`에 여러 날짜의 결과가 함께 있으므로 실행 기록과 소스 지문을 같이 봐야 한다. v3.0~v3.2 폴더에는 판정 파일과 봉인에 들어간 결과만 있고, 측정 원자료(`experiments/state/`의 저널)와 그림은 없다. `pq_afec_gen33`에는 검증 묶음 `g3/v33/validation` 가운데 기본 시험이 불러오는 분석 스크립트와 `M1_stage2_validation`만 있다. 그래서 M1 wire 관문은 이 저장소만으로는 돌지 않는다.

gen-2 최종 상태의 근거는 `pq_afec/experiments/state/fixloop_triage.json`과 `loop2.json`의 p16 history다. p6은 과거 done이지만 마지막 분류가 stale이므로 현재 통과 수에 넣지 않았다.

## 2026-11-08 정리

모든 코드에서 주석과 docstring을 지웠다. 셸 heredoc 안에 든 스크립트와 Go 코드를 문자열로 담은 패치 스크립트, git 설정 파일(`.gitattributes`, `.gitignore`)의 주석도 지웠다. 지우기 전 커밋은 `4f26a51`(태그 `pre-cleanup-2026-11-08`)이다. 지운 뒤에도 동작이 같은지는 언어별로 확인했다. 파이썬은 AST, Go는 토큰열, 셸은 bash가 다시 출력한 함수 본문, C는 gcc 전처리 결과, PowerShell은 파서 토큰열이 지우기 전과 같다.

연구 내용이 아닌 작업용 문서도 지웠다. 작업 인계 메모, 할 일 목록, 반복 작업의 과제 카드·결정 장부·일지, 저장소 게시 절차 같은 것들이다. 남은 문서가 이 파일들을 출처로 적은 곳은 링크 없이 이름만 남아 있고, 원문은 `4f26a51`에 있다.

문서의 제목과 본문 문장도 다듬었다. 줄표, 이모지, 굵게 표시를 걷어 내고 숫자와 조사의 띄어쓰기를 고쳤으며, 제목에 붙어 있던 부제와 작업 반복 번호를 뺐다. 수치, 표의 값, 인용, 코드 블록은 그대로다. 봉인 문서와 체크섬으로 보존한 사본은 손대지 않았다. 그래서 다른 문서가 동결 세대 문서의 문장을 행 번호로 인용한 곳은 `4f26a51`의 문서 기준이다.

봉인(`SEAL_*.json`)과 측정 기록에 적힌 소스 해시는 주석이 있던 바이트의 해시다. 그래서 봉인은 `4f26a51`의 바이트로 확인한다. 아래 명령은 기본값으로 그 커밋을 읽는다. `--worktree`를 붙이면 현재 파일을 읽고, 이때는 주석을 지운 파일 39개가 불일치로 나온다.

```powershell
python -I -B tools/verify_seals.py
```

같은 이유로 소스 해시를 직접 대조하는 시험 15개는 현재 커밋에서 실패한다. `pq_afec_gen3`과 `pq_afec_gen31`의 `tests/test_g3_m1confirm.py`에서 5개씩(봉인된 측정 실행기가 봉인과 다른 코드로는 시작하지 않는다), `pq_afec_gen33`의 `test_v33_j1_candidate.py`, `test_v33_j6_candidate.py`, `test_v33_l2_candidate.py`, `test_v33_l3_candidate.py`, `test_v33_l5_candidate.py`에서 하나씩이다. 나머지 시험 결과는 주석을 지우기 전과 같다. 보고서 수치 검사 `pq_afec_gen33/report_repro/check_report_numbers.py`도 정책 소스의 해시가 바뀌어 6항목을 stale로 적는다. 이 검사는 저장소 밖 원자료를 읽어야 해서 원래도 이 저장소만으로는 끝까지 통과하지 않는다. 봉인된 실행기를 다시 돌리거나 측정을 재현하려면 `4f26a51`을 체크아웃해서 쓴다.

문서에 적힌 `파일:줄` 위치는 주석을 지운 뒤의 줄 번호로 고쳤다. 원문 그대로 보존한 감사 기록 사본(`pq_afec_gen33/docs/loop_record`, `pq_afec_gen33/g3/v33/evidence`)은 체크섬이 바이트 동일을 보증하므로 고치지 않았고, 그 안의 줄 번호는 작성 당시 코드 기준이다.
