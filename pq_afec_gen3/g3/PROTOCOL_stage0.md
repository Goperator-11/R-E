# PAD-FEC v3 0단계 프로토콜: 기제 확인 (고정 팔)

작성 2026-10-02. 근거 문서는 `C:/dev/codex_handoff/state/evo/verdict_v3.md`이고, 이 파일의 조건, 팔, 표본 수, 1-RTT 기준, 판정 규칙 M1~M4, 실패 분기는 그 문서 4.2절을 그대로 옮겼다. 4.1절 공통 규칙과 3절 A단계의 구현 지시도 함께 적용한다. 판정문에 없는 세부 중 이 파일이 새로 정한 것은 8절에 따로 모았다.

예측값은 `g3/stage0_predictions.json`에 있고 `padfec3/layout.py`(J3, 판정문 2.3절)로 계산했다. 세 파일의 SHA-256은 `g3/SEAL_stage0.json`에 있다. 봉인 뒤에 이 세 파일 중 하나라도 바뀌면 봉인은 무효다.

## 1. 목적

0단계는 v3의 이득을 주장하기 전에 기제 세 가지가 실제로 동작하는지 고정 팔로 확인한다.

1. 선행 신용 데이터그램이 여러 개(ℓ≥2)여도 서버의 증폭 신용으로 계상되는가(M1).
2. 둘째 비행의 선행 패리티와 버퍼 대기(F2)를 없애면 2-RTT 연결이 짧아지는가(M2).
3. RTT200 15%에서 선행 신용을 둘로 늘리면 gen-2의 단일 선행 신용 약점이 줄어드는가(M3).

M4는 판정이 아니라 귀속 보고다.

## 2. 공통 망 설정

- 그룹 X25519MLKEM768, 첫 비행 데이터그램 k=2, W=1280 B, δ=0. 패리티 크기는 W+39+6k = 1,331 B다.
- 망 설정은 p17과 같다. netem rate는 업링크에만 걸고 손실은 클라이언트→서버 방향에만 건다(판정문 0절 6). 손실은 독립(버스트 없음)이다. 지연은 p17 `set_netem(rtt/2, ...)` 방식이다.
- 서버는 두 포트 방식으로 띄운다. 같은 netns에 동결 gen-2 서버와 g3 서버를 다른 포트로 두고, gen-2 팔은 gen-2 서버에, g3 팔은 g3 서버에 붙인다(판정문 1절 판정의 "두 포트 서버 방식", 3절 A단계의 서버 포트 인자).
- 바이너리 경로는 판정문 3절을 따른다. gen-2는 `/tmp/qamp_g3/g2/qamp`(동결 sha256 d98b05d73f44774ad622ab1c4993526cac58957b22310fc61122d7bd44964213의 복사본), g3는 `/tmp/qamp_g3/g3/qamp`다. 빌드 경로는 `~/quicbed_g3`, 작업 경로는 `WORK=/tmp/padfec_g3`, `PADFEC_GEN=g3eval_20261002`다.

## 4. 팔

| 팔 id | 바이너리 | 클라이언트 플래그 | 첫 비행 송신 순서 | 이후 비행 |
|---|---|---|---|---|
| v2-m1 | gen-2 동결 | `-fec fec -m 1` | O O P | gen-2 그대로 |
| v2-m3 | gen-2 동결 | `-fec fec -m 3` | P0 O O P1 P2 | gen-2 그대로(선행 P0, 300 µs 대기) |
| v3tr-m3 | g3 | `-fec fec -m 3 -layout v3 -lead 1` | L0 O O P1 P2 | v3 규칙 |
| 신용전용 ℓ2 (credit-only-l2) | g3 | `-fec fec -m 2 -layout v3 -lead 2` | L0 L1 O O | v3 규칙(뒤따르는 패리티 0개) |
| 신용전용 ℓ3 (credit-only-l3) | g3 | `-fec fec -m 3 -layout v3 -lead 3` | L0 L1 L2 O O | v3 규칙(뒤따르는 패리티 0개) |
| m4L1 | g3 | `-fec fec -m 4 -layout v3 -lead 1` | L0 O O P1 P2 P3 | v3 규칙 |
| m4L2 | g3 | `-fec fec -m 4 -layout v3 -lead 2` | L0 L1 O O P2 P3 | v3 규칙 |
| m4L3 | g3 | `-fec fec -m 4 -layout v3 -lead 3` | L0 L1 L2 O O P3 | v3 규칙 |

- v3 규칙은 공통 명세를 따른다. 첫 비행과, 1,200 B 이상 서버 데이터그램을 받기 전의 Initial 재전송 비행은 위 순서로 보낸다. 그 밖의 비행은 원본을 쓰는 즉시 보내고, flush 때 뒤따르는 패리티를 최대 min(m-ℓ, 1)개 붙인다(헤더 lead=0, m=1). 선행 패리티는 없다.
- g3 팔의 패리티 헤더는 fecVer 3이고 m 바이트에 (ℓ<<4)|m을 싣는다. g3 서버는 index < ℓ인 패리티를 즉시 스택에 넘기고 복구에 쓰지 않는다.
- `-fec fec`와 `-fec on`은 같은 모드다(동결 gen-2 소스 qamp.go L3115, g3 소스에서도 같은 분기). 클라이언트에 `-ips`는 주지 않는다(p17과 같음, W=1280).
- m4 팔은 g3 바이너리에서 고정 `-m 4`가 허용되어야 한다. auto 정책의 기본값은 바꾸지 않는다.

## 6. 지표

- 1-RTT 기준은 HCT < 1.5·RTT + τ(결정 전 바이트)다(판정문 4.2).
  - 결정 전 바이트는 송신 순서상 마지막 원본까지의 바이트, 즉 ℓ·1,331 + 2·1,280이다. v2-m1은 2,560 B, ℓ=1 팔은 3,891 B, ℓ=2 팔은 5,222 B, ℓ=3 팔은 6,553 B다.
  - τ(b) = 8b/(1000·u) ms이고 u는 업링크 Mbps다. 2 Mbps에서 위 바이트는 각각 10.24, 15.564, 20.888, 26.212 ms다.
  - 각 표의 "1-RTT 기준" 열이 이 값이다.
- 일차 지표는 계획한 모든 시도의 평균 HCT다. 실패한 시도는 클라이언트 timeout 10 s(10,000 ms)로 대입한다(판정문 4.1, p17 run_client timeout_s=10). 결과 행이 없는 시도(클라이언트 비정상 종료 등)도 실패로 보고 같은 값을 대입한다.
- 1-RTT 비율의 분모는 계획한 시도 수다. 실패했거나 행이 없는 시도는 1-RTT가 아닌 것으로 센다. 예측은 timeout을 모형화하지 않는다. 참고로 p20_residual.json의 같은 p17 조건 팔들은 n이 모두 2,250으로 계획 수(450×5)와 같다.
- 함께 보고할 것(판정문 4.1): 팔별 연결당 업링크 바이트, 1-RTT 비율, timeout 수, CRC 실패 0, 회계 위반 0, reused_units 0, 실행 중 소스 해시 불변. 성공 시도만의 평균 HCT도 함께 적는다.
- M1의 셋째 항목을 위해 g3 서버 통계에서 m4L3 연결의 선행 데이터그램(index < ℓ)이 스택 인계로 계상되었는지를 본다.

## 7. 판정 규칙 (판정문 4.2 그대로)

M1 (다중 선행 신용). 큰cert 2%에서 아래 셋을 모두 만족해야 한다.
- m4L3의 1-RTT 비율 ≥ 0.85. 예측 0.940.
- (m4L3 평균) - (v2-m1 평균) ≤ -18 ms. 예측 -36.5 ms.
- 서버 통계에서 선행 ℓ개가 모두 스택 인계로 계상됨. 모형 예측값이 아니고, ver-3 서버 규칙(index < ℓ는 즉시 스택 인계)이 동작하면 참이어야 한다.
  - 판정법(2026-10-02 10:05 KST 보완, 측정 전): m4L3의 구간마다 (g3 서버가 받은 패리티 수 - 그중 신용으로 스택 인계한 수) ≤ (클라이언트가 보낸 패리티 수 - 첫 비행에서 보낸 선행 데이터그램 수)이고, g3 서버의 `credit_parities_v3`가 `credit_parities`와 같으며, 클라이언트 행의 layout·lead 값이 팔 설정과 어긋난 경우가 0이어야 한다. 클라이언트 비정상 종료나 행 누락이 있는 구간은 이 검사에서 뺀다. 러너 `experiments/g3_stage0.py`의 `lead_credit`과 `mechanism_checks`가 이 정의다. 신용전용 ℓ3의 `credit_parities == parities`는 판정이 아니라 보조 자료로 보고한다. 서버 연결별 `beff_credit`(서버 첫 송신 전에 스택 인계된 신용 수)도 보조 자료로 함께 적는다.

M2 (F2). 큰cert 2%에서 (v2-m3 평균) - (v3tr-m3 평균)이 2.8~11.2 ms 안에 있어야 한다. 예측 5.60 ms.

M3 (신용 중복). RTT200 15%에서 (v2-m3 평균) - (m4L2 평균)이 11~44 ms 안에 있어야 한다. 예측 22.3 ms의 0.5~2배다. 이번 계산의 예측은 22.32 ms다.

M4 (귀속, 판정 아님). (m4L3 평균) - (신용전용 ℓ3 평균)을 FEC 몫으로 보고한다. 예측은 큰cert 2%에서 -4.06 ms(FEC 몫 4.06 ms), 큰cert 15%에서 -41.11 ms(FEC 몫 41.11 ms)다. 판정문의 투영 "2%에서 약 4 ms, 15%에서 약 41 ms"와 같다.

실패할 때의 분기(미리 고정):
- M1 실패: ℓ≥2를 철회한다. v3는 레거시 배치 + F2 + 학습으로 줄어들고, 큰 이득 주장도 철회한다.
- M2 실패: F2 주장을 철회하고 τ(W) 항을 끈다.
- M3 실패: RTT200을 S에서 D로 내린다.

## 8. 판정문에 없어서 이 파일이 정한 것

판정문 3절은 0단계 러너가 "p17 run_interleaved 구조"를 쓴다고만 적었다. 구간 크기와 회전 규칙은 판정문에 없으므로 아래와 같이 정한다. 러너(`experiments/g3_stage0.py`)는 이 규칙을 따르고, 러너 소스 해시를 측정 전에 따로 남긴다.

- 조건은 3절 표의 순서로 하나씩 끝낸다. 조건마다 두 서버를 띄우고 netem을 건 뒤, 그 조건의 모든 사이클을 돌리고 서버를 내린다. netem은 p17처럼 사이클마다 다시 건다.
- 한 사이클 안에서 팔마다 한 구간씩 돌린다. 구간은 팔당 40연결이다. n이 400인 신용전용 ℓ2(RTT200 15%)는 구간 20연결로 모든 사이클에 들어간다.
- 사이클 수는 n/40이다. 큰cert 2%는 10사이클, 나머지 조건은 20사이클이다.
- 사이클 c(0부터)의 팔 순서는 5절 표의 팔 순서를 c mod (팔 수)만큼 회전한 것이다(p17 run_interleaved의 `ARMS[r:] + ARMS[:r]`). 큰cert 2%(팔 5개, 10사이클)와 RTT200 15%(팔 5개, 20사이클)는 방격이 닫힌다. 큰cert 15%(팔 6개)와 2Mbps 15%(팔 3개)는 20사이클이 팔 수의 배수가 아니라 자리 균형이 완전하지 않다.
- 연결 간격은 50 ms(p17 unit_key의 rate>0 값), 연결당 timeout 10 s, expect-k 2, parity-delay 기본값 300 µs다. 고정 팔이므로 `-cache`, `-probe-every`는 쓰지 않는다.
- 두 서버는 p17과 같이 `-mode server -fec on -certsize <cert>`로 띄우고 `-feedback`은 주지 않는다. 통계 파일은 서버마다 따로 둔다. 클라이언트에는 모든 팔에 p17과 같은 `-uplink-mbps 2`를 준다. 이 값은 auto 정책만 읽으므로 고정 팔의 동작은 바뀌지 않는다.

## 9. 봉인과 진행 규칙

- 측정 전에 `g3/SEAL_stage0.json`의 해시를 다시 계산해 대조한다. 판정문 4.1이 요구하는 나머지 고정 대상(개발 자료 목록, 두 바이너리, g3 소스)의 해시는 이 봉인 밖에서 따로 남긴다.
- 계획한 블록이 끝나기 전에는 결과를 보지 않고, 중간에 멈추지 않는다. 실패한 검사는 실패로 둔다.
- 측정 뒤 g3를 고치면 그 0단계 자료는 개발 자료로 강등하고 새로 확증 실행을 한다.
- gen-2의 판정(17 통과, 7 실패)은 그대로 둔다.
