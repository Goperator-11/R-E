# pq_afec: QUIC 핸드셰이크 Initial 비행 FEC (정도현)

R&E 「ML-KEM 적용 시 전송 성능 개선을 위한 QUIC 기반 적응형 FEC 연구」에서
알고리즘, 구현, 실측을 맡은 부분이다. 팀 자료(`../mlkem-quic-amplification/`)와 짝을 이룬다.

---

## 검증 범위와 결과 해석

이 구현은 quic-go v0.61.0에서 클라이언트의 첫 Initial 비행을 보호하는 연구용 테스트베드다. 패딩 증가량 δ와 추가 패리티 수 m을 함께 고른다.

실측한 12개 설정은 `C ≤ (k−1)(W−h−f)`를 만족하지 않아서, 데이터그램 수와 크기를 그대로 둔 채 제자리에서 1개 소거를 보호할 수 없었다. 다른 패킷 배치나 다른 설정에서도 불가능하다는 뜻은 아니다.

`InitialPacketSize`를 1280에서 1281로 올린 과거 측정에서 X25519는 약 51.98 ms, X25519MLKEM768은 약 50.86 ms 짧아졌다. 추가량은 데이터그램당 1 B다. 첫 비행이 k개면 총 추가량은 k B이고, 아래 ML-KEM 실험(k=2)은 총 2 B를 추가했다. `1350`과 비교하면 데이터그램당 1 B 대 70 B다.

`A(B)=ceil(3B/P)·P`는 이 테스트베드의 패킷 단위 송신 동작을 설명하는 모형이다. RFC의 송신 한도는 주소 검증 전 수신량의 3배이고([RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1)), 이 모형의 올림은 RFC가 허용한 추가 예산이 아니다. 다른 QUIC 구현에서 같은 경계나 시간 이득이 나오는지는 재현하지 않았다.

정본 명세는 [PADFEC v2 명세](docs/PADFEC%20v2%20명세.md)다. 아래에서 날짜가 붙은 표는 그날 실행한 기록이므로, 코드를 고친 뒤 새로 잰 값으로 읽으면 안 된다.

## 결과

### 1. 1바이트 절벽 (v2 헤드라인)

```
A(B) = ceil(3B/P)·P ,  P = 1280       Δ_min = floor(A(B)/3 − B) + 1
W = 1280 = P  ⟹  3B = 3k·1280 은 항상 P 의 배수  ⟹  Δ_min = 1   (k 무관)
```

인증서 크기를 두 예측 임계 사이에 고정하고 `ips`만 바꿨다(RTT 50 ms, 손실 0, n=40).

| 그룹 | `ips=1280` | `ips=1281` | 차이 |
|---|---|---|---|
| x25519 (k=1), cert 4,000 | 104.838 ms (2-RTT) | 52.854 ms (1-RTT) | 51.98 ms = 1.040 RTT |
| X25519MLKEM768 (k=2), cert 6,500 | 104.899 ms (2-RTT) | 54.044 ms (1-RTT) | 50.86 ms = 1.017 RTT |

부정 시험도 통과했다. `1279 ≡ 1280`(같은 칸)이고 `1281 ≡ 1350`이다. 데이터그램당 1바이트를 더한 쪽이
70바이트를 더한 쪽과 같은 칸에 도달한다는 뜻이다. 연속 3배 모형으로는 원리상 이 결과가 나올 수 없다.

### 2. 측정한 자연 비행에서는 제자리 보호가 불가능하다

```
제자리(바이트 중립) 1-소거 보호 가능  ⟺  C ≤ (k − 1)(W − h − f)
```

k=1이면 우변이 0이므로 데이터그램이 하나뿐인 비행은 원리상 보호할 수 없다.
실측한 12개 설정은 모두 이 부등식을 어겼고, 가장 가까운 설정(ML-KEM/Initial 1450)도 76.0 B를 넘었다.
`f=0`으로 잡아도 60.0 B를 넘으므로 결론은 꼬리표 크기에 좌우되지 않는다.

> 이 부등식은 Singleton/MDS 한계에 QUIC 상수를 대입한 것이라, "정리"로 내세우면 반박당한다.
> 이 절에서 내세울 것은 실측 상수로 60~76 B가 모자란다는 부정 결론이다.

### 3. s0는 상수가 아니다

서버 첫 비행의 고정분 `s0`에는 서버 패킷 수에 비례하는 항이 있다.
임계 역산과 서버 바이트 직접 계수, 두 방법이 각각 독립적으로 상수 모형을 기각한다.

| 방법 | x25519 | X25519MLKEM768 |
|---|---|---|
| 임계 역산 | 34.5 B/패킷 | 34.5 B/패킷 |
| 서버 바이트 직접 계수 | 36.1 | 40.0 |
| 평균절대오차 (상수 → 패킷항) | 224.5 → 112.4 B | 144.2 → 101.8 B |

### 4. 신용과 복구는 하나의 패리티로 동시에 못 얻는다

증폭 신용은 패리티가 복호 가능한 마지막 패킷보다 먼저 와야 생긴다
(quic-go `connection.go:669`의 `if !wasProcessed { continue }`).
반면 손실 복구에서는 복구본을 넣는 대신 패리티를 버려야 회계가 맞는데,
이 판단은 패리티가 원본들보다 뒤에 와야 옳게 내릴 수 있다.

두 요구가 정반대라서 배치를 m에 따라 나눴다. `m=1`이면 `[원본…, 패리티]`로 패리티가 복구를 맡고,
`m≥2`이면 `[패리티0, 원본…, 패리티1]`로 앞 패리티가 신용을, 뒤 패리티가 복구를 맡는다.

## 2026-08-20 감사와 수리

알고리즘 전체를 반증 시험으로 감사했다. 수학층, 부호층, 채널층에서는 결함이 0건이었다.
`A(B)`는 독립 구현과 전수 대조했고, RS의 MDS 성질은 모든 소거 패턴으로 확인했고,
GE의 DP는 40만 시행 몬테카를로와 대조했다. 결함 4건은 모두 v2 비용식 층 한 곳에
몰려 있었고, 넷 다 고쳤다.

| # | 틀린 것 | 증거 | 수리 |
|---|---|---|---|
| 1 | 한 비용식에 손실 모형이 둘(왕복항은 독립 이항, 실패항은 Gilbert-Elliott) | 버스트를 1→5로 바꾸면 `p_fail`은 6.6배가 되는데 `n_exp`는 소수점 6자리까지 그대로 | `joint_arrival_pmf` 하나에서 두 항을 뽑는다 |
| 2 | 같은 손실 사건을 두 항에서 각각 청구 | m=0·k=1·p=0.2에서 `60 + 10 = 70 ms`(참값 60) | 왕복항은 복구 성공 상태에만 붙이고, 실패는 `(RTT + T_recover)` 한 번 |
| 3 | Python과 Go가 다른 m을 고름 | `policy.go`가 버스트를 `1.0` 리터럴로 박아 둬서 90조건 중 17건 불일치 | 버스트를 인자로 흘리고, 결합분포를 표로 심고, `pfailTable`(둘째 출처)을 삭제 |
| 4 | 순위·설명문이 틀린 바이트 수를 인용 | 패리티를 `W`로 세서 m=1에서 38 B, m=2에서 76 B 어긋남 | 후보 생성 단계부터 실크기 `W+32+6k`를 주입 |

- 결함 1·2·3은 뿌리가 같다. `n_rtt` 항과 `p_fail` 항이 서로 다른 확률공간에서
  왔는데 한 식에서 더해졌다.
- 헤드라인 결과는 영향을 받지 않는다. `p=0`이면 실패 확률이 0이라 새 식이 옛 식으로
  정확히 환원된다(자체시험 6). 1바이트 절벽과 용량 부등식은 순수 산술이고
  전수 검증을 통과했다.
- 결정이 실제로 바뀐 곳은 290개 조건 중 5건(1.7%)이다. 모두 필요 없는
  1,318 B 패리티를 사던 자리다.
- Python↔Go 대조에서 2,688 격자점 중 고르는 m이 다른 곳은 0건이었다(수리 전 19%).
  표를 `%.17g`(float64 왕복 정밀도)로 찍어서 두 구현이 비트 단위로 같다.
- 같은 결함이 되살아나지 않도록 `python -m padfec.policy`에 자체시험 13종을 넣었다.
  하나라도 실패하면 그 결함이 돌아온 것이다.

```bash
python -m padfec.policy     # 19 checks
python -m padfec.quantum    # 39 checks
```

### `T_recover` 실측 보정

무작위 손실로는 차이가 드러나지 않았다(24조건에서 옛/새 비용식 RMSE 6.543 대 6.548로 구분 불가).
그래서 측정 경로를 바꿨다. `-drop-initial 0`으로 매 판 첫 비행을 결정적으로 버리면
모든 표본이 손실 사건이 된다.

| RTT | k=1 | k=2 |
|---|---|---|
| 10 ms | 200.90 ms (20.09×) | 12.62 ms (1.26×) |
| 50 ms | 200.96 ms (4.02×) | 57.77 ms (1.16×) |
| 100 ms | 200.73 ms (2.01×) | 113.88 ms (1.14×) |
| 판정 | 고정 상수 | RTT 비례 |

결과를 가르는 것은 k 자체가 아니고, 실패한 순간 서버가 하나라도 받았는지다. 받은 것이 0개면
ACK가 없어 PTO(경로와 무관하게 200.86 ms)를 기다리고, 1개 이상이면 ACK로 구멍이 드러나
즉시 재전송한다(1.125·RTT + 1.42). 결합분포가 이미 두 경우를 구분하므로 `p_fail`을
`p_fail_pto` / `p_fail_ack`로 쪼개 각각 값을 매긴다.

검증 결과(`results/probe_trecover_verify.json`, x25519·k=1·cert 1,000·RTT 10 ms·n=300):

| 손실 | 실측 `off` | 옛 예측 | 새 예측 | 실측 `m=1` |
|---|---|---|---|---|
| 2% | 14.656 ms | 10.20 (−4.46) | 14.02 (−0.64) | 12.170 |
| 5% | 22.459 ms | 10.50 (−11.96) | 20.04 (−2.42) | 12.128 |

- 예측 오차가 각각 7.0배, 4.9배 줄었다.
- 옛 기본값은 두 조건 모두에서 `off`를 최적으로 골랐는데, 실측으로는 가장 나쁜 팔이다.
- 꼬리 분포에도 흔적이 있다. 손실 5% `off`의 p95가 211.2 ms인데, 이것이 앞에서 본 201 ms PTO다.
- FEC가 실제로 복구한다는 직접 증거도 나왔다. 결정적 소거에서 패리티 m=1을 쓰면
  252.09 ms → 52.31 ms(기준선 +1.04 ms)가 된다.

2026-08-20 당시 Python↔Go 대조는 2,688 격자점에서 불일치 0건이었고 자체시험은 19종이었다.

## 2026-08-20 v2 정책 Go 이식

폐루프(`-fec auto`)의 결정은 Go 안에서 내려진다. 그런데 v2에서 결정 변수가 둘
(δ·m)이 된 뒤에도 Go는 m만 골랐다. 헤드라인인 "1바이트로 왕복 하나 사기"는
사람이 `-ips`를 손으로 줄 때만 실현됐고, 정책이 스스로 그것을 고른 적은 없었다.

이식한 것은 후보 생성(`levers`)과 순위(`evalCands`)다. 확률 모형은 옮기지 않았다.
`padfec/table.py`가 검증된 Python 모형에서 결합분포를 표로 뽑아 심고, Go는 그 표를 조회만 한다.
옮긴 것이 정수 산술뿐이라 갈라질 여지가 없다고 가정했는데, 실제로는 한 곳이 갈라졌다.

> `ceilDiv`: Python `-((-a) // b)`는 `//`가 내림이라 올림이 되지만,
> Go `/`는 0 쪽으로 절사하므로 그대로 옮기면 내림이 된다. `ceilDiv(161,2)`가
> 81이 아니라 80이 나왔다. 칸이 한 칸씩 낮게 잡혀 δ 후보가 통째로 쓸모없어졌고,
> 이 문제는 5,670 격자점 중 92건의 불일치로 드러났다.

그래서 격자 대조를 관문에 상설로 붙였다(`experiments/gate_go_parity.py`).
격자의 정본은 Go 쪽(`policy.go`의 `policyGrid`)이고 Python이 그 출력을 따라간다.
양쪽에 목록을 따로 적으면 언젠가 갈라지기 때문이다.

- 대조 대상은 (mode, δ, m, InitialPacketSize) 네 개 전부다. 예전에는 m 하나였다.

### 정책 수렴 실측

격자 대조가 말해 주는 것은 두 구현이 같은 답을 낸다는 것뿐이다. 그 답이 실제 경로에서
효과가 있는지는 테스트베드에서 따로 쟀다(`_probe_v2converge.py`,
x25519 · cert 4,032 · RTT 50 ms · 무손실 · 라운드당 400 연결, 빈 캐시에서 시작).

| 라운드 | p 추정 | 평상시 선택 | ips 분포 | p50 |
|---|---|---|---|---|
| 1 | 0.0377 | `parity` m=2 | 1280: 388 / 1281: 12 | 52.35 ms |
| 3 | 0.0118 | `parity` m=1 | 1280: 380 / 1281: 20 | 52.40 ms |
| 6 | 0.0073 | `parity` m=1 | 1280: 380 / 1281: 20 | 52.41 ms |
| 7 | 0.0050 | `pad` δ=1 | 1280: 106 / 1281: 294 | 51.33 ms |
| 8 | 0.0050 | `pad` δ=1 | 1281: 400 | 51.29 ms |

8라운드째에는 400판 전부가 ips=1281, 패리티 0개였다. 사람이 손으로
`-ips 1281`을 준 팔(51.25 ms)과 사실상 같은 결과이고, 패리티 1,318 B를 사던
자리를 1바이트로 대체했다. 정책이 헤드라인 결과를 스스로 실현한 것은 이것이 처음이다.

> 주의: 여유가 1.42배뿐이다. `pad`가 `parity`를 이기려면 p < 0.00703이어야
> 하는데, 추정기(Jeffreys 사후평균 + 감쇠 0.99)가 무손실 경로에서
> 도달하는 하한이 0.00495다. 지금은 문턱을 넘어가지만, 감쇠나 탐색 주기를 조금만
> 바꿔도 영영 넘어가지 못한다. 그래서 `_probe_v2converge.py`는 측정값과 함께
> 이 두 수를 찍는다. "아직 안 넘어갔다"와 "영영 안 넘어간다"는
> 측정만 보면 똑같아 보이지만 처방은 정반대다.
>
> 6라운드까지 `parity`를 고른 것은 정책의 잘못이 아니다. p=0.0073이면
> 패리티가 실제로 옳은 선택이다. `pad`는 복구를 주지 않아서 손실이 한 번 나면
> PTO 201 ms를 물어야 한다. 결정 규칙은 맞았고, 추정값이 아직 참값에서 멀었을 뿐이다.

이 작업으로 탐색(무방비 관측)을 δ 후보로 보낼 수 있게 됐다.
손실률은 `m=0`인 연결에서만 편향 없이 관측되는데, 예전에는 `m=0` 후보가 맨몸
하나뿐이라 임계 위에서는 탐색 한 번이 곧 2-RTT였다. 그 비용 때문에 탐색 주기가
늘어나 400 연결에 무편향 관측이 3회뿐이었고, `p`가 Jeffreys 사전값(0.126)에
머물렀다. δ는 복구를 주지 않으므로 관측을 편향시키지 않는다. 그래서 이제는
가장 싼 `m=0` 후보로 탐색한다.

## 2026-08-26 증폭 신용의 경주

위 4절("신용과 복구는 하나의 패리티로 동시에 못 얻는다")은 패리티 배치를 정한
근거였다. 그런데 비용 모형은 그 배치의 결과를 바이트로만 세어, 패리티 m개의 바이트를
무조건 증폭 예산에 넣었다. 바이트 회계로는 맞지만 도착 시각이 빠져 있었다.

서버는 복호 가능한 마지막 패킷을 처리할 때 보낼지를 정한다. 패리티는 복호가
안 되므로 송신을 깨우지 못한다. 그래서 뒤따르는 패리티(m=1의 유일한 패리티,
m≥2의 index 1..)의 바이트는 예산에 들어가더라도 그 결정보다 늦게 오면 그 연결에서는
쓸모가 없다. 대역이 제한되면 늦어지는 정도가 곧 직렬화 시간이다.

    d = 패리티 바이트 / 업링크 대역

### 경주 측정

`experiments/`의 임시 탐침으로 전이 구간을 9점 훑었다
(cert 9000·k=2·RTT 50 ms·손실 0%·gap 50 ms·팔당 250 연결).
손실 0으로 재면 모형의 `p_two_rtt`가 0이므로 m1의 1-RTT 비율이 곧 q(d)다.

| 업링크 | 무제한 | 80 | 40 | 30 | 20 | 15 | 10 Mbps |
|---|---|---|---|---|---|---|---|
| 도착지연 d (ms) | 0 | 0.133 | 0.266 | 0.355 | 0.533 | 0.710 | 1.066 |
| m=1이 1-RTT | 1.000 | 0.996 | 0.972 | 0.640 | 0.404 | 0.212 | 0.004 |
| m=2가 1-RTT | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |

m=2가 어느 대역에서도 100%인 것은 4절의 배치와 맞는다. 앞선 패리티는 원본보다
먼저 나가므로 경주 자체가 없다. 흔들리는 것은 뒤따르는 패리티뿐이고, 문턱은
`d ≈ 0.3 ms`(서버의 송신 결정 지연) 근처다.

지수꼴과 정규꼴을 맞춰 봤지만 평평한 머리와 꼬리를 동시에 맞추지 못했다(정규꼴은
`d=0.133`에서 0.86, 실측 0.996). 그래서 표로 심고 선형보간한다.
확률표를 Go에 심는 것과 같은 이유다(`padfec/table.py` 머리말).

### 모형 변경

`flight_outcome`이 상태를 셋으로 가른다. (1) 복구가 일어난 상태에서는 서버가
복구용 패리티를 받아야 원본을 다 가지므로 경주가 없다. (2) 복구가 없으면
앞선 패리티만 결정적이고 뒤따르는 패리티는 `q(i·d)`로 갈린다. (3) 실패 상태는 그대로다.

대역이 무제한이면 `d=0`, `q=1`이 되어 옛 식과 비트 단위로 같다(자체시험 9b가
옛 식을 다시 적어 직접 비교하며, 최대 차이는 `1.11e-16`). 그래서 무제한 대역에서
이미 검증된 결과는 그대로 남는다.

| 2 Mbps·손실 2% | m0 | m1 | m2 | m3 |

| 실측 | 126.78 | 121.31 | 70.36 | 70.50 |
| 모형(전) | 100.36 | 53.01 | 55.51 | 55.45 |

### 관문과 p18의 사각지대

- Go↔Python 관문은 원리상 이 결함을 볼 수 없다. 관문이 재는 것은 같은 식의 두
  구현이 서로 같은지이고, 그 식이 테스트베드와 맞는지는 재지 않는다.
  둘이 똑같이 틀리면 관문은 통과한다.
- 바이너리가 낡으면 관문이 엉뚱한 곳을 가리킨다(2026-09-03 추가).
  관문은 빌드를 하지 않는다. `policy.go`·`pfail_table.go`를 고치고
  다시 빌드하지 않은 채 돌리면 어떻게 되는지는 외부 리뷰가 실제로 겪으면서
  알게 됐다. 08-29 `fcdd7a0`(반복 라운드 항 + p 축 정밀화) 이전 바이너리로
  돌리면 다음과 같다.

      격자점 178,200 · 진짜 불일치 5,016 건 · J 최대 46.09 ms
      (최악점 k=3 cert=12000 rtt=100 p=0.2875 L=4 up=10)

  다시 빌드하면 196,020점에서 불일치 0건이다. 관문은 조용히 통과하지 않고
  실패를 냈다. 위험한 것은 그 실패가 「진짜 불일치」라고 적혀 있어서
  모형 결함으로 읽힌다는 점이다. 그러면 멀쩡한 모형을 뜯어고치게 된다.
  열 수 검사(13개)로는 잡지 못한다. 그 변경은 열 수를 건드리지 않았다.
  `loop2.py`로 돌리면 `BED` 지문에 `.go`가 포함되어 있어 이 문제가 생기지 않으므로,
  무방비였던 것은 관문 단독 실행 경로뿐이었다. 이제 관문은 빌드 직전
  소스의 SHA-256을 `quicbed/build.sh`가 남긴 지문과 대조하고, 어긋나면
  격자를 읽기 전에 「모형이 아니라 빌드를 보라」고 알리며 종료한다.
- 격자만 넓히고 표를 그대로 두면 관문은 조용히 통과한다. 옛 바이너리가 더 적은
  점을 내고 그 점들은 다 맞으므로 「불일치 0 건」이 뜨고, 덮는 범위가 줄었다는
  사실은 어디에도 기록되지 않는다. `grid_points`는 결과에 남지만 그 수를 기대치와
  대조하는 코드는 없다. 지금은 위 지문 대조가 이 경우도 막지만,
  그 방어가 자가 지문 하나에 달려 있다는 뜻이기도 하다.
- `p18`은 그 축을 밟지 않았다. "고정팔 m=1..4 를 직접 재서 모형을 검증"하는
  단계인데 세 조건의 업링크가 모두 0(무제한)이었다. 모형이 틀린 곳은 대역이
  제한된 자리뿐이라 통과할 수밖에 없었다. 이번에 `("임계위·2Mbps", …)` 조건과
  m1−m2를 모형과 대조하는 검사를 넣었다.

- `c`의 정본값을 아직 정하지 못했다. 값은 34.5 ~ 40.0 B/패킷 구간에 있고,
  서버 데이터그램 수를 직접 세는 계측을 붙여야 확정된다.
- `p12c`(ips 1707·2134)는 영구히 불가능하다. veth MTU가 1500이고 quic-go가
  `InitialPacketSize`를 1452로 깎기 때문이다. x25519는 칸 3·4, ML-KEM은 칸 6·7 밖으로 나가지 못한다.
- 1바이트 절벽으로는 두 s0 모형을 구분하지 못한다. 상수 모형도 절벽을 맞히기 때문이다.
  절벽은 양자화의 증거일 뿐 패킷항의 증거는 아니다.
- 양자화는 곧 RFC 9000 §8.1 위반이다. quic-go의 `isAmplificationLimited()`는
  `bytesSent >= 3*bytesReceived`를 보는 불리언 게이트라서 마지막 패킷이 통째로 나가 3배를 넘는다
  (실측 ips=1200 → 3.20배, ips=1350 → 3.79배). 우리 설계는 그 위반에 기대고 있다.
- 단일 구현에서 관찰한 결과다. 양자화 상수 `P=1280`은 quic-go의 서버 패킷 크기라서
  다른 스택에서는 달라진다. quiche·ngtcp2에서는 재현하지 않았다.
- 폐루프의 후회는 기준 안에 들어왔지만, 그 오차막대는 믿기 어렵다.
  `p11`(v1 폐루프)의 수렴 후 최악 후회는 4.919 → 0.857 → 3.24 → (0.63 · 1.17)
  으로 움직였다. 값마다 뜻이 다르다. 4.919는 비교 팔에 m=3이 빠져 생긴
  판정불능의 흔적이고(결함 아님), 0.857은 그것을 고친 값, 3.24는 증폭신용
  수리 뒤의 회귀다. 다만 셋 다 `n=600`으로 잰 값이다.

  `--precise`(N=4000)를 두 번 돌렸고 둘 다 기준 2 ms를 통과했다(각각 9/9).

  | 실행 | 최악 후회(수렴 후) | 그 조건의 신뢰반폭 | 헤드라인 조건 |
  |---|---|---|---|
  | 2026-08-29 (커밋본) | 0.629 ms | ±0.429 | 임계위·손실 5% |
  | 2026-08-30 (작업본) | 1.173 ms | ±0.049 | 임계아래·무손실 |

  두 구간이 겹치지 않는다. 같은 코드, 같은 n인데 0.629±0.429와
  1.173±0.049가 만나지 않는다면 모자란 것은 표본이 아니라 오차막대 자체다.
  원인은 측정 순서였다. 08-30 판까지는 팔을 순차로 쟀다(m0 → m1 → m2 → m3 → auto.
  2026-09-07에 조건마다 서버 하나, 10블록 라틴 회전으로 교대 측정하도록 고쳤다).
  08-30의 헤드라인 조건에서 두 실행의 m 분포는 같은데(auto `{m0:100, m1:1900}`,
  m1 팔 `{1:2000}`) 팔 평균이 첫 팔 51.34 → 마지막 팔 52.51 ms로 한 방향으로
  표류했다. 08-29의 같은 조건은 51.72 → 51.74로 평평하다. 따라서 08-30의
  1.17 ms 중 대부분은 정책 후회가 아니라 기계 표류가 후회로 잡힌 것이고,
  오차막대는 팔 안의 표본분산만 담으므로 정의상 이 표류를 보지 못한다.
  처방은 표본을 늘리는 것이 아니라 팔을 교대(interleave)로 돌리는 것이다.
  그때까지 이 두 수가 말해 주는 것은 「2 ms는 넘는다」까지다.
  (같은 08-30 밤 자료에서 `p16`도 부하 흔적이 잡혀 09-01에 다시 쟀다.
  `p11`은 아직 다시 재지 않았다.)

- 후회의 분해는 같은 조건 안에서만 성립한다. 커밋본 헤드라인 조건에서
  0.6287 = 탐색세 0.5094 + 결정 규칙 자체의 후회 0.1193이다. 남은
  후회의 81%가 탐색세이고 결정 규칙이 지는 몫은 0.12 ms다.
  이 세 수를 다른 조건에서 뽑아 섞으면 안 된다. `worst_probe_tax_ms`
  (0.56)는 임계위·손실 2%의 값이고 `worst_ci95_half_ms`(0.486)는 임계아래·손실 5%의
  값이라, 헤드라인과 짝지으면 산수가 맞지 않는다(0.56+0.125 = 0.685 ≠ 0.63).
  `p11_adaptive.py`가 이 혼동을 주석으로 경고해 두었는데도(주석은 2026-11-08
  정리에서 지웠고 원문은 커밋 `4f26a51`에 있다) 실제로 한 번 일어났다. 인용할 때는 `worst_regret_late_ms`와
  `worst_regret_late_ci95_half_ms`를 반드시 쌍으로 쓴다.

- `s/√n`은 여섯 단계가 같이 쓰는 가정이다(계통 감사 2026-09-01).
  판정이 실제로 뒤집힌 곳은 `p16` 하나였고 고쳤다. `p11`은 여유가 0.78 ms라
  안전하지만(뒤집히려면 15배가 필요하다), `p15`의 보고 반폭은 1.25배 과소평가됐다
  (0.74 → 0.92, 여유 35% → 8%). 그 수를 보고서에 그대로 옮기면 정밀도를
  과장하게 된다. `p17`·`p18`·`p20`은 재실행 뒤 같은 자로 다시 잰다.

- 원자료가 커밋보다 앞서 있었다(2026-09-03에 해소). 위 08-30 `p11`을
  포함해 `results/*.json` 11개가 작업 사본에만 있어서, 커밋된
  `docs/다음 세션 인계.md`가 커밋되지 않은 파일의 수(1.17 ± 0.05)를
  인용하고 있었다. clone한 사람이 읽으면 문서와 원자료가 어긋났다.
  이번에 같이 커밋했다. README가 `results/*.json`에 대해 "보고서의 모든 숫자가
  여기서 나온다"고 적어 둔 이상, 측정이 끝나면 결과도 같이 커밋해야
  그 문장이 참이 된다. 지금 커밋된 `p11`은 위 표의 08-30 판(1.173 ±
  0.049)이고, 그 수에 계측 표류가 섞여 있다는 것은 바로 위에 적어 둔
  그대로다. 커밋했다고 표류가 없어지지는 않았고, 문서와 원자료가 같은 것을
  가리키게 됐을 뿐이다. 팔 교대 재측정은 아직 하지 않았다.
- 경주 문턱 `q(d)`는 이 기계에서 잰 값이다. 서버의 송신 결정 지연 분포라서
  기계와 부하에 따라 달라진다(`T_pto`·`c`와 같은 종류의 환경 상수다). 실제로 다른
  실험과 겹쳐 돌던 탐침은 `d=1.066 ms`에서 0.387을 냈고 한가한 기계에서는
  0.004였다. 정책이 밟는 자리는 `d≥1 ms`(대역 ≤10 Mbps, q≈0)이거나
  `d=0`(무제한, q=1)이라 선택은 바뀌지 않지만, 다른 기계에서는 다시 재야 한다.
- Go는 버스트 길이 L을 재지 못하고, 표에 심긴 가정값(`defaultAssumedBurst=1`)을
  쓴다. 경로가 버스트성이면 정책이 실패 확률을 낮게 본다.

## 선행연구와의 관계

- 아이디어 자체는 RFC 규범에 이미 있다. RFC 9002 §A.9 의사코드 주석에
  "Initial is padded to earn more anti-amplification credit"라는 문장이 있다.
- Fastly(McManus)가 "extra 200 bytes of padding will halve the handshake time
  for 7% of connections"라고 이미 적었다. 우리 기여는 왜 200이고 언제 1로 충분한지를
  닫힌 식으로 설명하는 것이다.
- Nawrocki (CoNEXT 2022) §5는 우리 문제를 "open challenge"로 명시해 두었다.
