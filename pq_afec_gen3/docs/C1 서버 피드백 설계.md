# C1 서버 수신 피드백 (탐색 없는 손실 관측)

> 2026-08-23, 구현 전에 쓴 설계다. 근거는 (a) 외부 알고리즘 조사 5영역,
> (b) 모형 스윕 `scratchpad/sim_feedback.py`·`sim_adaptive_value.py`,
> (c) 실측 p11 탐색세다. 이 중 (b)는 시뮬레이션이고 실측이 아니다.

## 1. 문제 (실측·코드로 확인된 사실만)

현행 손실 관측은 `policy.go:433` 한 줄이다.

```go
lossEvent = hctMs > st.ProbeMinHCT*1.3 + 2.0     // unbiased(=m0 탐색) 연결에서만
```

손실을 직접 세지 않고, 핸드셰이크 시간이 기준선보다 길면 손실로 분류한다.
그것도 일부러 m=0으로 가는 탐색 라운드에서만 갱신한다. 패리티가 있으면
복구가 손실을 가려 잔여손실만 보이기 때문인데, 이 진단 자체는 옳다.

이 방식에는 대가가 두 가지 있다.

| 대가 | 크기 | 출처 |
|---|---|---|
| 탐색세 | +0.48~0.51 ms/연결 (임계위 조건 후회의 25~40%) | p11 실측, 11번 패치의 분해 |
| 관측 기근 | 600 연결에 무편향 관측 3~6회 | `policy.go` L851 주석의 실측 + p11 자료 |

## 2. 현행 관측이 적응을 무력화하는 이유

모형 스윕(실측 아님)에 따르면, 손실률이 고정이면 최선 고정팔이 늘 있으므로
적응이 이길 수 없다. 적응이 효과를 내는 것은 손실률이 변할 때뿐이고, 그러려면
추정이 변화를 따라가야 한다. 현행 방식은 관측이 600 연결에 3~6회라 따라가지 못한다.

```
업링크 10Mbps · 손실 2%<->15% 교대 (모형)
  최선 고정팔   51.964
  auto(피드백)  51.545   +0.42 이득
  auto(현행)    52.196   -0.23 손해     <- 탐색세를 아직 안 넣은 값이다
```

p17이 이 예측을 실측으로 판정한다.

## 3. 설계

### 3.1 회신 내용

서버가 첫 비행에서 실제로 받은 것을 센다. 이 값은 이미 `connAcct`가 세고 있다.

```
받은 원본 수 (0..k)      RxOrig 계열
받은 패리티 수 (0..m)    RxParity 계열
복구 수 (0..1)           recovered
```

k<=3, m<=2라서 각각 2비트면 충분하고, 셋을 합쳐 1바이트에 담긴다.

### 3.2 싣는 위치

패리티가 이미 쓰는 방식(`buildParity` / `parseFecBlock`)을 방향만 뒤집어 쓰면 된다.
겉모양이 롱헤더 Initial이라 상대는 이 데이터그램을 연결에 귀속시키지만, AEAD를 통과하지
못하므로 QUIC 스택은 조용히 폐기하고 우리 계층이 가로채 읽는다.

```
[롱헤더 ~20B] [fbMagic 4B] [ver 1B] [flight 2B] [카운트 1B]  ≈ 28 B
```

### 3.3 보내는 시점과 증폭 한도

증폭 한도는 이 설계에서 가장 큰 제약이다. 서버가 첫 비행 중에 회신을 보내면 그
바이트가 증폭 예산을 쓴다. 우리가 최적화하는 대상을 피드백이 갉아먹는 셈이다
(28 B는 한도 3,840~16,640의 0.2~0.7%지만, 우리 임계는 1바이트 단위로 갈린다).

그래서 회신은 클라이언트의 두 번째 비행(Handshake)을 받은 뒤에 보낸다. 그 시점에는
주소 검증이 끝나 증폭 한도가 해제되므로 예산과 무관하다.

부작용도 있다. 클라이언트가 핸드셰이크 직후 바로 닫으면 회신을 받지 못한다. 실측으로
확인하고, 필요하면 닫기 전에 짧은 유예를 둔다. 이 유예가 HCT 측정에 섞이면 안 된다.
HCT는 핸드셰이크 완료 시점에 찍히므로 원칙적으로는 안전하지만,
p16식 음성 대조(피드백 on/off에서 HCT가 같은지)로 확인한다.

### 3.4 생존 편향: C2가 필수인 이유

첫 비행이 전멸하면 서버가 아무것도 받지 못해 회신도 없다. 피드백만 쓰면
손실이 가장 심한 연결이 통계에서 빠지고, 캐시가 낙관 쪽으로 편향된다.

그래서 클라이언트가 첫 비행 PTO를 관측하면 그것을 "n_sym 관측, n_sym 손실"로
적립한다. 회신이 온 연결만 세면 안 된다.

## 4. 검증 계획 (구현 후)

| 자 | 판정할 것 |
|---|---|
| `gate_go_parity` | 피드백 기반 p̂가 netem 참값을 회복하는가 (신규 게이트) |
| p17 | 대역 있는 경로·손실 변동에서 auto가 최선 고정팔을 이기는가 |
| p11 (11번 분해) | 탐색세가 실제로 0이 되는가 |
| p16식 음성 대조 | 피드백 on/off에서 HCT·증폭 임계가 안 바뀌는가 |
| p2 | 임계가 안 움직이는가 (회신 바이트가 예산을 안 먹었다는 증거) |

## 5. 기각한 대안

| 대안 | 기각 이유 |
|---|---|
| 첫 비행에 회신을 실어 보내기 | 증폭 예산을 먹는다 (§3.3) |
| 수신+복구를 합집합으로 보고 | 어떤 심벌이 "손실 후 복구"인지 사라져 손실률 복원 불가 |
| TFRC ALI를 주 추정기로 | 목적지당 1,600~4,000 연결 필요 + 비행 내 손실 다중도를 버린다 |
| 상시 EWMA / 무조건 감쇠 | 정상 채널에서는 감쇠가 최적이 아니다(Garivier). 현행 Go의 `decay=0.99`도 같은 이유로 재검토 대상 |

## 알려진 결함 (2026-09-07 코드 감사, 미수정)

서버 회계 `ca.RxOrigN`은 `FbSent`가 잠기기 전의 Initial 전용 데이터그램을
전부 첫 비행 원본으로 센다. 그런데 `FbSent`는 클라이언트의 Handshake 패킷이
와야 잠기고, 첫 비행이 복구 불가로 모자라면 클라이언트는 Handshake를 보내지 못한 채
Initial을 PTO로 재전송한다. 그 재전송도 `RxOrigN`에 들어가므로
(k=2·m=1에서 O1과 P를 잃으면 O0 + 재전송 O1' + P'로 rxOrig=2 rxPar=1),
클라이언트가 계산하는 `nLost = nSent - nRecv`가 0이 된다. 즉 복구하지 못한
손실일수록 심벌 손실 추정이 낮게 나온다. 잡히는 것은 전멸(C2 갈래)뿐이다.

처방(미적용): 패리티 블록 헤더의 원본 CRC 목록으로 재전송을 가른다(재전송은
패킷 번호가 바뀌어 CRC가 다르다). m=0 연결은 패리티가 없어 가를 수 없으므로
별도 `rxRetx` 필드로 드러내거나 첫 서버 송신 이후의 Initial을 제외해야 한다.
`-feedback`은 기본 파이프라인에서 꺼져 있다(p17은 `PADFEC_FEEDBACK=1`일 때만 켠다).
같은 감사에서 피드백 데이터그램 바이트가 `srv_bytes`에 섞이던 문제는 고쳤다.
