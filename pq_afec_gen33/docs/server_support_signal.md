# 서버 복호 지원 신호 설계 메모

이 문서의 initial-credit은 가칭이다. 번호를 배정하거나 DNS·QUIC 확장을 구현하지 않는다. M4 참조는 테스트베드가 명시한 supported만 복호 지원으로 쓰고, unknown·unsupported는 none·dup·pad 후보로 처리한다. 중복 Initial도 협상 전 첫 비행을 보호할 수 있으므로 raw parity가 유일한 방법이라는 A7-18 원문 표현은 쓰지 않는다.

HTTPS RR의 SvcParam은 서비스 연결 전에 매개변수를 전하는 확장 지점이다. 여기에는 복호 형식 판본, 지원 k·m 및 최대 UDP 길이, 신용을 받을 수 있는 범위, 응답 크기 힌트의 유효 범위를 넣는 방안을 검토할 수 있다. RFC 9460의 기존 키가 PAD-FEC 지원을 뜻하지는 않는다. [RFC 9460](https://www.rfc-editor.org/rfc/rfc9460.html)

향후 구현한다면 신호를 origin·ALPN·포트·실제 서비스 대상과 묶고, TTL과 서버 배포 변경을 반영해야 한다. 인증되지 않은 DNS 응답만으로 복호 지원을 확정하지 않는다. 크기 힌트는 실제 S 관측과 구분하고, 누락·만료·충돌·모르는 판본은 unknown으로 되돌린다. 복호기가 있다는 사실은 Retry 이전에 신용을 받거나 모든 패리티가 복구에 쓰인다는 보장이 아니다.

이전 연결의 인증된 transport parameter를 기억하는 방법도 가능하다. 첫 방문에는 사용할 수 없고, 다음 연결의 다른 backend가 같은 기능을 갖는다는 보장도 필요하다. 서버가 허용한 기억 범위·유효 기간·형식 판본을 별도로 설계해야 하며 기존 transport parameter 기억 규칙만으로 새 기능을 협상한 것으로 간주하지 않는다.

지원 표시는 토큰 수락과 독립이다. 토큰이 Initial에 있어도 서버는 주소 검증 여부를 판단한다. Retry 수락 사건은 클라이언트가 새 토큰을 받았다는 뜻이며 서버가 그 토큰을 검증했다는 관측은 아니다. [RFC 9000 §8.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.1)

검증용 on/off 설정으로 지원 입력을 바꿨을 때의 후보와 실제 wire를 기록한다. 오탐·만료·주소 변경에서 표준 서버가 처리할 수 있는 dup·pad 경로로 복귀하는지 확인한다. HCT 효과와 바이트 동등 비교는 E20·X1, 재방문 성능은 X4가 맡는다. C1 복구 보고는 패킷 수신 ACK를 대체하지 않으며, 첫 비행 뒤 도착한 회신을 첫 정책 결정의 사전 지식으로 쓰지 않는다.
