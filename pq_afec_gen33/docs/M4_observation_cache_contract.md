# M4 재방문 관측 캐시 계약

revisit_cache.py는 활성 L1과 분리한 Python 관측 참조다. HCT 비용을 계산하거나 행동을 고르지 않는다. 주소 토큰의 원문과 TLS 티켓은 저장하지 않는다. 클라이언트가 아는 실제 토큰 전달·수락 Retry와 연결 뒤 TLS DidResume를 사용한다. 서버의 AddrVerified는 캐시 입력으로 받지 않는다.

주소 분류는 no_token_unknown·token_unknown·retry_unknown이고, TLS 분류는 full·resumed·unknown이다. 토큰을 보냈다는 이유로 주소 검증 성공을 기록하지 않는다. 실제 TLS 결과가 없으면 unknown에만 저장한다. TLS 티켓 제안과 실제 재개는 다르므로 ticket_offered=true인 연결의 실행 전 조회는 full·resumed 두 관측을 각각 반환한다. false이면 full만 반환한다. 두 묶음을 합치거나 미래 DidResume로 선택하지 않는다. 이 조회가 어느 행동을 선택할지는 후속 비용 모형의 범위다.

기본 보관 한도는 목적지16개와 각 주소·TLS 분류의 최근32관측이다. 목적지는 관측 입력 순서의 LRU로 관리하고 조회는 순서를 바꾸지 않는다. 관측에는 성공·실패와 누락값을 그대로 저장한다. 실패·토큰 거절을 HCT0 또는 서버 바이트0으로 바꾸지 않는다. 성공 HCT를 수집했다면 양수 유한 ms여야 하며 바이트·k는 명시한 정수만 받는다. 요약의 HCT·서버 바이트·k 이력은 성공 연결에서 실제로 관측된 값만 사용한다.

연속 sequence는 캐시 전체에서 증가한다. 중복·역순 입력과 잘못된 관측은 상태를 바꾸기 전에 거부한다. INVALID_TOKEN은 스택이 확인한 terminal 오류라는 명시 입력만 받으며 token_rejected=true·ok=false이어야 한다. 실제 토큰 또는 Retry가 없으면 거부한다. 반환값은 다음 연결을 토큰 없이 새로 시작하라는 계획이다. 이 모듈이 소켓을 다시 열거나 TokenStore를 수정하지 않는다. TLS 티켓은 별도이므로 재시도에서 제안할 수 있다.

새 직렬화 형식은 별도 STATE_VERSION=1이다. 기존 L1 상태4와 섞지 않으며 구형·미지 판본, 중복 목적지·분류·sequence, 한도 초과, NaN·무한대·bool을 숫자로 넣은 입력을 거부한다. 복원은 새 객체에서 끝낸 뒤 반환한다. 저장·조회 결과는 복사본이다. 현재 구현은 단일 호출 흐름의 참조이며 파일 I/O·동시 실행 동기화를 제공하지 않는다.

단위 검증은 티켓 거절·재개·결측·토큰 거절·중복·직렬화·LRU·한도와 입력 원자성을 다룬다. 기존 T2 및 M4 개발 원자료는 변경하지 않고 관측을 재생해 독립 분류·보관 창과 대조한다. 성능·W1·Go 활성 정책 연결은 이번 참조 결과로 대신하지 않는다.

기존 자료의 ticket_offered는 첫 ClientHello를 인증·재조립한 뒤 pre_shared_key 확장41의 존재로 확인한다. 확장45의 PSK 모드 지원이나 session cache 적중만으로 제안을 추정하지 않는다. 확장 번호와 요청 구조는 [RFC 8446의 확장 정의](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2) 및 [PSK 정의](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.11)를 따른다. 첫 원본이 와이어 기록에서 빠진 경우는 제안 여부 결측으로 남겨 캐시에 넣지 않는다. Go 송신 전 훅에서 직접 얻을 입력과 이 사후 원자료 판독의 범위를 구분한다.
